Narration Audit — flow chart, every branch, every prompt (NARR-01)

Every narration surface in the game — the EVENT_NARRATION table (src/ui/util.js) AND every hand-written flash() call in src/ui/flow.js, src/orchestrator.js and src/ui/util.js — plus every action prompt and button label (ask()/panel() calls, D-30 — the text players read most: every turn, every decision), styled in warm gold so they read at a glance against the teal/amber narration cards — laid out as a flow chart in the order a real game actually plays it: turn start → storm legs → sail → the action prompt and the action you pick → shot clock → round roll-over → voyage end, looping back into the next round, each prompt sitting beside the narration that answers it, its buttons grouped right under it as their own small cards. Every branch a builder can produce is its own editable card — every got/heads/reason/ok/winner/ ingredient-present value and every config-gated variant (the trade-cooperation bonus, the sardine/candycrab rule) gets its own card, grouped inside the moment it belongs to. A moment with more than one outcome is drawn as a fork — several cards inside one box. Each card still carries a keep/cut/merge/rewrite recommendation, a notes field, and persists to your browser (localStorage); the toolbar exports every disposition as JSON.

How this page is built: every card calls the REAL builder — the EVENT_NARRATION table via describeFor/narrationVariants, and the real brokeSailLine/brokeAnchorLine/stormIntroClause — with a fabricated event tuned to that specific branch, so every rendering is the exact code that ships. Every card's HTML also runs through the real emojify(), matching what the shipped panel shows. Hand-written flash() lines that can't be called in isolation reconstruct their wording using the SAME real name/color/icon helpers the source line itself calls; a "Raw source" disclosure on every such card shows the exact JS text the extraction script pulled from the file, for cross-checking.

Flow chart edges are derived from the real call paths in src/ui/flow.js (humanTurn → windLeg legs 1/2 → per-square outcomes → humanAct → its outcomes → shot clock → round roll-over → finish/ bakeoff/end) — never invented. Where reachability genuinely depends on game state that can't be shown structurally (e.g. side-bet settlement only fires when spectating captains remain), the edge is drawn dashed and labelled uncertain.

This pass is self-contained and authoritative (D-25). Every tag you set means "keep/cut/ merge/rewrite AS DISPLAYED ON THIS CARD" — it does not refer back to pass 1. Many cards already show phase-15's new draft wording (second-person forms, the rewritten storm intro, the split battle spoil, the broke-sail/broke-anchor lines); tagging one keep ships THAT text, not a reversion to what shipped before this phase. Only the 17 cards you'd genuinely reached in your committed in-progress session (through the moored "storm shoved you onto it this turn" card) start pre-filled with your real marks — everything past that point starts blank with its own default tag, never a leftover note (D-27; see below).

Every card tracks whether you've actually looked at it (D-27). The toolbar's N of 81 reviewed counter and each card's own checkbox are the source of truth for that — an untouched card is dimmed and its recommendation is a default, not a decision, no matter what tag happens to be pre-selected. Changing a card's tag, or typing in its notes or question field, marks it reviewed automatically; the checkbox is there for the "I looked, the default is right, ship it" case where you change nothing. The export carries reviewed: true/false on every row — 15-06 applies ONLY the rows marked true. An unreviewed row is not a keep; it is unknown, and leaves that line exactly as the code currently is.

Every card now derives and shows its own intent, live, as you type (D-26): choosing cut or merge is always a deliberate choice and wins outright; otherwise an empty notes box means keep (ship the text as displayed), and any text typed into notes is read as replacement copy — the notes field is the rewrite. A rewrite tag left with empty notes resolves to keep and says so explicitly, so an intended rewrite is never silently lost. The derived line under each card's controls (→ KEEP as displayed / → REWRITE to: "…" / → CUT / → MERGE with …) is the actual exported intent — check it, not just the dropdown. Use the separate, dashed "Question for Claude" field for anything that isn't copy (a question, a "is this even called?") — it is never read as a rewrite and ships in the export as its own question field, untouched. If two cards resolve to the exact same rewrite text, both are flagged live (a warning under the derived-intent line, and counted in the banner below) — usually a sign a branch got the wrong text, occasionally intentional, but always worth a second look before it ships.

Two different notices, two different meanings — read the color (D-28). A pink "Merges into: …" note means separate lines in the code that happen to render the same text right now — a genuine merge candidate, pointing at ONE canonical destination (D-36 — see below; this used to be a symmetric "Byte-identical to: …" list before that fix). A teal 🔗 "Shared wording" note means the OPPOSITE: one string in the code reached by several branches (e.g. moored's "still docked" line, referenced by three different reason values) — tagging that merge would send the wrong instruction; keep or rewrite is what applies, and a rewrite there is called out on the derived line itself with every sibling it also changes.

A merge disposition names ONE destination, never a cycle (D-36). Wyatt hit this live: the three trade-wind rim-sweep lines pointed at each other ("many of them say to merge with flow.js:296, but that one says to merge with 571 — and 571 says to merge with 296") because the old cross-reference was symmetric — it listed OTHER byte-identical duplicates, never a destination, so three duplicates with no fourth anchor just pointed in a circle. Every merge card now carries an explicit Merge target selector, defaulting to a curated canonical destination where one is known (his own answer — all three rim-sweep lines merge into EVENT_NARRATION.tradewind — is pre-set) and offered even when the destination's wording differs slightly (byte-matching alone would never surface "carried into the trade winds" as the same moment as "swept into the trade winds"). Override it per card if the default is wrong. checkMergeCycles re-runs live on every tag/target change and fails loudly (banner) if two merge-tagged cards ever point at each other again.

A merge is never shown without a destination — the absence is as loud as the presence (D-44). Wyatt, on parley~refused: "this one is flagged for merging, but I think it's merging with the success message…? That seems wrong." It was: a bare merge tag with no visible target, sitting right below its sibling "Deal struck" card, reads as "merge with that one" — exactly backwards, since deal-struck and refused are opposite outcomes. Root cause: D-19's decision (parley folds into EVENT_NARRATION.trade) had been applied to the recommendation but never pre-set as the target — now fixed on both parley cards, the same way the tradewind trio already were. More generally: an unresolved merge target no longer shares → MERGE into: …'s calm blue — it gets its own loud, ⚠ MERGE: no destination chosen — pick one below state, styled with the same urgency as CUT, so a silent bare tag can never again be misread as pointing at whatever card happens to sit nearby. D-49: the two newround branches that were still unresolved (found sitting in Question fields since D-27) are now confirmed and pre-set the same way — heldStorm → table:newround ("Fresh storm"), streakStormHeldWontQuit → table:newround~streakStormHeldGusting — and the destination cards now name their sources too (the same forward-reference the tradewind trio's target already had, extended here to branch-card destinations, which previously showed nothing).

Every line has TWO renderings — now there are two copy fields (D-47). Neutral and addressed ("you") per D-07/D-10, but the card only ever offered one Notes box — so Wyatt had been writing the addressed version into the Question field, which by design (D-26) never becomes copy. Unfixed, 15-06 would have applied his neutral rewrites and silently discarded every "you" variant — a data-loss bug, not a convenience gap. Migrated conservatively, once, on load: a question moved to the new field only where it clearly specified the addressed rendering (matching you[- ]version, the "you", addressed, or opening with ye ) — everything else was left exactly where it was, since a wrong migration turns a genuine question into shipped copy, the precise failure the Question field exists to prevent. The two merge-target questions (D-49, above) were cleared rather than moved, since their answer is now the mergeInto selector itself — never left duplicated where a stale note could disagree with it (D-44). A one-time summary banner shows exactly what moved, so it can be checked against what he meant, not discovered later.

A TWO-PARTY line has THREE renderings — D-47 one step further (D-54). Wyatt, of the battle-opening card: "these battle lines NEED three options, just like are currently displayed. can you add those just here for parity?" — he was right: a battle names both an attacker AND a defender, so it renders neutral, addressed-to-attacker, AND addressed-to-defender, but D-47 only ever gave a card ONE addressed field. A rewrite of the second party's line had nowhere to go — exactly the D-47 bug, one layer deeper. Every two-party card (13 of them: battle ×3 branches, battleflee, parley ×2, trade ×2, blocked, bakeoff, the battle-opening announcement, and both side-bet lines) now gets a SECOND addressed field — derived from the card's own already-rendered variant count (.variantRow boxes actually on the page), never a hand-listed set of ids, so a future event with more subjects, or fewer, is picked up automatically. Labelled by role, never by sample seat name — "Addressed to the attacker"/"…the defender", "…the offerer"/"…the other captain" — since "Addressed to Davy Scones" says nothing about which role actually ships that line. Its own export key (addressedNotes2/addressedFinalText2, plus addressedRole/addressedRole2 carrying the exact role wording shown), its own derived line, and it drives the same auto-rewrite rule the other two copy fields do. The existing addressed text on those 13 cards was drafted from the first-named party's side (attacker/offerer/bettor) — left exactly where it is; the new field starts empty for the second party, so nothing already written moved or was overwritten.

Every card speaks pirate now — "ye"/"yer" (D-29, confirmed). you→ye, your→yer, you're→yer (one word does both jobs, his call), case-preserving, applied live to EVERY card on this page — narration, prompts, button labels — because keep means "ship exactly what this card displays" (D-25): if the conversion happened later instead, what you'd be approving here wouldn't match what actually ships. Type a rewrite into a notes box in plain English — it converts the same way, shown on the derived-intent line, so you never have to type "ye" by hand.

Scope is now "every string a player can read," not a fixed mechanism list (D-32). D-03/D-21 covered the EVENT_NARRATION table and flash()/ onFlash(); D-30/D-31 added ask()/panel() prompts and their buttons. Each time the page looked complete against ITS OWN definition of scope, and the definition was too narrow — an independent sweep found roughly 50 more strings still absent: the pre-game intro/barrier banners (the very first text any player reads), the end-of-voyage award names+bylines (the last), the live battle/bakeoff round-result lines, multiplayer room-join/service alerts, recipe-draft/waiting broadcasts, six of the seven dock-flavour hauls, the timer-toggle tooltip, and the pass-and-play hand-off screen. All of it is on this page now, placed where it actually fires — intro banners at the very start, awards at the very end, room-join errors in their own pre-game group — and a dedicated self-check (checkMiscCoverage) fails loudly if any of it, or a future addition in the same style, has no card.

The inverse also matters: no card may show text a player can never actually read (D-33/D-34). Wyatt found both by asking a card "when is this written?"/"isn't that used instead of this button?" — and was right both times. D-33: humanFlip()/fishCast() render ask(label||"<fallback>",opts); the extractor can only see the fallback lexically at that call site, never what a caller actually passes. Every real caller supplies a label, so the fallback shown at flow.js:103/:125 is provably unreachable — Wyatt had already typed a rewrite against one. D-34: an option flagged back:true or flip:true is excluded from the rendered button row entirely by localAsk() and replaced with a hardcoded control (a circular "‹", or the flippable coin) — the option's own label text (← Back, ← Actually, move instead, 🌕 FLIP!, 🎣 CAST!) is never shown to a player. Every one of these is still ON this page (so coverage — and any disposition already recorded against it — survives) but is loudly marked ⚠ dead copy with a pointer to the real text (a caller's actual prompt) or the real control (the ‹/coin), and defaults away from keep. checkDeadCopyMarking fails loudly if any known-dead card is missing its marker.

Every parenthesised coin amount carries an explicit sign, applied LIVE (D-38). Same principle as D-29's ye/yer: keep means "ship exactly what this card displays" (D-25), so a sign rule applied only later, at 15-06 time, would make every keep on an affected card approve something different from what actually ships — the flee card used to read (pays 1🌕); the shipped text reads (−1🌕). Two passes, run at the same chokepoint every other live conversion uses: a MECHANICAL one (any ASCII hyphen used as a minus inside a parenthesised coin amount becomes U+2212 −, everywhere, no direction judgement needed) and a TARGETED one, Wyatt's own confirmed table — battleflee's (they pay 1🌕)/(pays 1🌕) and fish's bare (2🌕)/ (1🌕) each become an explicit +/−. Scope stays narrow on purpose: amounts inside a sentence and price-only button labels stay unsigned, and flow.js:461's composed trade-offer summary ("Wheat + 2🌕", where + means "and also") is a recorded exception, never touched. checkSignRule fails loudly if any parenthesised coin amount is still unsigned or still uses an ASCII hyphen.

Fabricated events must be ones the real game could produce (D-51). Wyatt, of table:battle~crate: "this shouldn't say 'null' right? … Crustbeard takes null." It shouldn't, and the game never produces it — a hand-written spoil: null reached a rendered card. A third class of defect, distinct from the two already self-checked: D-21 catches a branch the game produces but no card renders; D-33/34/ 40/43 catch a card rendering text the game can never produce; this catches a card rendering the RIGHT line with IMPOSSIBLE VALUES — copy judged against numbers that could not occur. Every fabricated battle event (both the rendered cards and the self-check probe's own field-enumeration) is now asserted against its real emit sites' invariants: spoil and spoilIng are always set together (derived via ilabelImg(), the same helper the game itself calls — never a hand-written literal, which is how the null got in), and a battle's score must be one asyncBattle()'s own first-to-2 rule could actually reach (a fabricated 1–1 tie is impossible — fixed to a genuine 2–1 in 3 rounds). Checked against every OTHER fabricated event on the page for the same class of defect (paired fields, reachable scores) — see the plan's own execution notes for the full audit; everything else either had no such invariant or was already internally consistent.

A THIRD badge — reachable in principle, guarded in practice (D-40). Distinct from D-33 (structurally unreachable) and D-34 (a marker label a control replaces): this text COULD render, but a normal game never reaches it because an upstream guard — usually a disabled button, which localAsk() gives no click handler at all — prevents it. Wyatt has now spent a rewrite on the wrong half of a near-identical pair three times running (D-33's dubloon fallback, D-34's back labels, and the canonical case here: flow.js:582's "can't afford powder" flash, guarded by the Attack button's own disabled:!canAfford, while the wording a player actually reads lives on a different card — the sub helper text at flow.js:560). The 🛡 guarded badge names the guard and points at that live sibling; it is deliberately a different color from ⚠ dead copy because this text is worth keeping (a real safety net, e.g. against a desynced multiplayer client) — the badge only redirects a rewrite, it never asks for deletion. Curated by hand, not a general detector: proving a guard unreachable requires cross-referencing an if(<condition>) around a flash() call against a disabled: flag on an option in a different function entirely, which is real control-flow analysis this page's text-scanning tools aren't built to do safely yet.

Typing in Notes auto-selects "rewrite" — the dropdown stops disagreeing with the decision (D-42). D-26's derived intent already treats non-empty notes as rewrite regardless of the dropdown, and the export already carries that derived intent — the dropdown was never the source of truth, it just visibly disagreed, so every card cost a manual double-check. Now: typing non-empty notes on a keep-tagged card auto-selects rewrite; clearing the notes box reverts an auto-set rewrite back to keep. A manually-chosen rewrite (picked from the dropdown itself) is unaffected by clearing notes — it stays. cut/merge are untouched no matter what the notes say, preserving D-26's own precedence exactly: those two are deliberate choices and always win. A one-time retro-fix on load corrects any card already showing keep with non-empty notes — no disposition changes (the derived intent there was already rewrite), only the visible control catching up.

A branch the shipped config can never produce is badged too (D-43). Wyatt asked of table:trade~noBonus ("Cooperation bonus OFF") "when does this get shown?" — never: roundCfg() (src/engine/index.js) hardcodes tradeBonus:true and nothing in src/ ever mutates cfg afterward. Same for fish's "sardine rule OFF" branch (sardine:true, always). D-21's own branch enumeration was still right to render both — completeness matters — but the page never said which variants the CURRENT shipped configuration can never actually reach. Derived live by parsing roundCfg()'s own returned object literal (never a hand-written list): any TABLE_BRANCHES entry whose cfg override flips a flag away from what roundCfg() hardcodes gets the same 🛡 guarded badge as D-40 — worth keeping (correct the moment that flag becomes a real option), not worth a rewrite today. Because it is derived by parsing rather than a curated list, a flag that later stops being a literal (becomes a real, computed option) silently stops being flagged — nobody has to remember to update anything here.
