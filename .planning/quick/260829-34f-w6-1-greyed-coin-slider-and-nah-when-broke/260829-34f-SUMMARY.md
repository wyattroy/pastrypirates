# W6-1 — done

## What Wyatt asked

> **"Would ye offer any coin on top?" appears with NO SLIDER** when the player has no money left.
> **Expectation: the slider appears greyed out, and the button reads "Nah" instead of "Offer it!"**

## The cause

`coinSlider()` in `src/ui/flow.js` short-circuits on `max <= min` — *"nothing to choose — do not
present a slider with one stop on it"* — and falls through to a plain button list carrying the
caller's confirm label. So a broke captain was asked a yes/no question **with no visible control and
an affirmative button**.

That reasoning is still right for a range like 3..3. It is wrong for an **empty purse**, because
there the missing control *is* the answer to the question: the sentence asks whether to add coin and
the screen shows nothing to add it with.

## Measured, in the real browser, through the real function

| | drawn | disabled | opacity | cursor | number |
|---|---|---|---|---|---|
| a live slider | yes | no | 1 | default | 1 |
| an empty purse | **yes** | **yes** | **0.38** | **not-allowed** | **0.38** |

`disabled` does both jobs with one mechanism — the browser refuses the drag *and* the stylesheet
greys it — so there is no second state to keep in step with the markup.

## A DELIBERATE EXCEPTION TO RULE 8, flagged rather than decided — see Q-17

`coinSlider` has two callers and they need different words:

- the **offer** asks a question — *"Would ye offer any coin on top?"* — which **"Nah"** answers;
- the **counter** states a fact — *"ye're ASKIN' X for yer Y"* — where "Nah" would read as
  cancelling the whole counter-offer rather than declining the coin.

So the **mechanism is identical** for both (a greyed slider, and a caller-supplied decline label) and
only the **word** differs, because only the sentence does. Inventing a word for the counter would be
putting copy in his mouth, so the counter keeps "Ask it!" and the question is his.

## An existing gate fired, correctly, and was re-anchored rather than weakened

`w29_coin_question_check.mjs` watches the label passed to this exact call and required the argument
list to END at `"Offer it!"`. Adding the decline label broke it, and it said so. It now anchors on
the **label closure** it actually cares about and lets the argument list grow — an assertion that
breaks when an unrelated argument is appended is watching the shape of a line, not the thing it is
for. Red-proofed: it still fails when the label itself is broken.
