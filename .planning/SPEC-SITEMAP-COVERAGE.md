## In one paragraph, for a decision

**The risk he named is real, it is not guarded, and it is about to bite** — the next page this
project ships (`/rules.html`, `T-100`, already speced) would go missing from the sitemap in silence.
**But generating the page list from the directory is the wrong cure**, because which pages belong in
a search index is an editorial judgement, and a directory walk needs a hand-kept exclusion list — the
same rot moved somewhere he cannot see it. **The recommendation is that the fence and the guard are
the same job:** make every page declare whether it is public (which it should be anyway, per the
finding above), and then the coverage check derives its answer from those declarations with no list
in it at all.

## What already exists, and the half of his ask it does *not* cover

`scripts/qa/sitemap_write.mjs` was built under `T-098`. **It regenerates the DATES from git and
deliberately does not discover pages** — its own comment (`:12-16`) says the URL list is read out of
the existing file because page membership is editorial. That was the right call for the ask it was
serving (*"derive the dates, do not hand-type them"*). **It is not this ask.**

`scripts/qa/sitemap_lastmod_check.mjs` is the gate. It walks **sitemap → files**: for every `<url>`
block, does that page exist, and does its `<lastmod>` match `git log -1 --format=%cs`. **The
opposite direction is invisible to it by construction** — a page that exists with no entry is never
looked at, because the loop only ever iterates entries that are already there. Its own header states
the assumption out loud at `:22-24`: *"Add a page to the sitemap tomorrow and it is covered the
moment it is listed."* **"The moment it is listed" is the silence he is describing.**

This is the shape `CLAUDE.md` §2 already names: a gate aimed one direction is not silent, it is
*reassuring*. `sitemap_lastmod_check` will pass green forever on a sitemap missing half the site.

## The three options, with the trade-off stated

### A — fence the working files, then let the gate derive coverage from the fence ✅ **RECOMMENDED**

**Two halves, and the first half is worth doing on its own merits whatever he decides about the
second.**

**A1 — close the fence (this is the finding above).** Four `robots.txt` lines, in the same shape the
file already uses for `lab.html` and `stats.html`:

```
Disallow: /art-review/
Disallow: /notes/
Disallow: /scripts/
Disallow: /.planning/
```

**A2 — then the coverage rule works with no exception list in it**, because once the fence is
closed, "public" is a thing every path declares:

> a tracked `.html` that is **served at the site root or one directory below**, is not `Disallow`ed
> in `robots.txt`, and does not carry `noindex`, must have a `<loc>` in `sitemap.xml`.

After A1 that rule matches exactly `index.html`, `about.html` and `classic/index.html` — two listed,
one `noindex` — and **nothing else**, so it is green today and goes red the day `/rules.html` lands
unlisted.

- **What it buys:** his silent failure becomes a loud one, and thirteen working files stop being
  crawlable.
- **What it costs, honestly revised:** A1 is four lines. A2 is one function in a file that already
  parses both sides, plus a red-proof. **A1 alone is minutes; A1+A2 is one watch.** *(The first
  version of this file sized A2 alone at "one watch" and had no A1 in it. That sizing was wrong,
  because without A1 the rule fails on 13 of his own pages — CEO 150.)*
- **What it does not do:** it never writes `sitemap.xml`. That file is a site-identity file
  (rule 14) and the repair stays a deliberate command — a guard that silently repairs its own
  subject can never be seen to have failed.
- **Why it fits the house rules:** after A1 it derives its answer from the pages and from
  `robots.txt` rather than from a list somebody typed for it (`CLAUDE.md` §6 — *"a hand-kept list of
  what to guard rots exactly like the thing it guards"*). **The "one directory below" clause is the
  one hand-set knob left, and it is there to bound how deep the site goes, not to name pages.**

### B — generate the page list from the directory, as his sentence literally proposes

- **What it buys:** the sitemap can never be missing a page, because nobody maintains it.
- **What it costs, and this is why it is not recommended:** 13 tracked `.html` files, 2 of which
  belong. A directory walk adds eleven wrong ones unless it carries exclusions — and an exclusion
  list is the hand-kept list he is trying to get rid of, moved into a script where he cannot see it.
  It could read the `noindex`/`robots.txt` declarations instead (that is option A's logic), but then
  it is *writing* a site-identity file from inferred rules, and a wrong inference publishes itself
  to Google with nothing in between.
- **Honest note:** B is not absurd. It is the same idea as A with the arrow pointing the other way.
  **A reports; B publishes.** On a file that can affect the live domain, reporting is the safer half.

### C — leave it, and remember

- **What it buys:** nothing to build.
- **What it costs:** exactly the failure he described. `T-100` is the next page and it is already on
  the Chart.
