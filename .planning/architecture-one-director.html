Pastry Pirates · back-end direction · 2026-08-30

One engine, one director

How to structure the game so that solo, pass-and-play, host and guest cannot drift apart — and so they still cannot drift apart after two years of new features.

00The thesis

The turn loop should produce a script. The client should perform it.

Today the turn loop performs it directly — and only one client runs the turn loop.

Everything below follows from that one sentence. It is not a rewrite: measured this afternoon, the rules engine is already completely pure — src/engine/index.js contains zero references to host, guest, mode, the DOM or the network. The foundation is sound. What is tangled sits one storey up.

01What is actually wrong, measured

The problem is not that the guest has different code. It is that two jobs are being done by one file. src/ui/flow.js is simultaneously the turn director (whose go is it, what are they asked, what happens next) and the screen director (look here, hold this for 400ms, animate the boat along this path). Those are different jobs with different lifetimes, and only the authority runs that file.

FileisHostpassAndPlayWhat that means

Two consequences you have already seen with your own eyes. The camera: the instruction "look here" is issued twelve times inside the turn loop and is not an event, so it never crosses the wire — the host's camera is directed, the guest's is nudged. The route: the engine computes the real legal path through the water, hands it to the host's animation, and publishes an event containing the seat number and nothing else. The path is dropped on the floor.

02Four layers, and one hard rule

DECISIONS GO DOWN
L4 · Performer
The only thing that touches the screen
Plays storyboards. Owns the DOM, timers and animation. Identical on every client, in every mode.
L3 · Presentation
Event in, storyboard out
A pure function: given an event, return an ordered list of beats — draw this, look there, hold 400ms, clear that. No DOM, no timers, no network. This is where the camera cues and the sail route belong.
L2 · Authority
Whose turn, what are they asked, in what order
Owns the clock and produces the ordered event stream. Exactly one instance per game, wherever it happens to live.
L1 · Rules
State + decision → new state + facts
Already pure today. Knows nothing about time, screens, players or the network.
FACTS COME UP

The hard rule: calls only go down, facts only come up. L4 never calls L2. L3 never touches the DOM. L1 never learns a screen exists.

That rule is what makes the structure survive people — including future sessions of me. A layer violation becomes a mechanical fault a gate can fail the build on, rather than a judgement call somebody has to notice in review.

Why L3 must be pure, specifically

Because a pure function can be compared. If presentation is a function from events to storyboards, then two clients given the same events must produce byte-identical storyboards — and that is a fast headless test, not a two-browser expedition. It turns "do the screens agree?" from a thing you hope about into a thing the build knows.

03Where the modes go to die

Solo, pass-and-play, host and guest differ in exactly one respect: who answers a question. Nothing else. Not the rules, not the drawing, not the pacing.

// one interface, four implementations, zero branches anywhere else
askDecision(seat, question) → answer

  solo           human at this device  |  bot
  pass-and-play  human at this device, behind a hand-over gate  |  bot
  crew (host)    human here  |  remote human, over the wire  |  bot
  crew (guest)   — does not decide at all; it watches

Mode becomes a table of Deciders, not a set of ifs scattered through the code. The authority layer does not branch on mode; it asks. This is the whole structural answer to "how do all modes stay consistent" — you delete the concept of mode from every layer except the one line that chooses a Decider.

04And then there is no guest

Once L2 produces an ordered event stream and L4 consumes storyboards, the network is merely a way to move events from L2 to L4.

  • Solo is a client whose authority is local.
  • A guest is a client whose authority is remote.
  • A spectator, a replay, a second device — all the same client, with a different event source.

There is no guest code path to keep in sync, because there is no guest code path. That is the property you actually asked for, and it is the only version of it that survives a year of new features: not "we remember to update both," but "there is one."

The middle one deserves emphasis. It compares scripts, not pixels — so it is deterministic, fast, and runs on every commit. Every one of the fourteen problems from this morning's playtest would have failed it. That is the difference between a rule you believe in and a rule the repository enforces while you sleep.

06Migration — six steps that each ship

A big-bang rewrite is how this dies. Strangler fig instead: the new path grows alongside the old one, and the old one is deleted last.

  1. Define the storyboard, and teach L4 to play one. Route exactly one event kind — sail — through it, on every client. Nothing else changes.
  2. Put the route on the event. Delete the host-only animation call sites. The guest's boat starts sailing the actual water. First visible win.
  3. Move the camera cues into storyboards, one at a time. Twelve of them. Each is small and independently verifiable.
  4. Stand up the storyboard-parity gate as soon as two event kinds are converted — early enough that it guards the rest of the migration rather than certifying it afterwards.
  5. Introduce the Decider interface. Convert solo first (simplest), then pass-and-play, then crew. Mode branches start disappearing.
  6. Delete the old paths and turn the layering gate on strict. Only now.

07Three things I would push back on

The determinism corpus will object, and it has a point

Putting the route onto an event changes what the engine emits, which by this project's own rules invalidates the replay corpus and forces a gated re-record. My recommendation is to avoid that entirely by splitting the event in two: a canonical part that determinism hashes, and a presentation payload attached to it that determinism ignores. That is a better distinction anyway — it stops presentation detail leaking into the definition of a legal game. But it is a decision, not a detail, and it is yours.

Worth disagreeing with

Perfect simultaneity is not achievable and should not be the goal. The network guarantees a guest is always roughly a tenth of a second behind. Chasing literal "same thing at the same instant" leads to lockstep with stalls, which plays worse than what you have. The invariant I would hold instead: both screens show the same sequence, and neither can show a beat the other never receives. Same script, possibly a moment apart — never a different script.

The host's tab is your server, and one day that will matter

Not now. But today the authority lives in one player's browser, so the host closing a tab ends everybody's game. The layering above is precisely what makes moving the authority elsewhere — a dedicated tab, or a real server — a change of where L2 runs rather than a rewrite. Worth knowing the door is being left open, and worth not walking through it yet.
