# Stack Research

**Domain:** Zero-build native-ES-module refactor of a vanilla HTML/CSS/JS browser game
**Researched:** 2026-07-24
**Confidence:** HIGH (verified against current npm registry versions, current Node.js `vm` docs, and Firebase's own modular-upgrade docs; MEDIUM on the exact GitHub Pages MIME-serving behavior, which is not independently testable from here but is well-established industry practice)

## Recommended Stack

### Core Technologies

| Technology | Version | Purpose | Why Recommended |
|------------|---------|---------|-----------------|
| Native ES modules (`<script type="module">`) | Browser built-in (ES2020+ baseline, universally supported since ~2018 in evergreen browsers incl. Safari 11+) | Split `index.html`'s inline script into `js/engine.js`, `js/ui.js`, `js/net.js`, etc., loaded by the browser directly | Decided constraint. Native modules give you real file-scoped variables (no more implicit `window` globals — the #1 requirement of the "tame 40+ globals" cleanup), static `import`/`export` for tracing coupling, and automatic deferred/ordered execution — all with **zero tooling**. This is the only option that satisfies "no bundler" literally. |
| Node.js (for dev-only scripts) | **>=20** (repo's current runtime is v25.9.0; recommend pinning `"engines": { "node": ">=20" }` in `package.json`) | Runs `scripts/*.js` test/sim harnesses, `madge`, `eslint` — never shipped to the browser | Node has supported stable native ESM (`import`/`export`, `package.json` `"type": "module"`, dynamic `import()`) since v12–14; nothing here needs anything newer than what's already installed. Pin a floor, not a build requirement. |
| `package.json` with `"type": "module"` | n/a (new file — repo currently has none) | Tells Node "treat `.js` as ESM by default" so the **same** `js/engine.js` file can be `<script type="module" src="js/engine.js">`'d by the browser *and* `import`-ed directly by Node test harnesses, with zero transpilation and zero duplicate files | This is the crux of the "how do Node harnesses load ES-module source" question. Without it, Node treats bare `.js` as CommonJS and `import`/`export` syntax throws `SyntaxError`. With it, `node scripts/real_game_test.js` and browser-side `<script type="module">` load the identical file through native ESM in both runtimes — no `.mjs` renaming gymnastics needed. **Caveat:** this makes ALL `.js` files under the repo root ESM by default for Node, including the existing `scripts/*.js` harnesses — see Node/test-harness section below, they must be converted or given a `.cjs` extension. |
| Firebase JS SDK — **compat build, stay on v12.15.0** (loaded as classic, non-module `<script>` tags, unchanged from today) | 12.15.0 (current registry latest is 12.16.0 — a minor bump, not required by this refactor) | Multiplayer sync (`firebase.database()`, `.ref()`, `.on()`/`.off()`, `.push()`, `.set()`) | See "Firebase-ES-module interaction" below — this is the concrete decision the downstream consumer needs. Short version: **do not migrate to the modular v9+ API as part of this milestone.** The compat build's global `window.firebase` object is fully readable from `<script type="module">` code (verified: modules are always execution-deferred; the existing compat `<script>` tags in `index.html` have no `defer`/`async`, so they run synchronously during parse, before any deferred module script's top-level code runs — the global is guaranteed to exist). Rewriting every `.ref()/.on()/.push()` call site to the modular functional API (`ref()`, `onValue()`, `push()`) is a full API-surface rewrite of the networking layer, not a structural split, and would put the "determinism must not break" constraint at real risk for no benefit this milestone actually needs. |

### Supporting Libraries

None. There is no npm-installed runtime dependency for the shipped game — `index.html` continues to load Firebase compat from the `gstatic.com` CDN exactly as it does today; the only new npm packages in this stack are **devDependencies** for local tooling (below), which never ship to the browser.

### Development Tools

| Tool | Purpose | Notes |
|------|---------|-------|
| `python3 -m http.server` | Local static dev server for testing the modular split in a browser | Already available (repo dev machine has Python 3.9.6 confirmed). Verified locally: `mimetypes.guess_type('foo.js')` → `('text/javascript', None)` — correct JS MIME type out of the box, no config needed. This has been the default `.js` MIME mapping in Python's `mimetypes` module since 3.9 (previously `.js` could map to `application/octet-stream` on some platforms, which browsers reject for `<script type="module">`). Run from the repo root: `python3 -m http.server 8000`, then load `http://localhost:8000/index.html`. **This replaces `file://` dev workflow**, consistent with the milestone's decision to drop `file://` support. |
| `npx serve` or `npx http-server` (optional, NOT required) | Alternative static server with live-reload / nicer directory listing | Only reach for this if the team wants auto-reload during the split; `python3 -m http.server` alone is sufficient for correctness. Both are npx-invoked (no permanent install needed) so neither adds a build step — they're a dev convenience, not a shipped artifact. Current versions: `serve@14.2.6`, `http-server@14.1.1`. |
| `madge` v8.0.0 | Static circular-dependency detection across the new `js/*.js` ES modules | Run as `npx madge --circular --extensions js js/`. Verified current version via npm registry. Madge parses ESM statically (no execution, no bundler) — a correct fit for "no build step." **Important nuance to carry into the split:** unlike CommonJS, native ES modules *support* circular imports via live bindings — a cycle is not automatically fatal. What madge actually catches for you here is the *dangerous* case: a cycle where one module reads an imported binding at module-evaluation time (top level, not inside a function) before the other module has finished initializing it — that throws a real `ReferenceError` (TDZ) in the browser console. Use madge to enumerate cycles, then manually confirm each one only accesses the imported binding lazily (inside a function/method body), which is the safe pattern. |
| ESLint v10.7.0 + `eslint-plugin-import` v2.32.0 (optional but recommended) | Catch stray globals during the de-globalization pass (`no-undef` with an explicit `browser: false` env + a small allowlist) and enforce `import/no-cycle` as a second, faster check than madge | This is new tooling for this repo — `CLAUDE.md` currently documents "No formal linting." Framed here as **narrowly scoped to this refactor's specific risk** (globals leaking, accidental cycles), not a general style-linting adoption — keep the config to `no-undef` + `import/no-cycle` and skip stylistic rules to avoid scope creep. Runs via `npx eslint js/` in CI/pre-commit; never touches the shipped bundle since there is no bundle. If Wyatt would rather not add a new tool at all, the module system itself already does most of this job for free: an unresolved reference in an ES module throws `ReferenceError` immediately at runtime (module scope, unlike classic scripts, does not silently fall through to `window`), so the fast feedback loop exists even without ESLint — ESLint just moves that feedback from "browser console at runtime" to "editor/CI at write time." |
| `node:assert` + `node:test` (optional, for `dlog_replay_test.js`-style pass/fail harnesses only) | Built into Node since v18/v20, zero install | `dlog_replay_test.js` already hand-rolls a `check(name, actual, expected)` counter pattern; `node:test`'s `describe`/`it` + `node:assert/strict` can replace that boilerplate 1:1 if desired. **Not recommended for `real_game_test.js` / `battle_sim.js`**, which are statistical dumps (win rates, averages) rather than pass/fail assertions — their existing `console.log` + `padEnd`/`pct()` formatting convention (per `CLAUDE.md`) is the right tool for that job and shouldn't be forced into an assertion framework. |

## Installation

```bash
# No runtime/production dependencies — index.html keeps loading Firebase compat from the
# gstatic.com CDN exactly as it does today. Nothing to `npm install` for the shipped game.

# Dev tooling only (new package.json, devDependencies):
npm init -y   # then set "type": "module", "private": true
npm install -D madge@^8 eslint@^10 eslint-plugin-import@^2

# Local dev server (no install — already on the machine):
python3 -m http.server 8000
```

## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|-------------|-------------|--------------------------|
| Firebase **compat** build, unchanged | Firebase **modular v9+** SDK via ESM CDN imports (`import { getDatabase, ref, onValue, off } from "https://www.gstatic.com/firebasejs/12.16.0/firebase-database.js"`) | If a *future* milestone explicitly wants to rewrite the networking layer. It's a real, verified option — the modular build is native ESM and importable straight from the CDN with no bundler, and `onValue()` returns its own unsubscribe function, which actually pairs nicely with this milestone's `.off()`-teardown cleanup goal. But it means touching every `.ref()/.on()/.off()/.push()/.set()` call site across the multiplayer sync code, which is a rewrite of working, determinism-sensitive logic — too much blast radius to fold into a *structural* split milestone. Flag this as a deliberate, revisitable decision, not a default. |
| `python3 -m http.server` | `npx serve` / `npx http-server` / a hand-rolled Node `http` one-liner | Only if live-reload-on-save becomes a real friction point during the split. All are equivalent for correctness (proper MIME types for ESM); the python option needs zero install. |
| `madge` for cycle detection | `dpdm` (npm, v4.2.0) or ESLint's `import/no-cycle` rule alone | `dpdm` is a fine equivalent (also static, also zero-execution) if madge's Graphviz-oriented output isn't wanted — pick one, not both. `import/no-cycle` alone is lighter-weight (no separate CLI invocation) but less visual; good as a CI gate once `madge` has been used once to map the initial boundary graph during planning. |
| Relative-path imports (`./engine.js`, `../shared/constants.js`) for internal modules | Import maps (`<script type="importmap">`) for bare specifiers (e.g. `import { Game } from "#engine"`) | Only if the module graph gets deep enough that relative paths (`../../js/engine.js`) become genuinely hard to read. For a ~5,200-line file splitting into a handful of top-level modules, relative paths are simpler, need no extra `<script>` block, and avoid a second thing to keep in sync with the file layout. Don't introduce import maps preemptively. |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| Vite, esbuild, Rollup, Parcel, webpack — any bundler | Explicit decided constraint: "no bundler." Also would reintroduce a build step (`npm run build`) that breaks the "push static files to GitHub Pages" deploy model this milestone is preserving. | Native `<script type="module">` + relative imports, served as-is. |
| TypeScript / `.ts` files, JSDoc-driven `tsc --checkJs` type-checking build | Explicit decided constraint: "no TypeScript." `tsc` even in check-only mode is a build step someone has to remember to run, and the codebase's existing convention is deliberately untyped, compact vanilla JS. | Keep plain JS; use ESLint's `no-undef` for the one specific problem (stray globals) that type-checking would otherwise be reached for. |
| Firebase **modular v9+ SDK** as a wholesale swap-in this milestone | Not achievable as a drop-in — Google's own docs are explicit that the modular SDK "cannot be used alongside the existing namespace-based library" (i.e., you can't `firebase.database()` *and* `getDatabase()` against the same app instance without the compat shim bridging them), and swapping fully means rewriting every multiplayer call site. That's a scope and risk mismatch for a structural-split milestone with a hard "determinism must not break" constraint. | Compat build, unchanged, treated as an intentional global (see Firebase section above). Revisit modular migration as its own future milestone if wanted. |
| Node `vm.SourceTextModule` / `--experimental-vm-modules` for the test harnesses | Verified still experimental as of the current Node.js docs (checked against v26.x docs, no change from earlier versions) — an experimental flag is a bad foundation for a test harness meant to get *more* trustworthy, not less. It's also solving a problem the refactor itself removes: `real_game_test.js`/`dlog_replay_test.js` only need `vm` today because the `Game` class is buried inside `index.html` and has to be regex-sliced out. Once it's a real file, plain `import()` replaces the entire vm dance. | Plain Node ESM: `import { Game, roundCfg } from "../js/engine.js"` (or dynamic `import()` if you need to stub `document`/globals first — see below). |
| `<script type="importmap">` for Firebase or other CDN packages | Unnecessary — Firebase CDN imports use full URLs, not bare specifiers, so no import map is needed even if the modular SDK is adopted later. Import maps add a second source of truth for module resolution with no benefit here. | Full CDN URLs directly in `import` statements (already how the modular-SDK alternative above would work, if chosen later). |

## Stack Patterns by Variant

**If the `Game` engine class still touches `document`/`window` at construction time (it currently does — see `real_game_test.js`'s sandbox comment: `document.body.innerHTML = emojify(...)` runs at boot inside the extracted engine region):**
- Treat that as a bug the split should fix, not a pattern to preserve. The `Game` class belongs in `js/engine.js` with **zero DOM references** — that's what makes it importable in Node with no stubbing at all, and it's also literally what "harden the deterministic engine/replay module seams" (an Active requirement) means in practice: a pure-state-in, events-out class.
- Until that's fully true, the Node harness needs a minimal global stub set *before* importing the module (globals must be assigned prior to the `import`, e.g. via a tiny `--import` preload script or by setting `globalThis.document = {...}` at the very top of a `.mjs` entry file before a dynamic `await import(...)`), because static `import` statements are hoisted and evaluate before any code in the importing file runs.

**If a module needs to run identically in both the browser (`<script type="module">`) and Node (test harness):**
- Keep it framework/DOM-free and export plain functions/classes (`export class Game`, `export function roundCfg`). Node and the browser then load the *exact same bytes* — no adapter file, no `.mjs`/`.js` split, thanks to root `package.json`'s `"type": "module"`.

**If a module is browser-only (UI rendering, Firebase networking) and never needs a Node harness:**
- No special handling needed — it just never gets `import`-ed from `scripts/`. Don't over-engineer isomorphism into `js/ui.js` or `js/net.js`; only `js/engine.js` (and any shared pure helpers/constants module) needs the "importable from Node" property.

## Version Compatibility

| Package A | Compatible With | Notes |
|-----------|------------------|-------|
| `firebase*-compat.js@12.15.0` (classic `<script>`, no `type=module`) | `<script type="module">` app code on the same page | Confirmed via the classic-script-execution-order mechanism (not Firebase-specific): non-deferred classic scripts run synchronously at parse time, before any deferred/module script's top-level code — so `window.firebase` is guaranteed set before app modules run, with the compat tags left exactly where they are today (lines ~25–26 of `index.html`, ahead of the future `<script type="module">` tags). No reordering strictly required, but keeping them visually above the module tags documents the dependency. |
| Firebase compat build | Firebase **modular** build | NOT compatible for direct mixed usage against the same `firebase.initializeApp()` instance without the compat shim doing the bridging — this is why the recommendation is "stay on compat," not "mix compat and modular." |
| `package.json` `"type": "module"` | existing `scripts/battle_sim.js`, `scripts/real_game_test.js`, `scripts/dlog_replay_test.js` (currently CommonJS: `require("fs")`, `require("vm")`) | **Breaking**, not just additive — once root `package.json` sets `"type": "module"`, plain `.js` files under it are parsed as ESM by default and `require()` throws `ReferenceError: require is not defined`. Every existing `scripts/*.js` harness needs one of: (a) convert to `import fs from "node:fs"` / `import path from "node:path"` syntax (recommended, and required anyway for `real_game_test.js`/`dlog_replay_test.js` per the "expanded headless replay/test harness" Active requirement — they need rewriting to `import` the real `js/engine.js` instead of `vm`-slicing `index.html`), or (b) rename the file to `.cjs` to opt back into CommonJS regardless of the package.json setting (viable escape hatch for `battle_sim.js`, which never touches `index.html` and has no reason to change). |
| Node's dynamic `import()` | Node.js all currently-supported versions (>=18) | Stable, not experimental — unlike `vm.SourceTextModule`. This is the mechanism for "import the engine module, but only after stubbing a couple of globals it still touches," since static `import` statements can't be preceded by other code in the same file. |
| GitHub Pages static hosting | `.js` served with a correct JavaScript `Content-Type` | GitHub Pages' CDN serves `.js` with a standard JS MIME type already (this is how every other ESM-on-GitHub-Pages project works); this is a non-issue for production. The only environment where MIME correctness needed verifying was the **local** dev server, which is why `python3 -m http.server`'s behavior was checked directly rather than assumed. |
