# RESEARCH-2 — Engineering quality audit of `4/`

**Audited:** `4/index.html` (175 KB) + `4/src/` (25 files, 18,174 lines JS) + `4/scripts/` (4 files)
**Baseline for comparison:** live `index.html` (112 KB) + `src/` (21 files, 11,132 lines) + `scripts/` (43 files)
**Method:** read the code; ran the root test suite; ran every script in `4/scripts/`; diffed the two trees. No repo files modified.
**Date:** 2026-08-18. Branch `main`, clean.

---

## The one-paragraph verdict

The owner's suspicion — *"there were all sorts of wrong ways this was coded"* — is **half right, and
wrong about which half.** The *code craft* in `4/` is better than the live game in several measurable
ways: the engine is determinism-clean (zero `Math.random`/`Date.now` anywhere in `4/src/engine/`) and
DOM-free; **every layering rule holds** and there are **no circular imports**; there is **not one
commented-out code block** in 18,000 lines; divergence from `src/` is **strictly one-way**, so no fix
is stranded and promotion needs a cutover rather than a merge; and `4/` actually **closes** real gaps
live still has, including a global unhandled-rejection handler and a genuine architectural
improvement (turn sequencing moved out of the orchestrator into the engine). The problems are not
sloppy lines. They are **scope, process, and unmeasured performance**: `4/` is a *solo, no-Firebase
prototype* that deliberately deleted multiplayer, has **zero automated test coverage**, hard-codes
assumptions about living in a subdirectory, ships two player-reachable dev flags, and — most
importantly — **spent the performance headroom that the v1.0 Safari storm fix bought**, without ever
being measured on Safari. Promotion is a real project, not a `git mv`.

**The three things that would bite hardest, in order:** (1) multiplayer does not exist in `4/` and
none of its network code has ever executed; (2) nothing tests `4/`, including the determinism
guarantee the whole multiplayer design rests on; (3) the storm is now ~5× the paint area with a
60 fps camera loop on top, on the exact code path that crashed Safari once already.

### One claim I checked and had to reject

A sub-audit reported the sharpest finding of the whole exercise: that the bot-initiated trade path bypasses `worthReAsking`, the anti-spam memory, so bots can re-hail a player who already refused. **On reading the code, this is not correct, and it is worth recording so nobody "fixes" it.**

- Human path: `4/src/ui/flow.js:1572` filters the holder list inline — `g.holdersOf(offer.want,p).filter(q=>g.worthReAsking(p,q,offer.want,offer))`.
- Bot path: `4/src/ui/flow.js:1975` iterates `g.holdersOf(offer.want,p)` **unfiltered** — which is what triggered the report. But the bot path applies the same memory *upstream*, at offer-composition time: `botOpenTradeLive` calls `g.botOpenOffer(p)` (`4/src/ui/flow.js:1967`) → `composeOffer` → `4/src/engine/index.js:1393` `const live=holders.filter(q=>this.worthReAsking(p,q,want,provisional)); if(!live.length)return null;`

So the memory is applied on both paths, at different points, **deliberately**: the bot filters on *whether to speak at all* (with a documented two-pass bid at `4/src/engine/index.js:1384-1392` explaining why the order matters), then addresses the whole table, per the v2 rule-4 design stated at `4/src/ui/flow.js:1956-1958`. The residual asymmetry is narrow and probably intended: a bot's table-wide announcement still reaches a captain who refused, provided at least one *other* holder is still worth asking. Not a defect — a design difference. **No action.**
