## mp-pause-clock-desync — pause/resume desynced the MP shot-clock between host and guest
- **Date:** 2026-07-26
- **Error patterns:** pause resume desync, shot clock, turn clock countdown, host vs guest mismatch, frozen remaining differs (host 13s guest 20s), guest races to 0 / "lose your turn" on resume, shotClockDeadline, shotClockPauseElapsed, clockState, broadcastClock, watchPause/watchClock, multiplayer Firebase sync, host authority, CLOCK-02
- **Root cause(s):** Missing host→guest propagation on the pause/resume path — an AND-gate of two conditions: (1) `watchPause()`'s host branch recomputed the deadline in `applyPauseState()` (pause stashes `shotClockPauseElapsed`; resume sets `shotClockDeadline = Date.now()+30000-shotClockPauseElapsed`) but NEVER called `broadcastClock()`, the sole writer of the synced deadline — so guests kept rendering the stale pre-pause deadline and raced to 0 on resume; (2) the guest paused-render derived its frozen number from `appState.shotClockPauseElapsed`, a value set only on the host — on a guest it defaults to 0, so guests froze at 20s while the host showed 13s. Fixing one alone leaves the other symptom.
- **Fix:** (a) `watchPause()` host branch calls `broadcastClock()` after `applyPauseState()` on BOTH pause and resume; (b) `broadcastClock()` payload carries `paused` (every write) + `pauseElapsed` (while paused only); (c) `setClockUI()` derives a `paused` render flag from the broadcast's own `paused` bit (host uses its live flag) so the frozen↔running flip and the deadline update atomically on guests (kills the resume flash-to-0 from a watchPause/watchClock ordering gap), and reads `state.pauseElapsed` for the frozen number; (d) UX: `.tappable` affordance on the your-own-turn frozen paused number (CLOCK-03). Host authority preserved (guests never mutate deadline/pauseElapsed); freezing still routes solely through `appState.shotClockPaused`; no watcher added/removed (inventory stays 19); `src/engine/` untouched.
- **Files changed:** index.html, src/orchestrator.js, src/ui/panel.js
- **Commit:** 8a8da0a
- **Why not caught:** No automated gate existed for this class. `npm test`'s 9 checks (determinism, engine/net/state/module/ui contracts, no-undef, 19-watcher inventory) verify module boundaries, determinism, and identifier resolution — none execute the 2-client Firebase render path or assert host↔guest clock-render parity. The project is deliberately zero-dependency with no DOM/multiplayer test harness, so cross-client render desync is only reachable by manual 2-window UAT — which is exactly what caught it (Phase 13 test 3).
- **Recurrence guard:** (1) This KB entry — a future Phase-0 recall on "pause/resume desync" / "host guest clock mismatch" surfaces the invariant. (2) Inline invariant comments committed at each fix site (`CLOCK-02 FIX` in `broadcastClock()`, `watchPause()`, and `setClockUI()`) recording the two design rules that prevent the class: **any host mutation of `shotClockDeadline`/`shotClockPauseElapsed` must be followed by `broadcastClock()`** (broadcastClock is the single synced-deadline writer), and **guest render must read broadcast `state.*` fields, never host-only `appState.*` timer locals**. (No automated regression test added: a faithful one needs a DOM/Firebase harness the project deliberately omits; the agent-authored logic repro that models the exact math is the demonstration artifact.)

## storm-push-not-rendered — per-square storm movement never appeared on the board
- **Date:** 2026-07-26
- **Error patterns:** boat teleports during storm, ship does not step square by square, per-square render does nothing, board a square behind the narration, "false dock held fast", movement only visible after the next event, liveRender has no effect, storm push invisible, renderLiveShips, windLeg/botWindLeg, STORM_STEP_MS/BOT_STORM_STEP_MS, D-09/D-22, STORM-01
- **Root cause(s):** **Wrong render source, not a missing render call.** `render()` (`src/ui/board.js`) draws every ship from `appState.game.events[appState.evIdx].state` — the position SNAPSHOT `Game.ev()` bakes into each event — never from the live player objects. An ordinary square of a storm push emits NO event (`windPush` just does `p.pos=nx` and falls through), so the per-square `liveRender()` added by plan 14-05 faithfully repainted an *unchanged* snapshot. The intermediate squares were unrenderable by construction; the boat only jumped when the leg's own outcome event finally landed. Affected the human path (`windLeg`) identically to the bot path (`botWindLeg`), and every browser identically — despite the original sighting being Safari, this was never a Safari or a timing bug. A second, masked defect surfaced only after the first was fixed: both storm-beat intervals (320ms human / 170ms bot) were SHORTER than the ships' 350ms CSS glide, so every square was cut off mid-animation and never landed.
- **Fix:** UI-tier only; `src/engine/index.js` untouched. (a) New `renderLiveShips()` paints ship transforms (plus any chat bubble and the active-turn ripple) from `appState.game.players`' live positions — positions only, since coins/crates/log/scrub/host-broadcast all legitimately belong to the event stream. (b) `windLeg` and `botWindLeg` call it on the ordinary per-square beat, and `botWindLeg` also calls it *before* an outcome narrates, so the "moved AND emitted" case (a rim square, where `tradewind()` flings the ship to the quadrant head) has the board correct before the line describing it plays. (c) `SHIP_GLIDE_MS` introduced and both beats raised above it (STORM_STEP_MS 320→420, BOT_STORM_STEP_MS 170→380) so the beat/glide coupling is explicit and cannot silently drift again. (d) Companion bug: `movedSinceTurnStart(e)` compares the `moored` event's own snapshot against the `turn` event that opened that seat's turn, so the "gust shoves you onto a dock" line renders only when the ship actually moved; an already-parked ship reuses the approved "still docked" line, introducing no unapproved copy. Derived from the event stream rather than UI scratch state deliberately — `describe()` also runs on remote guests and on reload-replay, where host-only bookkeeping would tell the wrong story. A storm's second gust is always PERPENDICULAR to its first (`PERP`), never a reversal, so a storm can never return a ship to its turn-start square — which makes "position then vs now" exact rather than approximate.
- **Files changed:** src/ui/board.js, src/ui/flow.js, src/ui/util.js, scripts/bot_storm_narration_test.js
- **Commit:** 14d8258
- **Why not caught:** `scripts/bot_storm_narration_test.js` (added by the very plan that introduced the bug) asserted that the right *events* were emitted and narrated — which was always true. Nothing asserted that the *board* reflected the ship's position, because the project has no DOM harness. The determinism corpus is likewise event-stream-only and stayed 31/31 green throughout, correctly: the engine was never wrong. This was a pure presentation defect, reachable only by a human watching a storm, and that is exactly what caught it (Phase 14 plan 14-06 playtest).
- **Recurrence guard:** (1) This KB entry. (2) A new assertion 5 in `bot_storm_narration_test.js` builds four scenarios from real engine event streams (shoved-onto-dock, parked-on-dock, intervening leg-end windmove, wrong-seat anchor) as the companion-bug regression guard — mutation-tested with 3 planted mutants, all 3 killed; one mutant survived the first draft and the intervening-windmove scenario was added specifically to kill it. (3) The `SHIP_GLIDE_MS` constant now names the coupling between the storm beat and the CSS glide it paces, so a future pacing change cannot re-create the cut-off-mid-glide defect silently. **Standing invariant recorded at the fix site: any UI that must show a position the event stream does not record has to paint from live state — `render()`'s snapshot source can only ever show positions that emitted an event.**
- **Known limitation (by design):** multiplayer GUESTS still do not see intermediate squares — a guest renders purely from the broadcast event feed, and showing them would mean adding to the event stream, which the determinism corpus forbids. Guests keep today's behaviour (boat lands on its final square). Host and solo play get the full animation.
