<objective>
Prove behaviourally what the rest of the phase built structurally.

ROADMAP criterion 3 is deliberately hard: it demands a reconnect-and-count check and rules out code review by name. Research then narrowed the target further. The obvious test — leave the room and rejoin — proves nothing, because `location.reload()` is the only leave path the app has and a reload zeroes the JS heap regardless of whether the registry works or is absent entirely. So this plan runs a same-tab, no-reload attach, detach and re-attach cycle against the registry's own bookkeeping, which is the listener ground truth once the registry is provably the only attach path.

Research also narrowed which leaks actually exist today, and they are not the ones the roadmap's framing implies. Three specific vectors get their own steps: a response listener abandoned when a room dies mid-decision, a double-invoked room join doubling every room listener, and — the one where the correct behaviour is survival rather than teardown — the connection and presence watchers, which must outlive a room leave.

Then criterion 4: a real two-tab game. The local identity trap is the whole difficulty. All tabs in one Chrome profile share local storage and the local id is read once at load, so without resetting it first the guest rejoins as the host and the test measures nothing while appearing to pass.

Purpose: satisfy NET-03 and ROADMAP criterion 4 with observed behaviour, not inference.
Output: two verbatim transcripts recorded in the SUMMARY, and a finding list if anything diverged.
</objective>

**Step 0 — rule out a load failure before measuring anything.** Confirm the module marker is true and the boot counter is exactly one. If the module never ran, every count below would be zero and the probe would pass while measuring nothing.

**Step 1 — session baseline at the home screen.** With Firebase initialised and no room open, record the session-scoped count, the room-scoped count, and the full registry listing verbatim. Expect two session-scoped entries — the connection and presence watchers, attached once per page life — and zero room-scoped.

**Step 2 — attach the full room scope.** Create a room and start the game so the game-start function runs its host branch. Record all three values again. Compare the room-scoped count against the host-side figure derived in 09-02 and recorded in its summary. A mismatch means either the derivation was wrong or a watcher is not attaching; investigate rather than adjusting the expectation.

**Step 3 — state the vacuity guard explicitly.** Write down, in the transcript, that step 2's room-scoped count was greater than zero and what it was. Steps 4 and 6 are meaningless without it: a teardown that brings an already-empty registry to zero passes trivially.

**Step 4 — tear the room down in the same page load.** Call the debug hook's room teardown directly. Do not reload. Assert three things: the room-scoped count is zero, the session-scoped count is still two, and the registry listing contains exactly the two session entries by label.

The session half is leak vector (c), and it is the one place where the correct behaviour is the opposite of the phase's headline. The connection and presence watchers track the browser's connection to Firebase itself, not any particular room. Tearing them down alongside room watchers would be a regression dressed as a fix, and a count-only check that celebrates reaching zero would score it as a success.

**Step 5 — prove the surviving listeners are live, not merely counted.** With the room scope down, interrupt the network connection and restore it, and confirm the sync notice responds. A registry entry that says "attached" while the underlying listener is dead is exactly the failure a count cannot see.

**Step 6 — re-attach in the same page load.** Re-run the classic watcher-attach path for the room scope. Assert the room-scoped count returns to precisely its step-2 value — not double, not one more. A doubled count here is the leak NET-03 exists to catch. Compare the listing's labels as a set against step 2's; they must match exactly.

**Step 7 — leak vector (b): the double-invoked room join.** Invoke the room-join path a second time in the same tab without leaving. Expect a named registry error in the console for each already-tracked entry, and the room-scoped count unchanged. Record the error text verbatim. Its absence is a failure, not a pass — the refusal is the mitigation, and a silent second attach is the bug.

**Step 8 — leak vector (a): the abandoned response listener.** Stage a pending remote decision so a response listener is attached and waiting, then tear the room down before any reply arrives. Assert the response listener is gone from the listing and the room-scoped count dropped by the expected amount. If staging a real pending prompt is impractical in the available flow, say so plainly and record that this vector rests on the unit-test case added in 09-03 rather than on a browser observation — do not describe an unstaged step as observed.

**Step 9 — the production leave path.** Finally, exercise the real leave function. It calls the room teardown before reloading, so the observable consequence is the same teardown already checked; what this step confirms is that the production path reaches it at all, rather than the teardown being reachable only from a debug hook. Confirm by instrumented observation or by the console error a second teardown would produce, and say which.

Record everything verbatim: every expression evaluated, every returned value, every console line. If any step diverges from its expectation, stop and report it as a finding. Do not edit the expectation to match what you saw.

Run a real two-tab multiplayer game and confirm the extraction did not break sync. This is ROADMAP criterion 4, and it is also the only check in the phase that can catch a relocated path typo — a wrong path fails silently, so no grep and no unit test will find it.

**Handle the identity trap first, or the test measures nothing.** All tabs in one Chrome profile share local storage, and the local id is read once from storage at load. Without intervention the second tab loads with the first tab's id and rejoins as the host. Before each tab loads, clear local storage and set a unique local id, then load the page — and do this **sequentially**, one tab fully set up before the next begins. Record the two ids used. If the guest tab shows the host's seat or the host's controls, stop: the reset did not take, and nothing observed after that point means anything.

**Then play a real game.** Host tab creates a room; guest tab joins with the code; host starts. Confirm each of these on the guest side, and record which watcher each one exercises:

- The board and captain rows appear, driven by the broadcast event feed.
- Events accumulate as the host plays, in order, with the log growing.
- Narration appears and updates.
- The flip animation fires in sync when the host flips.
- A battle scoreboard appears for a spectator and clears when the battle ends.
- The shot clock reflects the host's state, and toggling the turn timer from either tab is reflected in the other.
- A chat message sent from either tab appears in both.
- The recipe picks and the turn order both land.
- The seat list rendered in the lobby matched the actual joins.

That list is not decoration: it is the guest-side watcher inventory. Anything on it that does not fire names the exact watcher whose path or event string is wrong.

**Confirm host authority is unchanged.** Only the host should be writing game state; the guest should be render-only. Confirm the guest never advances the game itself and that a decision requested of the guest's seat is prompted through the host's flow, not taken locally.

**Check the console in both tabs.** No registry duplicate-attach error should appear during a normal create, join and start — its absence here is part of the pass criteria, which is the opposite of its role in Task 1 step 7, where its presence was required. No new reference errors, no new undefined-identifier errors, and no sync-failure banner.

**Record the room-scoped counts in both tabs mid-game** from the debug hook, and compare the guest's against the guest-side figure derived in 09-02. This ties criterion 4 back to NET-01's inventory.

**Report environment artifacts as artifacts.** Live auto-play is slow and occasionally flaky with several heavy tabs on one CPU. If a step is slow or stalls, say so and say what you did. Do not retry silently until green, and do not record a retried pass as a clean pass.

**If something is genuinely broken,** diagnose it, name the watcher or writer at fault, fix only that, and re-run the entire check chain plus the affected steps. Record the diagnosis and the fix. Do not work around a symptom.

Leave the server running when the session ends; stop it only when told to.
