<objective>
Close the last two watchers and move every remaining piece of Firebase transport out of `index.html`, so `src/net/` owns transport completely and `index.html` owns only orchestration and UI.

The two self-cancelling one-shots are the interesting half. D-02 is explicit that they are already correct in spirit — a one-shot response listener that stops listening the moment its matching reply lands — and that "fixing" them into the registry must not break that. Their real gap is narrower and easier to miss: if the room dies, or the target seat never answers, the listener is never removed at all. Routing their cancellation through the registry preserves the self-cancelling behaviour and adds room-death teardown, which is the actual leak.

The other half is bulk: roughly forty non-listener Firebase call sites, several of which sit inside functions that also make a UI call. Those get split — the write moves, the UI stays. The error-surfacing helper stays in `index.html` too, because it toggles a DOM element; every relocated write takes it as an argument exactly as it takes it today.

Purpose: complete SPLIT-04 and take the registry-mediated watcher count from sixteen to eighteen.
Output: `src/net/writers.js`, `src/net/readers.js`, the final two watcher wrappers, and an `index.html` with zero direct Firebase calls.
</objective>

Both accept a label from the caller, and the caller supplies the prompt's unique id as part of that label. That matters: the registry's duplicate-attach key includes the label, so two prompts issued sequentially against the same response path would otherwise look like a duplicate to the registry once the first has detached and a second attaches. **Rewrite the two call sites in `index.html`.** In each helper, the callback keeps its exact body with one substitution: where it currently calls the Firebase removal API directly, it calls the registry's detach with the id the wrapper returned. There is an ordering subtlety worth being deliberate about: the callback needs the id that `attach()` returns, but `attach()` needs the callback. Declare the callback first and let it read the id from an enclosing binding assigned by the attach call. That is exactly how the research pattern structures it, and it works because the callback cannot fire before the attach that installs it has returned.

Do not call the Firebase removal API from these callbacks. Going around the registry still detaches the underlying listener, so the game would keep working — but the registry's count would then overstate reality, and the registry's count is the entire basis for NET-03's ground-truth argument. A silently-wrong count is worse than a leak, because it reports success.

**Do not change the self-cancelling behaviour.** D-02 is explicit: these two are already correct on the normal path. A reply with a matching id must still stop the listener immediately. The only new behaviour is that a room teardown now also removes one that is still waiting.

**Confirm the room-death path actually reaches them.** With both registered at room scope, the room teardown loop must include a pending one-shot. **What stays behind, and why.** Three categories of code currently interleaved with these writes must not move:

- The error-surfacing helper. It toggles a visible sync notice, which is UI. It stays exactly where it is, and every relocated write receives it as an argument the same way it receives it today. The chat push is the one exception in the current code — it uses an inline console log rather than the shared helper. Preserve that difference rather than normalising it; normalising would add a visible banner to a failure that deliberately does not raise one.
- The guards. Host-authority checks and replay-flag checks sit ahead of most of these writes. They stay at the call site. The transport functions are unconditional. Moving a guard into `src/net/` would make the module read app state, and would move a host-authority decision out of the layer that owns it (D-08).
- The UI calls. Several of these functions make a UI call and then a write in the same body. Split them in place: the UI call stays on the line it is on, the write becomes a call into the writer module.

**The decision-log writer needs specific care.** D-09 makes its write ordering load-bearing for replay correctness. Its current shape increments a counter, pushes the plain value into the local log, and writes the encoded wrapper to Firebase at a specific index — issued before the resulting events are pushed to the broadcast feed, so the log can never lag the feed. Preserve all of that: one write per call, issued at the same point, in the same order, fire-and-forget. Do not batch, do not collect into an array and flush, do not add an await, do not switch to a multi-path update. Any of those changes the interleaving between the log and the event feed, which is exactly what replay depends on.

**The event-feed push loop needs the same care.** It pushes one event per iteration while advancing a counter. Move the push itself; leave the loop and the counter in `index.html`. Converting the loop into a single batched write would change the order guests observe events in.

Move them into a single writer that takes the database handle and the local id; keep the callback's structure and its silent failure handling identical, since a project whose rules predate the presence node will permission-deny these and the current code deliberately swallows that.

**Copy path expressions, never retype them.** A wrong path fails silently — the write lands somewhere no one reads, and guests simply never see the data. Nothing in this repo's test suite catches that. This is the single highest-risk mechanical error in the plan.
