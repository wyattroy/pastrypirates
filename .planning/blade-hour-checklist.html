Setup — about 10 minutes

1 · Prove a headless watch can pulse
In the repo folder (regular PowerShell):
claude -p "Run exactly this command and show its output: node scripts/wyclau/glass.mjs --note 'headless permission probe'"
Then confirm .planning\wyclau\HEARTBEAT has a fresh timestamp. This proves claude is on PATH and the permissions survived — both were proven in the first Razer hour, this re-checks them cheaply.
2 · The O2 test — can a Blade session publish the Glass?
Open an interactive claude in the repo and say: "Republish the Glass, and state plainly whether the Artifact tool exists in your tool list. Write the answer to the ledger verbatim, commit and push." Whatever the answer, it settles the one unexplained fault left in the system (three Blade sessions have reported no publish path; nobody knows if the tool was absent or refused).
3 · Register the Bell
ELEVATED PowerShell, with your real repo path:
schtasks /Create /TN "wyclau-bell" /SC MINUTE /MO 10 /TR "powershell -NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File C:\Users\wyatt\Projects\pastrypirates\scripts\wyclau\bell.ps1 -Repo C:\Users\wyatt\Projects\pastrypirates"
⚠ THEN VERIFY IT, ALWAYS — this step can fail SILENTLY. On 2026-09-01 the task was created in a fresh elevated window where $repo had never been set, so the path expanded to nothing: the task read -File \scripts\wyclau\bell.ps1 -Repo, reported Ready, and fired every 10 minutes into a missing file for an hour (Last Result -196608). A registration that looks fine and does nothing is the worst outcome here, so check it:
schtasks /Query /TN "wyclau-bell" /V /FO LIST | findstr /C:"Task To Run"
Both full paths must appear. Then force one run instead of waiting ten minutes — schtasks /Run /TN "wyclau-bell" — and confirm a ring: line lands in the log. Also, in Task Scheduler → Properties: General → “Run whether user is logged on or not” (ends Interactive only); Conditions → untick both power boxes, or the Bell stops the moment the charger comes out.
4 · Ring the first watch by hand
Run the Bell once yourself — any PowerShell window, no elevation needed, no variables (a fresh window forgets step 3’s $repo, which is what made the first version of this step error):
powershell -NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File C:\Users\wyatt\Projects\pastrypirates\scripts\wyclau\bell.ps1 -Repo C:\Users\wyatt\Projects\pastrypirates
It prints nothing itself — the watch launches HIDDEN. Confirm with Get-Content C:\Users\wyatt\Projects\pastrypirates\.planning\wyclau\restarts.log -Tail 3 (a line starting ring:) and the Get-CimInstance line from step 5 (one ProcessId). Expected: that watch takes the top queue item — starting the detached release trial on build .5 — then ENDS its turn. Ending is correct; it's the whole design.

The ring test — both directions, ~35 min of mostly waiting

5 · Direction 1: a killed watch gets relieved
While a watch is mid-work, kill it on purpose:
Get-CimInstance Win32_Process -Filter "Name='claude.exe'" | Where-Object {$_.CommandLine -like '*-p*/door*'} | Select ProcessId
Stop-Process -Id <that pid> -Force
Within ~15 min (one 10-min tick + the 5-min grace) the log gains a new ring: line and a fresh watch appears. The killed item stays claimed in the ledger — the next watch sees it there. That's the designed recovery, not a mess.
6 · Direction 2: a working watch never gets a double
While a watch is visibly alive, let two Bell ticks pass (20 min — good moment for coffee). Then rerun the Get-CimInstance line: the count of door-launched claude.exe must be exactly ONE, and the log must show no new rings. This is the direction the old watchdog failed four times in one day.
