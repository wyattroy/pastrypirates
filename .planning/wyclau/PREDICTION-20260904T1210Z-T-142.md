# Prediction — T-142, the still-open third bug (recipe-choice prompt over the captains bar)

**Written before measuring anything.**

**What I expect:** the recipe-CHOICE prompt (`recipeDraftNet()`, `src/orchestrator.js:939-957`,
rendered through `localAsk`/`panel()` in `src/ui/flow.js`) does **not** set `stage:true` on its
options (its `optsFor` only sets `cls:"recipeCard"`), so it never calls `enterCenterStage()`
(`src/ui/stage.js:2640`, gated on `ap.dataset.pp4Stage || ap.querySelector(".bko")`,
`stage.js:2867`) and therefore never gets the `.pp4Center` class's full-viewport dim backdrop
(`index.html:2261-2262`, `rgba(4,16,22,.6)` above `#pp4Cap`'s z-index:22). Instead it falls
through to the plain `.centered` class (`stage.js:3914`, `index.html:1836`) which only
repositions the card — no backdrop at all. So on tablet, where the card's own width crosses
`#pp4Cap`'s horizontal position, the captains bar should read straight through with **no** scrim,
exactly as `solo-tablet-002` showed pre-fix, and the shipped `.modalOverlay`-keyed fix
(`src/orchestrator.js:2564-2572`) should not touch it at all, because it only watches
`.modalOverlay` elements and this prompt is not one.

**What would prove me wrong:** a posed screenshot of the recipe-choice prompt on a tablet seat
(820×1180, the same seat `t142_captains_under_modal_check.mjs` uses) showing `exposedPx === 0` —
i.e. the captains bar is not visible/reads as fully covered where the card overlaps it — or the
card confirmed not to overlap the bar's rect at all on that viewport.
