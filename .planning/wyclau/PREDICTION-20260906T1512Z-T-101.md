## What I expect, and why

**The one-source answer is the same one T-100 (rules.html) already found and shipped**: a
generator (`scripts/lib/credits_page.mjs` → `scripts/build_credits_page.mjs`) reads the
`#creditsModal` block out of `index.html` at build time and writes `credits.html`. Nobody edits
`credits.html` by hand; a gate (`scripts/qa/credits_page_check.mjs`) re-runs the generator on every
`npm test` and fails on one byte of drift — same shape as `rules_page_check.mjs` §6.

**Simpler than rules.html in one real way**: the credits modal carries no `data-rule` spans (no
tuned numbers — it's a paragraph of prose, not game mechanics), so there is no `rulesFacts()`
dependency and no engine import. The generator is closer to a plain HTML extraction.

**One register question already answered by his own note, not left open**: the modal's text is
already his own plain first-person voice (it says "This game was made by...", not "Ye scurvy
dog..."), so no register conversion is needed — the extraction preserves it as-is, and the gate
should assert the page contains NO pirate-speak markers (a cheap regression check, since a future
editor could accidentally drop pirate flavor into this modal by copy-paste from elsewhere).

**Wiring, mirroring the rules-page precedent exactly**: the footer's `.footerCredits` button stays
a `<button>` that opens the modal in-game (nothing about the in-game experience should change —
he didn't ask for that). The crawlable link is a new `<p data-page-omit>` line inside the modal,
matching `.howShare` — "These credits live at credits.html" (in his own plain voice, not pirate
speak, since the whole modal is in that register). `data-page-omit` already exists as a mechanism
(built for T-100) and strips cleanly for a second consumer — no new stripping logic needed.

**Scope I will NOT add**: Google Analytics on credits.html. His ruling on `T-206`
("The public pages only — the game, About and Rules") named exactly three pages. Credits was not
one of them. Adding analytics here would be scope creep past an explicit, page-by-page ruling —
flagged as a question for him rather than assumed either way.

**Sitemap**: add `credits.html` to `sitemap.xml` (mirrors `T-098`'s coverage rule — every genuinely
public page belongs there), with a derived `<lastmod>`, never hand-typed.

**Gear**: I expect this to be COSMETIC-to-PLUMBING at most — a new static page plus a small,
crawlable link added to an existing modal. No game mechanics change. I will run `scripts/qa/gear.mjs`
after the edit and trust its verdict over my own guess.

  not force a sea trial verdict I have not actually run.
- If the credits modal's prose contains something I mis-extract (e.g. the Ko-Fi button inside the
  modal, which is UI chrome not credits text) and the generator naively includes it, the page would
  ship a broken "Buy me a cookie" button with no `mountKofi()` wiring behind it. I will explicitly
  exclude the Ko-Fi button div from the extraction (mark it `data-page-omit` too), and the gate
  should assert credits.html contains no `id="btnKofiCredits"` button.
- If `rules_page_check.mjs`'s canary pattern (checking `about.html` still shows "Credits") breaks
  because I touch `about.html`'s Credits card while doing this — I do NOT intend to touch
  `about.html` at all for this item, only `index.html` (the modal + omit line), a new
  `credits.html`, a new generator/gate pair, `sitemap.xml`, and `package.json`'s gate chain. If I
  find myself needing to touch `about.html`, that means my scope assumption was wrong and I should
  stop and re-check rather than pushing through.
