Your two computers

Everything you need to know, on one page. Written 6 September 2026, after a morning lost to this.

The Blade is home. The Mac is a visitor.

The Blade never moves and never sleeps, so it can hold things. The Mac goes in your bag. So the Mac should never be the only place something lives — it arrives, does its bit, and hands it back.

The Blade

Home

  • Runs the Watch, all day
  • Runs sea trials (85 minutes each)
  • Anything that must not be interrupted

The Mac

Visitor

  • Thinking, reviewing, talking to Claude
  • Small edits
  • Then push, and walk away

Don't start a sea trial on the Mac. It takes 85 minutes and you'll close the lid.

Three rules

1

Bookend every Mac session

Sit down: git pull --rebase  ·  Before you close the lid: git push

If either one complains, stop and paste it to Claude. This is now automatic — a hook pulls for you when you open a session, and warns you if the machine is holding anything when one ends. The rules are here anyway, because you should know what it's doing.

2

On the Mac, start Claude with /door

It syncs and runs the check that asks “can this machine actually publish?” — the one that would have caught September 3rd on day one instead of day three.

3

Never close the Mac when git is mid-something

If you see “continue”, “abort”, or “rebase in progress”, git is holding the door open, waiting for you. Closing the laptop there is what stranded your hand-drawn X for three days.

Two commands, when you're unsure of anything

node scripts/where_is_my_work.mjs     is my work on staging? is it live?
node scripts/wyclau/can_push.mjs      can this machine publish? yes/no + the fix

Between them they answer every question that went wrong on 6 September.

The other thing: two websites, two different actions

There is one repo you work in — pastrypirates, on both machines. There are two websites, and getting to each one is a different action.

StagingProduction
Addressstaging.playpastrypirates.complaypastrypirates.com
Who's thereyou, playing work-in-progressreal players
The actiona copy — you publisha merge — you release
The commandnpm run deploy:staginggit merge into main
Approvalnone needed, do it dailyalways yours, live instantly

You never “merge to staging.” Staging is an address, not a branch. That one wrong verb is what confused Claude for a whole morning.

There is a second repo on GitHub called pastrypirates-staging — but it is just a web host that happens to be a git repo, like an FTP folder. Nobody develops in it. Don't clone it. It exists only because GitHub Pages can serve one branch per repo at one address, so a second address needs a second repo.

Production being older than your branch is normal. It's deliberately unreleased. It is not a bug, and nobody should alarm you about it.

Earned the hard way on 6 September 2026: Claude read a git command that answers a question about production, concluded your merge had failed, and told you so twice. Three mechanisms now exist so that neither of us has to remember any of this — a command, and two hooks that fire at the moment of the mistake rather than sitting in a document.
