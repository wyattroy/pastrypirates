# Prediction — INBOX-20260904T004944Z (cdp.mjs has no timeout on any CDP call)

**Claim being tested:** `scripts/lib/cdp.mjs`'s `send()` (line 51) has no timeout — its promise
only resolves when Chrome's WebSocket answers. If Chrome never answers (a page-side promise that
never settles inside `Runtime.evaluate`, or a crashed tab), the call hangs forever and so does
anything awaiting it (`npm test`, a sea trial leg).

**What I expect, and why:** I expect this is real and unfixed. `grep -n "timeout" scripts/lib/cdp.mjs`
returns nothing, and `send`'s executor (`new Promise(res => { ...; pend.set(i, res); ws.send(...) })`)
has no `setTimeout`/`Promise.race` anywhere near it. `git log -- scripts/lib/cdp.mjs` shows no commit
mentioning timeout. So the gap he described is still open.

**The fix I'm about to make:** wrap the promise `send()` returns in a bounded timeout (default
120000ms, matching his "say, 2 minutes" suggestion, kept overridable per-call) that (a) rejects with
a named error instead of hanging, and (b) deletes the pending entry from `pend` so a very-late
response from Chrome after the timeout does not resolve a promise nobody is awaiting anymore (a
resolved-but-abandoned entry is a memory leak, not a correctness bug, but it's free to close while
I'm in the function).

**What would prove me wrong:**
- If `send()` already has a timeout somewhere I mis-read (e.g. inherited from `fetch` or the
  WebSocket library itself) — I'd expect to find it by reading the whole file again slowly, not by
  grep alone.
- If wrapping `send()` breaks a caller that depends on it never timing out on a legitimately slow
  call (e.g. a multi-second `Runtime.evaluate` awaiting a real in-page promise) — the default must be
  generous enough that no existing script trips it. I will check callers (`playtest.mjs` and anything
  else using `.ev(...)`/`.send(...)`) for any call likely to legitimately run past 2 minutes before
  shipping a fixed default.
- If my test of the timeout wrapper (a promise that never resolves, raced against a short timeout)
  itself hangs or times out unpredictably — that would mean my fix does not actually bound the wait,
  which is the exact defect it's supposed to remove.

**How I'll measure, not assume:** a new gate, `scripts/qa/cdp_timeout_check.mjs`, that (1) fails on
the current code (no timeout export/mechanism to find), (2) after the fix, proves a promise that
never resolves is rejected within a bounded, short window (not "eventually", a real wall-clock
measurement) rather than by reading the source and trusting a comment.
