# PREDICTION — `T-105`, Layers A and B: the Glass must not be able to lose his writing

*Written 2026-09-02 ~21:05Z (5:05 PM ET) BEFORE any measurement or edit, per the prediction rule.
The "was I right" half is appended at the bottom, before the close, and names where I was wrong
first.*

## What I am about to do

Build **Layer A** (never `force`; the platform's own refusal is the guard) and **Layer B** (the
harvest stamp records an artifact VERSION, not a clock) from
[`SPEC-GLASS-HARVEST-SAFETY.md`](../SPEC-GLASS-HARVEST-SAFETY.md). **Layers C and D are not in this
watch** and I will say so rather than let the summary round toward finished.

Why now, when two previous watches correctly skipped this row: the spec made a measurement the
precondition — does the Artifact tool actually refuse a publish built on a stale read? The
19:29Z watch handed that question to the Glass-update peer and the answer is on the record at
`INBOX.md:1302` — **it conflicts by default; `force: true` is the only path to an overwrite** —
answered from the tool's documented contract, NOT from a live experiment, and flagged as such by
the peer itself. **I am building on an inference, and that is stated everywhere it matters.**

## What I expect to find, before I look

1. **`FRESH_MIN = 30` in `.claude/hooks/glass-harvest-first.cjs:37` is the whole guard**, and it is
   a clock. I expect the hook to allow any Glass publish whose `LAST-HARVEST` file was touched in
   the last thirty minutes, without ever asking WHAT was read.
2. **Nothing anywhere forbids `force`.** I expect zero occurrences of a `force` token on any Glass
   publish path — which means the most dangerous flag in this system is currently unguarded rather
   than misused.
3. **`LAST-HARVEST` is a bare ISO timestamp** and no code reads its CONTENTS — only its mtime.
4. **The existing gate `scripts/qa/glass_harvest_hook_check.mjs` will go RED** when I rewrite its
   cases 2 and 3, because those two cases encode the clock: case 2 ages the file three hours and
   expects a deny, case 3 touches it and expects an allow. **A gate that asserts the old behaviour
   is the thing that has to fail first.**

## What would prove me WRONG — named before the result exists

- **If something already reads `LAST-HARVEST`'s contents**, Layer B is not a greenfield change and
  I would be about to break a reader I never looked for.
- **If the hook is not actually registered**, everything I harden is decorative and the honest
  report is "the guard has not been running", not "the guard is better".
- **If `force` already appears somewhere on a Glass path**, then Layer A is not preventive — it is
  a live defect, and it outranks everything else in this watch.
- **If the Glass-update session's tick cannot obtain a version id at its harvest read**, Layer B is
  unbuildable as specified and the honest answer is to say so, not to ship a stamp that records
  `"unknown"` and looks like a receipt.

## What this CANNOT do, stated now so it cannot be claimed later

**A hook is a shell process with no Artifact tool. It cannot fetch the live page, so it can never
answer "is the version I harvested still the version that is live?"** Anything I build here that
appears to answer that would be exactly the instrument failure this whole spec is about.

**Therefore the acceptance test in the spec's §2 — he writes seven seconds after a harvest, a
session republishes five minutes later, his words survive — is NOT passed by this watch.** Layer A
narrows it to "the platform refuses, if the inference holds"; Layer B makes the stamp capable of
expressing the question; **only the session's own re-read at step 7, and ultimately Layer D, close
it.** If the close of this item reads as though that test now passes, the close is wrong.

## THE RESULT — where I was WRONG first

**WRONG, AND IT IS THE BIGGEST THING IN THIS WATCH: I could not build the fix at all.**
Layers A and B both land in `.claude/hooks/glass-harvest-first.cjs`, and the edit came back
*"Claude requested permissions to edit … which is a sensitive file"* — the harness refusing to let
an unattended agent rewrite its own hook configuration. **I did not predict this and nothing in the
spec, the Chart row or two previous watches' notes mentions it.** The row's sizing line reads
*"Hooks, the Glass runbook and `glass.mjs`"*, and one of those three is unreachable from a Bell-
launched watch. I did not retry it and did not work around it — that permission wall is a good
rule, and one of the four watch-blocking walls now on the record beside `git mv` and
`deploy-staging.sh`.

**WRONG, 2 — my own force probe measured nothing, and it reported a guard that does not exist.**
The first run of the rewritten gate printed `force denied=true`, which would have meant the hook
already refused a forced publish. It does not. The aged-receipt case immediately before it leaves
the stamp three hours old, so the clock denied that publish for STALENESS and my probe read the
denial as being about `force`. **A probe that cannot reach its subject is not a measurement**
(rule 6), and this one was mine, in the same hour I was writing a gate about instruments that
cannot fail. Fixed by writing a fresh receipt before the probe; the comment at that line says so.

**WRONG, 3 — prediction 4 was half right.** I said the existing gate's cases 2 and 3 encode the
clock and would both go red. They did — but I also assumed I would keep them as assertions, and the
honest shape turned out to be a PENDING block that *fails the moment the hook is fixed*, because a
permanently red gate is one everybody learns to run past.

**RIGHT, and measured rather than assumed:**
1. `FRESH_MIN = 30` was the whole guard — `glass-harvest-first.cjs:37,57`, and the gate's live
   readout still says `bare-timestamp denied=false`.
2. **Zero instructions to force a Glass publish anywhere** — gate case 9, red-proofed on a
   synthetic line. Layer A is preventive, not a live defect. My named-wrong case did not fire.
3. `LAST-HARVEST` was a bare ISO timestamp and **nothing read its contents** — only
   `statSync().mtimeMs`. My named-wrong case did not fire, so Layer B breaks no reader.
4. The hook **is** registered (gate case 7, red-proofed by case 8). My named-wrong case did not fire.
