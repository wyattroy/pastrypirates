# Prediction — T-219 (sea trial resume cache keyed on a hand-typed stamp)

**Written before touching code.**

**What I expect:** `scripts/playtest_gate.mjs` keys its per-leg resume cache (`legFile()` /
`readDone()`) on `STAMP` alone, read from `PP4_STAMP` in `src/ui/stage.js:43` — a string a human
bumps by hand (`scripts/bump-build.mjs`). If I edit any other game file (e.g. `src/ui/util.js`)
without bumping that string, and a leg result file already exists for the current `STAMP`,
`readDone()` will return the STALE result and the leg will be reported `RESUMED` rather than
re-sailed — even though the code under test changed. I expect I can demonstrate this directly by
computing the resume key twice (before and after touching an unrelated source file) and observing
it is identical, without spinning up a browser or running a leg.

**Why it might be wrong:** something else downstream (e.g. `sea_trial.mjs`'s `sailedHere()`,
which matches on `__runId`, not `__stamp`) might already fully neutralize the staleness — i.e. a
resumed leg might get correctly excluded from "sailed" credit anyway, making this a non-bug in
practice. I read `sailedHere()` already (`scripts/sea_trial.mjs:344`) and it compares
`leg.__runId === thisRunId`; a RESUMED leg keeps the OLD run's `__runId`, so it should already be
excluded from THIS run's "sailed" count. **If that is fully true, the actual player-visible harm
is not "an untested change gets reported as passing" — it's "the trial reports fewer sailed legs
than it actually needs to, forcing a slower full re-sail every time,"** which is a smaller bug
than the Chart row implies. I will check this by re-reading both functions side by side before
concluding which failure mode is real.

**What would prove me wrong:** if `sailedHere()` credits a resumed (stale) leg as sailed in THIS
run despite code changing — I'd need to trace whether `RUN_ID` (which embeds `Date.now()`) ever
collides with an old resumed leg's `__runId`. It cannot, by construction (different `Date.now()`
per process). So my prediction is: **the resume cache does NOT cause false PASS claims** (that
specific danger is closed by the runId check), but it DOES cause **false "0 sailed, all NOT RUN"
reports** when a whole build's cache is stale-but-samestamp, which is exactly what the Chart row's
own evidence shows (`SEA-TRIAL-2026-09-03T1630Z-Wy-Blade.md`: "0 of 10 sailed, 10 NOT RUN" after a
1-minute run). That's a real defect (a trial that silently does nothing while looking like it
ran), just a different shape of harm than "ships an untested build as tested."

**The fix, if confirmed:** derive the resume key from a content hash of the actual game tree
(`index.html` + `src/**`) combined with `STAMP`, not `STAMP` alone — so any code change
invalidates old leg caches regardless of whether a human remembered to bump the display stamp.
Keep `STAMP` itself unchanged for human-readable reporting (it's read by `ceo_brief.mjs`,
`chartkeeper.mjs`, `sea_trial.mjs`, and the deploy stamp check — none of those should change).

**If wrong:** report exactly what I found instead of forcing the fix into the shape the Chart
row assumed.

## RESULT — measured 2026-09-04T03:5xZ

**Confirmed the main prediction.** Read `sea_trial.mjs:344`'s `sailedHere()` side by side with
`playtest_gate.mjs`'s resume path: `RUN_ID = ${STAMP}-${Date.now().toString(36)}` is generated
fresh every process start, and a resumed leg keeps the OLD run's `__runId` unchanged (`results[i]
= already` at line 617, no re-stamp). So a resumed-but-stale leg can never match `thisRunId` in a
LATER run — `sailedHere()` correctly returns false and the report correctly says NOT RUN. **No
false-pass path exists.** The real cost is a trial that spins uselessly (every leg RESUMED, report
says FAILED, nothing was actually re-driven) until a human notices and bumps `PP4_STAMP` by hand —
annoying and wasteful, but fail-safe, not fail-silent.

**Did NOT confirm or rule out the secondary question** (whether cross-process-restart resiliency —
the actual reason this cache exists, per the comment at `playtest_gate.mjs:526-538` about container
recycling) is ALSO broken by the same fresh-`RUN_ID`-per-process mechanism. That would need reading
`start_trial_detached.mjs`'s restart logic, which I did not do — ran out of budget for this watch
and did not want to guess at something this subtle in a subsystem with this much history of subtle
breakage (CEO 64, 74, 169's own findings all lived exactly here).

**Decision: did not attempt a code fix this watch.** The Chart row's proposed fix (hash the game
tree into the cache key) addresses the STAMP-not-bumped problem, which is real but smaller than
described. It does NOT address the RUN_ID-per-restart question, which might need a different fix
entirely (e.g. threading a stable run id down from the outer supervisor across restarts). Shipping
a fix for the wrong half of the problem, in a subsystem this fragile, seemed worse than leaving it
open with an accurate note. Redirected this watch's effort to a smaller, fully-verified, correctly
red-proofed item instead (T-246, `scripts/wyclau/assign_handles.mjs`).
