  <what-built>
    `index.html` gained exactly one line: an attributed module script tag loading `src/main.js`, placed after the existing inline classic script closes. `src/main.js` imports `src/module-contract.js`, sets `window.__pp_module_ok` to `true` behind a `typeof window` guard, and logs an explicit error if the `firebase` global is missing when running in a browser.

    Everything automatable has already run and is green: the Node import proof exits 0 with empty stderr, the attribute-less script tag count in `index.html` is still exactly 1, the engine source region hash matches the Wave 1 manifest byte for byte, the 30-seed corpus verifies green without re-capture, and both existing harnesses pass. `src/main.js` returns HTTP 200 with a valid JavaScript content type from the local server.

    What none of that can tell us: whether the page actually loads and plays in a real browser. The corpus runs headless in Node against an engine that has not moved, so it would pass even if this edit broke page load entirely. That gap is what this checkpoint closes.
  </what-built>
  <how-to-verify>
    **Chrome**

    1. From the repo root, start the canonical dev server: `python3 -m http.server 8000` (or `npm start`, which is an alias for the same command).
    2. Open `http://localhost:8000` in Chrome and open DevTools before the page finishes loading.
    3. In the Console tab, confirm there are **no errors**. Specifically confirm none of these appear: `firebase is not defined`; any message beginning `[main.js]`; any failure to load `src/main.js` or `src/module-contract.js`; any MIME-type refusal mentioning a module script.
    4. In the Console, evaluate `window.__pp_module_ok`. It must return exactly `true`. If it returns `undefined`, the module entry did not execute — that is a failure even if the game otherwise appears to work, because Phases 8 through 11 depend on this marker as a tripwire.
    5. Evaluate `typeof firebase`. It must return `"object"`, confirming the compat SDK loaded before the module entry.
    6. Play one solo game start to finish. Exercise sailing, docking, at least one trade, at least one battle, fishing, and reaching the end-of-voyage screen. Watch the console throughout — it must stay clean for the whole game, not just at load.
    7. Confirm gameplay feels identical to before this phase. No code has moved yet, so any behavioral difference at all is a real finding.

    **Safari** — this step is Wyatt's and cannot be delegated; no automation can drive Safari.

    8. Open `http://localhost:8000` in Safari. Enable the Develop menu if it is not already on (Settings, Advanced, "Show features for web developers"), then open the Web Inspector Console.
    9. Repeat steps 3 through 6 in Safari. Safari enforces module MIME types more strictly than Chromium and can skip a module silently, so step 4 matters more here than anywhere else — a silently skipped module shows no error at all, and `window.__pp_module_ok` returning `undefined` is the only signal.
    10. Pay particular attention to storm rendering during the solo game. Safari has a prior storm-crash precedent in this project, recorded in STATE.md, and this is the first phase boundary where the page structure changed.

    **When done**, stop the server.

    Report back: the value `window.__pp_module_ok` returned in each browser, whether each console stayed clean, and whether each solo game completed.
  </how-to-verify>
