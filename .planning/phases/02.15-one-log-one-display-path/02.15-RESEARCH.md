## Summary

The "one current prompt" Wyatt asked for does not exist as a concept anywhere in the code today —
`appState` has no `currentPrompt` field, and there is no dispatcher. What exists instead is **five
separate call sites**, all sharing one fork shape (`decisionIsLocal(seat) ? <local path> : <remote
path>`), writing to **two different Firebase nodes** through **three different remote-publish
functions**. The rendering these fork to is already unified (three of five reach it through
`optionButtonsHTML`/`sailPanelHTML`); the orchestration — who decides local vs. remote, and what the
host's own screen draws from — is not.

**The five fork sites**, all confirmed by direct reading:

| # | Function | File:line (fork) | Firebase node | Remote publisher | Rendering already shared? |
|---|---|---|---|---|---|
| 1 | `ask()` | `4/src/ui/util.js:1577` | `rooms/{room}/prompt` (`kind:"ask"`) | `orchestrator.remotePrompt` (`:1195`) | Yes — `optionButtonsHTML` |
| 2 | `pickCell()` | `4/src/ui/flow.js:569` | `rooms/{room}/prompt` (`kind:"pick"`) | same `onRemotePrompt` → `remotePrompt` | Yes — `sailPanelHTML` (closed by the "narrow half," evening of 2026-08-20) |

**This is bigger than the 02.15-01 plan's framing of "one line" (`ask()`'s fork).** That framing was
written before the evening's narrow-half work exposed that `pickCell()` carries an identical,
independent fork, and this research additionally found `battleAsk()` bypasses `ask()` entirely with
its own inline `remotePrompt()` call, and the recipe-draft ceremony (`recipeDraftNet`/
`netIntroBarrier`) forks through a **third** transport (`draftPrompt`, not `prompt`) with the same
shape again. **A plan that converges only `ask()`'s fork leaves four siblings unconverted and the
gate would have to be scoped explicitly to avoid implying more was fixed than was.**

**Primary recommendation:** Do not attempt all five in one plan. Pick **one** tracer that (a) closes
Wyatt's one remaining named divergence (20 — the host's missing sail squares) and (b) has the
smallest blast radius. That is **`pickCell()`** (#2), not `ask()` (#1), for reasons in "Don't
Hand-Roll" and "Architecture Patterns" below — its rendering is already fully converged and
red-proofed (`prompt_field_parity_check.js` assertion 2), it carries exactly one Firebase node
(`prompt`, same as `ask()`), and it is the highest-value single fix left. Converging `ask()`,
`battleAsk()`, and the draft-prompt pair are separate, later tracers — name them as explicitly
left, the same way Stage 4 itself was named left in `02.15-01-SUMMARY.md`.

## Architecture Patterns

### The fork, in the two functions that matter most (measured)

**`ask()`** — `4/src/ui/util.js:1519-1626`. The fork itself, `:1577`:
```js
const base=decisionIsLocal(seat)?netHandlers().onLocalAsk(msg,opts,colors,sub,extra)
  :netHandlers().onRemotePrompt(seat,{kind:"ask",msg,labels:opts.map(o=>o.label), /* ...7 fields... */});
```
`netHandlers().onLocalAsk` is wired in `4/src/main.js:93` directly to `ui.localAsk` (no wrapper).
`netHandlers().onRemotePrompt` is wired at `4/src/main.js:78` to `orchestrator.remotePrompt`.

**`pickCell()`** — `4/src/ui/flow.js:516-572`. The fork, `:569`:
```js
const bug=sailSelfCheck(p,cells);   // hoisted ahead of the fork — runs for EVERY captain (narrow half, evening 2026-08-20)
const base=decisionIsLocal(p.idx)?localPickCell(p,cells,bug)
  :netHandlers().onRemotePrompt(p.idx,{kind:"pick",cells,msg:sailPickMsg(p.idx),hint:bug||null});
```
Note: `pickCell()` calls `localPickCell` **directly** (not through a `netHandlers()` indirection the
way `ask()` calls `onLocalAsk`) — one asymmetry to be aware of when writing the dispatch; `ask()`'s
seam has one more layer of indirection than `pickCell()`'s does today.

**`remotePrompt()`** — `4/src/orchestrator.js:1195-1202`. Publishes to `rooms/{room}/prompt` via
`netSetPrompt`, then returns a Promise that resolves when a `response:{id}` node appears (written by
`sendResponse`, `:1207`, called from the guest's `watchPrompt` click handlers or `expireShotClock`'s
flip-forfeit path).

**`netSetPrompt`** — `4/src/net/writers.js:71` — `db.ref("rooms/"+room+"/prompt").set(payload)`.
**No null guard on `db`.** If `db` is null (solo, pass-and-play), this throws immediately on the
`.ref` call. This is the load-bearing fact behind Pitfall 1.

### The worked model already shipped: `applyActiveSeat` (Stage 2, `01d03ef`/`a69ca77`)

`4/src/ui/util.js:1781-1786`:
```js
export function applyActiveSeat(seat){
  if(seat==null)return;
  const ps=appState.game&&appState.game.players;
  if(!ps||!(seat>=0&&seat<ps.length))return;
  setActor(seat);
  if(window.__pp4)window.__pp4.actor(seat);
}
```
Called from **both** the host's own turn functions (`humanTurn`/`botTurn`, display-only side) and
from `watchEvents()` (`4/src/orchestrator.js:1330`, guest side) reading `e.p` off the event stream.
**This is the shape to copy for the prompt channel — with one addition the active-seat case did not
need: a prompt also has to carry an ANSWER back, and `applyActiveSeat` never resolves anything.**

### What a "current prompt" dispatch would need to carry

Reasoned from the union of what `ask()`'s remote payload and `pickCell()`'s remote payload already
send (both confirmed at the cited lines above):

| Field | Present today (ask) | Present today (pick) | Notes |
|---|---|---|---|
| `kind` | yes (`"ask"`) | yes (`"pick"`) | discriminant |
| `msg` | yes | yes | |
| `id` | stamped by `remotePrompt`, not by the caller | same | needed only for the round-trip; a host-local answer needs no `id` at all today (it resolves a Promise directly) |
| `seat` | stamped by `remotePrompt` | same | whose decision this is |
| options/cells | `labels`,`colors`,`classes`,`disabled`,`why`,`shorts`,`seats`,`flipIdx`,`back` | `cells`,`hint` | already channel-specific; a unified dispatch does not need to force these into one shape, only to route through one function |
| `battle` | conditionally, from `battleAsk`'s inline call | n/a | confirms `battleAsk` is a THIRD writer to the same node with its own extra field |

**The existing `prompt` node schema is already close to what a "current prompt" needs to BE for the
`ask`/`pick` pair** (it is literally what gets published). What is missing is not the wire shape —
it is a **local-side equivalent**: today the host's own seat never touches this shape at all, it
calls `localAsk`/`localPickCell` with plain positional arguments. Converging means the host
constructs the SAME payload shape for its own seat, hands it to one dispatcher, and the dispatcher
decides render-only (local) vs. publish-and-await (remote) — mirroring `db && room` exactly the way
`flash()` already does for narration (`4/src/orchestrator.js:308-311`).

### Recommended shape (reasoned, not yet built — this is what the plan should evaluate)

```
function decidePrompt(seat, spec){          // spec = {kind, msg, ...channel-specific fields}
  if(db && room) netSetPrompt(db, room, spec-with-id-and-seat);   // mirror, remote clients only
  if(decisionIsLocal(seat)) return localRender(spec);              // resolves a Promise directly, no wire round trip
  return awaitRemoteResponse(spec.id);                             // same promise remotePrompt() already returns
}
```
This is deliberately close to what exists, not a rewrite — `remotePrompt` already does the "publish
+ await response" half correctly for a genuinely remote seat. The new work is making the HOST'S OWN
seat go through an equivalent construction instead of `localAsk`/`localPickCell` being called as
disconnected functions from the game loop, so that (a) both tiers can point at "the same dispatch"
in the sense PAR-14 requires, and (b) a future third client type (spectator, replay) has one seam to
hook rather than two.

### Anti-Patterns to Avoid

- **Do not route the host's own prompt through Firebase.** `netSetPrompt` has no `db` guard
  (Pitfall 1) — a literal loopback breaks solo instantly. `flash()` and `applyActiveSeat` already
  establish the pattern (`isHost && db && room` mirror, direct local call always): copy it, don't
  reinvent it.
- **Do not converge `ask()` and `pickCell()` into ONE function.** Their remote payloads are
  shaped too differently (7 fields vs. 3) and forcing a shared schema is exactly the kind of
  "synchroniser" `02.2-PARALLEL-PATHS-AUDIT.md` §5 warns against — "the pattern in all six: the fix
  is a deletion, not a synchroniser." Converge the ORCHESTRATION (who decides, when it clears), not
  the wire schema.
- **Do not widen `ORCHESTRATION_DECL`'s `localAsk` entry to `shared:true` unless the host's own
  ask actually reaches a shared code path.** `scripts/host_guest_parity_check.js:438` currently
  declares it a gap on purpose (`"the host draws its own prompt from the game loop. Closes at Stage
  4, which is abandonable under D-04."`). If this plan converges `pickCell()` instead of `ask()`,
  the declaration needs a NEW entry for the pick channel's orchestration state, not a change to the
  `localAsk` row — see "Common Pitfalls" #5.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| "Both tiers draw from one place" for a fire-and-forget signal | A new pub/sub mechanism | `flash()`'s existing shape (`isHost&&db&&room` mirror, direct local call) — already the model for narration and active seat | Two working examples exist in this exact codebase; a third mechanism for the same problem is the disease this whole phase exists to cure |
| Field parity between two prompt renderers | Manual review | `4/scripts/prompt_field_parity_check.js` — extend it, don't duplicate it. Assertion 1 covers `kind:"ask"`, assertion 2 covers `kind:"pick"` (added in `b76983d`, red-proofed with 11 drills) | Already gated, already red-proofed, already the exact right shape for this class of bug |
| Orchestration parity (who calls a renderer) | A new checker | `scripts/host_guest_parity_check.js` assertion 6, `ORCHESTRATION_DECL` (`:423`) — add a row, don't write a parallel mechanism | This is literally what assertion 6 was built for in 02.15-01, and its `--drill` harness already proves it can fail |
| Shot-clock force-resolve for a prompt that never comes back | A new timeout mechanism per channel | `withShotClock()` (`4/src/ui/util.js:1949`) — already races any Promise, local or remote, and is channel-agnostic | It already handles both `ask()`'s and `pickCell()`'s promises identically; a converged dispatch must keep returning something `withShotClock` can wrap the same way |

**Key insight:** every mechanism this stage needs (mirror-when-remote, race-with-timeout,
field-parity gate, orchestration gate) already exists in this codebase for a sibling channel. The
work is applying the SAME four mechanisms to the prompt channel, not inventing a fifth.

## Common Pitfalls

### Pitfall 1: The host-loopback trap (CRITICAL — this is what makes Stage 4 different from Stages 1-3)

**What goes wrong:** `runLiveNet()` drives solo and pass-and-play, not only a networked host — the
fork at `4/src/orchestrator.js:1839` is `if(appState.isHost)`, and `isHost` is true in solo (there is
no room, `appState.db` is null). `netSetPrompt` (`4/src/net/writers.js:71`) dereferences `db` with
**no null guard** — confirmed by reading the function body, it is a bare `db.ref(...)`.

**Why it happens:** it is tempting to make the host "just call the same publish function it would
call for a remote seat" for symmetry. For narration and active seat that is safe because those
paths were built with an explicit `db && room` guard from the start (`flash`'s mirror,
`applyActiveSeat`'s pure computation). A prompt dispatch built by analogy without that same guard
would crash on the very first prompt of a solo game.

**How to avoid:** the local branch of the dispatch must NEVER touch `netSetPrompt`/`remotePrompt`.
Firebase publish happens only under `db && room`, exactly as `flash()` already does it
(`4/src/orchestrator.js:311`, `if(appState.isHost&&appState.db&&appState.room)`).

**Warning signs:** any code path where the host's own seat's prompt construction shares a call to
`netSetPrompt`/`remotePrompt` unconditionally. **A two-tab test cannot catch this — it always has a
room.** A full solo game must be played before believing any part of this stage, exactly as
`02.15-01-PLAN.md` required for Stages 1 and 2 and `02.15-01-SUMMARY.md` confirms was actually done
(20-33 events, zero errors, `a-solo-plays.png`).

### Pitfall 2: Pass-and-play is not "my seat" — `decisionIsLocal`, not `seatLocal`

**What goes wrong:** `seatLocal(s)` (`4/src/ui/util.js:1788`) is `s===appState.mySeat` — true only
for the browser's own seat. `decisionIsLocal(s)` (`:1804`) is
`(passAndPlay && game.players[s].strategy==="human") || seatLocal(s)` — true for ANY human seat when
the table is sharing one device. `ask()` and `pickCell()` both already use `decisionIsLocal`
correctly. **But `recipeDraftNet`/`netIntroBarrier` use `seatLocal` directly** (confirmed at
`4/src/ui/flow.js:2264`, `4/src/orchestrator.js:~856`), and reason about "is this MY seat", which
happens to work there only because `netIntroBarrier` has its OWN separate `appState.passAndPlay`
branch a few lines above (`4/src/ui/flow.js:2249-2261`) that intercepts pass-and-play before the
fork is reached. **A converged dispatch built for `ask()`/`pickCell()` and later extended
carelessly to the draft-prompt pair would break the device gate**, since those two functions do not
share the same pre-fork pass-and-play interception.

**How to avoid:** if this plan's scope stays to `pickCell()` (recommended) or `ask()`, this pitfall
does not fire — both already use `decisionIsLocal`. Record it in the plan as a landmine for
whichever future session converges the draft-prompt pair.

### Pitfall 3: Two independent teardown paths, matched only by convention

**What goes wrong:** a local answer clears state through `localAsk`'s `done()` closure
(`4/src/ui/flow.js:216`: `delete $("actionPanel").dataset.pp4Stage; panel("")`) or
`localPickCell`'s equivalent `done()`. A remote answer clears state through `sendResponse`
(`4/src/orchestrator.js:1207-1217`, same two lines, commented explicitly as "Mirror localAsk's
done()"). **These are two hand-written copies of the same four lines, not one function.** They agree
today because someone wrote a comment reminding the next editor to keep them in sync — the exact
"discipline, not structure" pattern `02.2-PARALLEL-PATHS-AUDIT.md` names as the root cause of every
other drift in this codebase.

**How to avoid:** if the dispatch converges the ANSWER side as well as the ASK side, this is the
natural place to collapse both teardown copies into one function the dispatch calls regardless of
which branch resolved. If the plan scopes narrowly to only the asking side, name this teardown
duplication explicitly as left, so a future editor changing one does not assume the other updates
itself.

### Pitfall 4: The shot clock's force-resolve must keep racing whatever the dispatch returns

**What goes wrong:** `withShotClock(seat, base, defaultVal)` (`4/src/ui/util.js:1949`) only fires
when `appState.isHost && seat===appState.shotClockSeat` — it wraps `base` (the promise `ask()` or
`pickCell()` already built) in a race against `appState.shotClockForce`, which `expireShotClock`
calls at 30s. **This is channel-agnostic today because it only cares that `base` is A promise, not
which function produced it.** A converged dispatch must still hand `withShotClock` something it can
race the same way — if the new dispatch's local branch resolves through a different mechanism (e.g.
an event emitter instead of a returned Promise), `withShotClock` breaks silently: the clock would
still visually count down but nothing would force-resolve when it hits zero.

**Also note:** `expireShotClock` (`4/src/orchestrator.js:244-283`) has its own `seatLocal` check at
the tail (`if(!seatLocal(p.idx)&&appState.db&&appState.room)netRemovePrompt(...)`) — a remote
timeout clears the Firebase `prompt` node, a local timeout does not (because nothing was ever
published for a local seat today). **If the dispatch starts publishing a mirror copy for the host's
own prompt too (as Pitfall 1's fix implies it might, under `db&&room`), this cleanup line needs the
same `db&&room`-not-`seatLocal` treatment**, or a networked host's own expired prompt would leave a
stale `prompt` node other clients could misread.

**How to avoid:** keep `base` a Promise (or whatever shape `withShotClock` already races) in every
branch of the new dispatch, and re-derive `expireShotClock`'s cleanup condition from `db&&room`
rather than `seatLocal` if a mirror-publish is added for the host's own seat.

### Pitfall 5: The gate can go green by declaration-widening instead of by the fault closing

**What goes wrong:** `ORCHESTRATION_DECL` (`scripts/host_guest_parity_check.js:423-439`) is a hand-
maintained list. `02.15-01-SUMMARY.md`'s own Deviation #2 already shows a case where the plan's
predicted mechanism was wrong and the real fix was found elsewhere (`turnOrder` vs.
`seatOrderFrom`'s fallback) — the gate would not have caught that mismatch on its own; only a human
verifying the RIGHT thing moved caught it. Task 2 of `02.15-01-PLAN.md` names this exact risk
explicitly: *"Do not 'fix' this by widening the declaration... that would turn the gate back into
the reassuring kind."*

**How to avoid:** whichever fork this plan converges (`pickCell` recommended), add a NEW row to
`ORCHESTRATION_DECL` for it (not just flip `localAsk`'s existing row to `true` unless `ask()` itself
is what's being converged), and require the drill harness to prove a synthetic regression on that
NEW row is caught, the same way `--drill` already proves the existing four rows can fail
(`scripts/host_guest_parity_check.js:816-849`).

## Open Questions

1. **Does a guest's reload mid-prompt recover cleanly today, independent of this plan's changes?**
   - What we know: `watchPrompt`/`watchDraftPrompt` attach as Firebase `value` listeners
     (`netWatchPrompt`, `4/src/net/watchers.js:114`), which fire immediately with the current node
     value on attach — this is standard Firebase RTDB `value` semantics, not specific code in this
     repo, so it was not independently re-verified against Firebase's actual behaviour in this
     session.
   - What's unclear: whether `watchEvents`/`watchRecoveryState` reconstruct enough of `appState.game`
     on a fresh guest page-load (as opposed to a reconnect within the same page life) for the
     re-delivered prompt to render sensibly against it. `ROADMAP.md`'s wave-order note for 02.1
     flags this exact gap as unresolved: "a guest who reloads mid-voyage today rebuilds nothing
     locally until the next broadcast event arrives."
   - Recommendation: treat this as PRE-EXISTING risk, not new risk this plan creates. Verify with a
     live two-tab session (kill/reload the guest mid-prompt) as part of Task 7-equivalent
     verification, but do not block the plan on fixing it unless it demonstrably regresses.

2. **Is `battleAsk()` in scope for "the prompt channel" as Wyatt named it, or is it a fourth
   channel entirely?**
   - What we know: it shares the `prompt` Firebase node and the `kind:"ask"` discriminant with
     `ask()`, but is a structurally separate function with its own fork, called only from
     `asyncBattle`.
   - What's unclear: whether Wyatt's "the prompt channel" (singular, from the handoff) means
     literally `ask()`, or means "every place a captain is asked something and the host's loop
     waits." The five-fork enumeration in this document treats it as the latter, since `battleAsk`
     shares every structural property `ask()` has (blocks the host loop, forks on
     `decisionIsLocal`, publishes to `prompt`).
   - Recommendation: the plan should state explicitly which of the five it converges and name the
     rest as left, rather than let the phrase "the prompt channel" default to meaning only whichever
     one function got picked.

3. **What should `PAR-16`'s display-rules document actually contain, given nothing exists yet?**
   - What we know: `ROADMAP.md`'s Phase 02.15 section says it should be "written as each piece
     converted... what the log entry is, what gets drawn, and how long it stays," and that it should
     become "the thing Phases 4 and 5 conform to."
   - What's unclear: whether it should be one file covering all channels (narration, active seat,
     captains order, prompt) or grown incrementally per-channel across multiple phases (since
     Phase 02.15 itself is landing in two sessions/plans).
   - Recommendation: start it now, in this plan, with the two entries 02.15-01 already made TRUE
     (narration, active seat) plus whatever this plan converges — do not wait for every channel to
     be done before the first version exists, matching Wyatt's own "write it down as you convert"
     instruction rather than "write it down at the end."
