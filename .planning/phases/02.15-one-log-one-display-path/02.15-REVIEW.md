### WR-01: Task 3's required standing static "solo guard" assertion was never built, and the SUMMARY never says so

**File:** `scripts/host_guest_parity_check.js`, `4/scripts/prompt_field_parity_check.js` (absent from both)
**Issue:** `02.15-02-PLAN.md`'s Task 3 action item 8 requires: *"Add the standing solo guard as
assertion 3 of the existing gate... Assertion 3 declares the functions that make up the local
render-and-resolve path and asserts, comment-stripped, that none of them references any Firebase
prompt writer or publisher... Red-proof it with a drill that plants one such call and watches it
fail."* Task 3's own `<done>` block repeats it as a completion criterion: *"assertion 3 stands as
the standing static solo guard."* I grepped both parity scripts for any reference to
`netSetPrompt`/`netRemovePrompt`/`netSetResponse`/`remotePrompt` inside a check on
`renderPickPrompt`/`localPickCell` — there is none. The only place this exact check exists is as a
one-off `node -e` script embedded in the PLAN's own `<verify>` block, which ran once during Task 3's
execution and was never persisted into a committed, drillable gate. `02.15-02-SUMMARY.md` never
mentions "assertion 3," "solo guard," or this gap anywhere — it is not listed as parked, not named
as a deviation, and not flagged as left undone; the summary's "THE GATE'S READINGS, QUOTED" section
only discusses the two count-based re-anchors.
**Concrete failure scenario:** a future edit to `renderPickPrompt()` or `localPickCell()` — say, a
well-intentioned refactor that folds in a "mirror the host's own prompt for spectators" call, which
this very plan explicitly rejected as a design temptation — could reintroduce a call to
`netSetPrompt`/`remotePrompt` on the local render path with zero automated gate catching it. The only
thing that would catch it is a human remembering to manually drive a full solo voyage before
shipping, which is exactly the fragility Pitfall 1 and this task's own `<action>` item 8 were written
to make structural rather than a matter of memory. Currently the live code IS safe (verified
directly — neither function references any writer), so there is no live bug; the risk is a silent
regression with no gate to catch it and no record that the gate is missing.
**Fix:** Add the assertion as specified — either as a new numbered assertion in
`scripts/host_guest_parity_check.js` (the plan's own suggested home) or `4/scripts/prompt_field_parity_check.js`,
declaring `renderPickPrompt`/`localPickCell` as the local-path function list and failing if a
comment-stripped scan of their bodies matches `netSetPrompt|netRemovePrompt|netSetResponse|remotePrompt|onRemotePrompt`.
Drill it with a synthetic tree that plants one such call. At minimum, if this is deliberately being
deferred, update `02.15-02-SUMMARY.md`'s Deviations section to say so — right now a reader has no way
to know this protection doesn't exist without diffing the plan against the shipped scripts by hand.

**Outcome: FIXED.** Added as assertion 3 of `4/scripts/prompt_field_parity_check.js` (commit
`b172c08`) — that file had exactly two assertions before this fix, matching the plan's own words
("assertion 3 of the existing gate"). Declares `renderPickPrompt`/`localPickCell` as the local-path
function list; fails on a comment-stripped match of
`netSetPrompt|netRemovePrompt|netSetResponse|remotePrompt|onRemotePrompt`; fails loudly (anti-vacuity)
if neither function is found. Red-proofed twice: directly against the real source tree (planted
`netSetPrompt` inside `renderPickPrompt`, watched `FAIL` naming it, reverted, watched `PASS`, file
confirmed byte-identical), and as three new standing `--drill` fixtures (3a/3b/3c) plus the existing
negative control (drill Z, real tree). `02.15-02-SUMMARY.md` addendum records the gap and this fix.

### WR-02: `renderPickPrompt()` silently dropped the "older host payload" `msg` fallback the retired `remotePickHighlights()` had

**File:** `4/src/ui/flow.js:544` (via `4/src/orchestrator.js:1443`)
**Issue:** The retired `remotePickHighlights(cells,promptId,msg,hint)` rendered
`sailPanelHTML(msg||sailPickMsg(appState.mySeat),hint)` — its own comment explained this was
deliberate: *"Falls back to sailPickMsg(mySeat) for an older host payload with no msg field, so a
mid-game version skew still reads sensibly."* `renderPickPrompt(spec,answer)` renders
`sailPanelHTML(spec.msg,spec.hint)` with no fallback, and `watchPrompt`'s pick branch calls it with
`msg:p.msg` — also no fallback. In this codebase's actual deploy model (no build step, `main` is
pushed to live mid-session, per `docs/GIT-AND-DEPLOY.md` and CLAUDE.md §6), a guest whose tab is
holding an older cached module set while the host is on a newer one (or vice versa, in the rarer
direction) is a real, if narrow, scenario — and it is precisely the scenario this fallback was
written for.
**Concrete failure scenario:** if `p.msg` is ever `undefined` on the wire (stale client, a future
refactor that renames the field, or a genuinely old host), the sail card renders the literal string
`"undefined"` where a sensible fallback sentence used to appear — a visible regression under
tonight's own hard constraint ("NOTHING A PLAYER CAN SEE CHANGED"). It is not exercised by the three
voyages this drop was verified against (all played on one build, one stamp, no skew), so it would
not have been caught by this session's own testing.
**Fix:** Either restore the fallback inside `renderPickPrompt` (`spec.msg||sailPickMsg(appState.mySeat)`,
gated so it only applies when `spec.msg` is falsy) or explicitly note in `docs/DISPLAY-RULES.md`'s
pick-channel row that this defensive fallback was intentionally dropped and why.

**Outcome: FIXED.** Restored exactly the suggested fallback inside `renderPickPrompt`
(`4/src/ui/flow.js:544`, commit `c63d76e`): `sailPanelHTML(spec.msg||sailPickMsg(appState.mySeat),spec.hint)`.
`pickCell()` always populates `spec.msg` locally so this never fires on the tracer's own path today —
it only guards a stale/skewed client, exactly the scenario the retired `remotePickHighlights()`
fallback existed for. Re-anchored `prompt_field_parity_check.js` drill 2c's surgery target to the new
line so the standing gate's red-proof still holds; `node 4/scripts/prompt_field_parity_check.js --drill`
passes (13/13, real tree clean).

### IN-01: Redundant `panel("")` call on the guest's answer path

**File:** `4/src/orchestrator.js:1207-1215` (`sendResponse`), reached from `4/src/orchestrator.js:1443`
**Issue:** `renderPickPrompt`'s `done(v)` calls `teardown()` (which already runs `panel("")`) before
calling `answer(v)`. For the guest's pick branch, `answer` is `cell=>sendResponse(p.id,cell)`, and
`sendResponse` itself unconditionally calls `panel("")` again a few lines later. This is harmless —
`panel()` is idempotent/debounced (`CLEAR_GRACE_MS`) — but it's a duplicate call left over from
converging two independently-written teardown paths into one call sequence.
**Fix:** No urgency; if `sendResponse` is ever touched for other reasons, consider whether the pick
channel still needs its own `panel("")` call given the renderer already clears the panel before
`answer` fires.

**Outcome: SKIPPED (not fixed tonight).** `sendResponse` (`4/src/orchestrator.js:1207`) is shared by
BOTH the ask channel and the pick channel — its own comment says it mirrors `localAsk`'s `done()`,
and removing/conditioning its `panel("")` call would need to reason about whether the ask channel
(not converged tonight; Tasks 4/5 remain parked) still depends on it, which is a change to
`orchestrator.js`, a file untouched by tonight's two Warning fixes. The finding itself says "no
urgency" and flags this as speculative ("if `sendResponse` is ever touched for other reasons").
Left as recorded here rather than widening tonight's diff into a file neither Warning fix touched.
