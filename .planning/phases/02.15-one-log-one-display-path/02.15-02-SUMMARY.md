## Deviations from Plan

### Auto-fixed / Handled Inline

**1. [Rule 1 — bug in the plan's own verify oracle] Task 3's literal verify script over-matches on `JSON.stringify` of the whole result object.**
- **Found during:** Task 3's structural verification.
- **Issue:** The plan's check `if(/renderPickPrompt/.test(t))` (where `t` is the FULL JSON of `checkOrchestrationParity`'s result, including `notes`) would ALWAYS fail once `renderPickPrompt` exists as a declared row — `notes` unconditionally lists every row by name, including passing shared ones, matching the SAME pre-existing pattern `flash`/`applyActiveSeat` already establish. The check as literally written could never pass for a genuinely converged renderer.
- **Fix:** Verified the meaningful semantics instead — `s.failures` (not the whole stringified object) does not name `renderPickPrompt`, and does name `localAsk`. Ran and recorded both the literal check's output (showing the over-match) and the corrected one (showing the real state) so the discrepancy is auditable.
- **Verification:** Manually confirmed via `checkOrchestrationParity(root,{strict:true}).failures` containing only the `localAsk` message.

**2. [Rule 1 — bug, shorthand property regex] The plan's wire-field key extraction regex misses ES6 shorthand properties.**
- **Found during:** Task 3's wire-payload-unchanged verification.
- **Issue:** `[...lit.slice(0,200).matchAll(/([A-Za-z_$][\w$]*)\s*:/g)]` only matches `key:value` pairs, not bare shorthand identifiers. The `{kind:"pick",cells,msg:...,hint:...}` literal (both before AND after Task 3 — this was never touched, only lifted into a named `spec` variable) uses `cells` as shorthand, so the check as literally written would report "cells" missing from a payload that has always carried it.
- **Fix:** Used a shorthand-aware regex and, more decisively, cross-checked against `4/scripts/prompt_field_parity_check.js` assertion 2 — the gate BUILT for exactly this purpose — which independently confirmed `sail payload fields: cells, hint, kind, msg`.
- **Verification:** `node 4/scripts/prompt_field_parity_check.js` passes; sail payload field set unchanged.

**3. [Rule 1 — real regression caught before shipping] Hardcoding `renderPickPrompt` in `host_guest_parity_check.js` assertion 2 broke root `npm test`.**
- **Found during:** Task 3's re-anchor of the root-tree parity gate.
- **Issue:** The plan's instruction to "re-anchor its two function names to `renderPickPrompt`" assumed a single tree. `scripts/host_guest_parity_check.js` scans TWO trees (root v1, untouched since 2026-08-02, and `4/`, converged tonight) via its own tree-selector. Hardcoding the converged name broke assertion 2 against the ROOT tree — which this file is wired into root `npm test` FOR (`package.json`'s `test` script) — for a reason that has nothing to do with any drift on that tree. This is exactly the "gate red for reasons unrelated to what it measures" failure the file's own header warns against.
- **Fix:** Made the assertion DUAL-MODE: detect whether `renderPickPrompt` exists (converged, `4/`-shape) or not (legacy, root-shape), and apply the check that shape earns. Root tree passes byte-identically to before; `4/` gets the stronger converged check.
- **Verification:** `node scripts/host_guest_parity_check.js` (bare, root default) exits 0; `node scripts/host_guest_parity_check.js --tree=4 --report` shows assertion 2 failing ONLY on the pre-existing, unrelated `class:"sailCell"` issue (Phase 3/TEST-06's, not touched here).

**4. [Rule 1 — measured correction] "Solo has `db===null`" was wrong; corrected in `docs/DISPLAY-RULES.md`.**
- **Found during:** Task 6's solo voyage, driven live.
- **Issue:** The plan text (`<the_shape>` constraint 1, and Task 3's action block) repeatedly states solo has `db===null`. Measured directly: `{dbTruthy:true, room:null, isHost:true}`. `4/index.html` loads the real Firebase SDK.
- **Fix:** DISPLAY-RULES.md's Rule A section corrected with the measured reading, and the actual safety-relevant field (`room`, not `db`) named explicitly for future writers of the mirror-when-remote guard.

## Infrastructure finding, worth recording even though it is not a game defect

**A long-running headless Chrome tab intermittently reports `document.hidden===true`, throttling `setInterval` timers (including the driver used to play these voyages) to roughly 1 tick/sec instead of 2/sec.** This is the documented `docs/DRIVING-THE-GAME.md` §8b trap, encountered live: it stalled the FIRST pass-and-play attempt for several minutes before being diagnosed via `document.visibilityState`. Neither `Page.bringToFront` nor `Page.setWebLifecycleState({state:"active"})` nor `/json/activate/{id}` restored `document.hidden` to `false` in this headless build — closing a stray `about:blank` tab and re-launching a completely fresh Chrome instance did eventually produce a clean run, but the exact trigger was not isolated. Not a code defect; recorded here because it cost real time and the next session driving this game headlessly should know the symptom (steady 2 ticks/sec dropping to near-zero with no error) and the mitigation that worked (kill everything, relaunch fresh, avoid excessive concurrent CDP connections to the same tab).
