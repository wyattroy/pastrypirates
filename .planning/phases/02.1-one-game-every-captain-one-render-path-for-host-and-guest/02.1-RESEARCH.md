## Summary

Every renderer in `4/` reads `appState.game` directly. That was correct the day the redesign
shipped — `4/`'s stage (camera director, ribbon, radial prompt) was built and verified **solo-only**
(`511c427`, 2026-08-11, "a verbatim copy of /3 wearing the new shell, solo only"). In solo,
`appState.game` **is** live truth: nothing else writes to it. Multiplayer was off. The moment Phase 2
turned Firebase back on, that assumption silently became false for every guest, and nobody had to
touch a line of stage code for it to happen — the bug was already latent in code that had never been
run against a second browser.

**The mechanism, confirmed by direct source read:** `beginGame()` (`4/src/orchestrator.js:1592-1593`)
is the one and only branch point between "who computes" and "who watches":

```js
if(appState.isHost){runLiveNet().catch(e=>voyageAground(e,"runLiveNet"));}
else{watchEvents();watchPrompt();watchNarr();watchFlip();watchBattle();watchDraftPrompt();watchClock();watchTurnOrder();watchRecoveryState();}
```

`runLiveNet()` mutates the real `Game` instance (positions, round, wind, coins — everything).
`watchEvents()` (`:1215-1240`) does none of that: it pushes each incoming event onto
`appState.game.events` and calls `render()` — it never writes `game.players[i].pos`, `game.round`,
`game.windNow`, etc. So on a guest, `appState.game` is a `Game` object that was constructed once
(`beginGame()`, `:1570`) and then frozen at its starting values for the entire voyage, while
`appState.game.events` fills up with everything that actually happened. `render()`
(`4/src/ui/board.js:1567`, `:1576`) already knows this and reads `events[evIdx].state` for what to
draw — that part is correct and always has been. **The bug is everything that draws WITHOUT going
through `render()`'s own snapshot lookup**, all of it in `4/src/ui/stage.js`: `ribbonTick()` reading
`g.round` (`:403`), `pillHTML()` reading `g.windNow`/`g.forecastWind()` (`:381-384`), and every
camera function (`camToSeat`, `camFitSail`, the `battle`/`stormCam` hooks in `window.__pp4`) reading
`g.players[i].pos` directly (`:72, 97, 111, 1627, 1650-1656`).

**The good news, and it is the single most load-bearing finding in this research:** the engine
already bakes everything these functions need into every event, via `Game.ev()`
(`4/src/engine/index.js:316-317`):

```js
ev(o){if(!this.record)return;o.round=this.round;o.wind=this.windNow;o.storm=this.stormNow;o.wind2=this.windNow2;
  o.state=this.players.map(p=>({pos:[...p.pos],coins:p.coins,ing:[...p.ing],done:p.done,baking:!!p.baking}));
  o.tokens={...this.tokens};this.events.push(o);}
```

Round, wind, storm, and full per-player position/coins/ingredients/done/baking state are on **every
single event already**, over the wire, today. The `newround` event additionally carries `next`
(`forecastWind()`) and `nextStorm` (`4/src/engine/index.js:2939-2940`). **No engine change, no wire
format change, and therefore no determinism concern is needed to fix the ribbon, the wind pill, or
the camera.** This is a UI-tier fix: teach the guest's copy of `appState.game` to stay honest, or
teach the renderers to read the event snapshot the way `render()` already does. See Question 2/3
below for the recommendation between those two shapes.

**Primary recommendation:** apply each incoming event's baked-in state onto `appState.game` itself
(inside `watchEvents()`), the same pattern `applyEndMeta()` (`orchestrator.js:756-765`) already uses
at end-of-voyage — just run it every event instead of once. This makes `appState.game` simply true on
both tiers, deletes the need to touch 6+ separate stage.js call sites individually, and is the
"elegant version that deletes code" the project's own standing rule asks for. Full trade-off analysis
in Question 3.

The second thread — the duplicated prompt renderer (`localAsk` vs. `watchPrompt`/`watchDraftPrompt`)
— is a narrower, already-partly-recognized problem (the code's own comment at `orchestrator.js:1286`
calls it out). Fixing the state layer first, per Wyatt's sequencing ruling, does not fix this thread;
it is a separate, second piece of work within the same phase. See Question 5.

The flat-card bug (Question 7) traced to a **root cause fully confirmed by source read**, unrelated
to attribute-escaping of quote characters (which is already correct) and instead caused by a later,
attribute-blind emoji-to-`<img>` substitution pass. See below — this is the one piece of this
research with a complete, ready-to-implement fix.

## 2. Can the guest's state be made honest without changing what the engine emits?

**Yes — confirmed by direct source read, for everything the ribbon and camera need.**

`Game.ev()` (`4/src/engine/index.js:316-317`, quoted in full above) already bakes onto **every**
event: `round`, `wind` (=`windNow`), `storm` (=`stormNow`), `wind2`, and a full `state` array
(`pos`, `coins`, `ing`, `done`, `baking`) for every player, plus `tokens`. The `newround` event
additionally carries `next` (`forecastWind()`) and `nextStorm` (`4/src/engine/index.js:2939-2940`,
also `:2960`).

Cross-checked against everything the category-(c) sites in Question 1 need:

| Renderer needs | Already on the wire? | Where |
|---|---|---|
| `ribbonTick()`'s day counter | Yes | every event's `o.round` |
| `pillHTML()`'s wind now / forecast / storm-next | Yes | `o.wind`/`o.storm` on every event; `next`/`nextStorm` on the `newround` event specifically |
| Every camera function's `g.players[i].pos` | Yes | every event's `o.state[i].pos` |
| Coins/ingredients (for anything that might read them for camera/UI decisions) | Yes | every event's `o.state[i].coins`/`.ing` |
| `done`/`baking` flags | Yes | every event's `o.state[i]` |

The one thing genuinely absent from the per-event payload is **derived/aggregate fields only needed
at game end** (`battles`, `trades`, `attWins`, `finishOrder`, `winner`, `flips`, `heads`) — and those
are already handled, once, by the existing `applyEndMeta()` (`orchestrator.js:756-765`) reading a
separate `meta` node written by `writeMeta()`. Nothing this phase needs to fix requires touching that
path.

**Conclusion: this phase requires zero engine changes.** Wyatt's ruling ("change the stream if that
is the right design, accept the re-record") removes a constraint that, on the evidence, this phase
does not need to spend. See Question 4 for why the "re-record" framing doesn't even apply yet.

## 3. The shape of the fix at the state layer

Three options were evaluated, per the brief.

### Option A — a single accessor every renderer calls

E.g. `currentPos(seat)` that returns `events[evIdx].state[seat].pos` (falling back to
`game.players[seat].pos` when no events exist yet, matching `render()`'s own existing fallback at
`board.js:1567`). Every one of the ~6 category-(c) sites in stage.js would call this instead of
`g.players[i].pos` / `g.round` / `g.windNow`.

- **Pro:** smallest diff; touches only the reading sites; no risk to anything that legitimately
  needs live `appState.game` (there is none on a guest, since a guest never computes — see below).
- **Con:** every NEW render site added in the future has to remember to call the accessor instead of
  reaching for `appState.game` directly — the same "match by discipline, not by structure" failure
  mode `host_guest_parity_check.js`'s own header quotes D-56 naming (`scripts/host_guest_parity_check.js:16`).
  It does not delete any code; it adds a parallel path.

### Option B — apply the snapshot back into `appState.game` on receipt (RECOMMENDED)

Extend `watchEvents()` (`orchestrator.js:1215-1240`) so that, immediately after pushing the incoming
event, it also writes `event.state[i]` onto `appState.game.players[i]` **in place** (mutate the
existing player objects' `pos`/`coins`/`ing`/`done`/`baking`, don't replace the array), and sets
`appState.game.round = event.round`, `.windNow = event.wind`, `.stormNow = event.storm`, plus (only
on a `newround` event) `.windNext = event.next`, `.stormNext = event.nextStorm` so
`forecastWind()` keeps working unmodified.

- **Pro — this is the "elegant version that deletes code" the project's own standing rule asks for.**
  Every one of the 6 category-(c) sites needs **zero changes** — `g.round`, `g.players[i].pos`,
  `g.windNow` simply become true. `applyEndMeta()` already proves this exact pattern is sound and
  already ships (`orchestrator.js:756-765` does precisely this, once, for the end-of-voyage summary
  fields) — this option is "run the same idea every event instead of once at the end," not a new
  invention.
- **Pro:** because it mutates the SAME player object references (never reassigns `appState.game.players`),
  nothing that holds a reference to a player object (e.g., `renderBattleFromSnap`'s
  `appState.game.players[snap.attIdx]`, `flow.js:2282-2285`) needs to change either — the reference
  stays valid and its fields become correct.
  - **Verified safe:** a guest never calls any function that *computes* off `appState.game`
    (`reachable()`, `sailSelfCheck()`, `pickCell` legality, bot planning) — those only run on the
    host or in a local (solo/pass-and-play) decision. A guest's copy of `appState.game` is read-only
    in practice already; this option formalizes that by keeping it truthful rather than frozen.
- **Con:** couples `watchEvents()` to the shape of `event.state` — if a future engine change alters
  what `state` carries per player, this one function needs updating (a single, findable chokepoint,
  not a maintenance risk spread across 6 files).
- **Con:** the `newround`-only fields (`windNext`/`stormNext`) need a small `if(e.t==="newround")`
  branch inside `watchEvents()` — a few lines, not a redesign.

**This is the recommendation.** It turns 6+ scattered reading-site fixes (Option A) into one
writing-site fix, matches the pattern the codebase already trusts (`applyEndMeta`), and — per the
project's own stated preference — *deletes* the implicit "guest state is a lie" caveat from
`docs/DRIVING-THE-GAME.md` §5c rather than working around it.

### Option C — a derived view object

A `guestView()`/`renderState()` object rebuilt on every event, separate from `appState.game`, that
every renderer reads instead. Evaluated and **not recommended**: it recreates the exact "two copies
that must be kept in step" shape the phase exists to eliminate (this is structurally the same
mistake as the two prompt renderers in Question 5) — now `appState.game` (host-authoritative) and
`guestView` (event-derived) both exist, and a renderer written against the wrong one is a new,
silent bug class. Option B collapses to one object; Option C doubles it.

sending an array of `{label,cls,disabled,why,seat,short}` objects instead of six parallel arrays
(`labels[]`, `classes[]`, `disabled[]`, `why[]`, `shorts[]`) — the parallel-array shape is a
convention this codebase chose, not a platform constraint. A single option-list payload would let one
button-builder function be shared verbatim between `localAsk` and `watchPrompt`, which is the real
fix for "a genuine second copy" (`orchestrator.js:1286`'s own words).

directly (`flow.js:213`, `done(v)` calls `res(v)`); a remote seat resolves through

resolution paths must stay separate even if the two RENDER paths are unified** — unifying the button
HTML-builder does not mean unifying `res(v)` vs. `netSetResponse(...)`. The safest refactor shares a
pure "build this button row's HTML from an option list" function called by both `localAsk` and
`watchPrompt`, while each keeps its own distinct `onclick` wiring (`res(i)` vs. `sendResponse(id,i)`).
This mirrors the fix already proven for `sailHighlightRect()` (G25, `flow.js:388-419`) — "fixed by
construction, not by copying attributes... each caller keeps its own click handler... only the RECT
is shared."

## 7. The flat-card bug — root cause fully confirmed, fix identified

**This is a confirmed, verified root cause** (not a guess), traced through three source files.

**The escaping at the `data-why` attribute IS correct.** Both embedding sites already HTML-escape
the why text before it reaches the attribute:

- `localAsk`, `flow.js:248-250`: `const esc=s=>String(s).replace(/&/g,"&amp;").replace(/"/g,"&quot;").replace(/</g,"&lt;");`
  … `data-why="${esc(x.o.why)}"`.
- `watchPrompt`, `orchestrator.js:1290,1299`: the identical function, named `escW`, same three
  replacements, same usage.

Neither of the currently-shipped `why:` strings in the codebase (`flow.js:1243,1247,1374,1525,1602,
1760,1763,2026`) contains a literal `"` character, so this escaping is not currently exercised
against a real quote — but it is correctly written and would hold one if it ever appeared.

**The actual bug is one step later, and it is attribute-blind.** `panel()`
(`4/src/ui/panel.js:434-435`) runs the **entire assembled HTML string** — the whole button row,
attributes included — through `emojify()` before setting `innerHTML`:

```js
export function panel(html,needsAction=false){
  html=emojify(html);
  ...
```

`emojify()` (`4/src/shared/index.js:113-116`) is a blind, whole-string regex replace with **no
awareness of HTML structure at all**:

```js
function emojify(html){
  if(!html)return html;
  return html.replace(EMOJIFY_RE,m=>iconImg(EMOJI_IMG[m.replace(/️$/,"")]));
}
```

`🌕` (the coin glyph) is in `EMOJI_IMG`, mapped to `COIN_IMG` (`shared/index.js:85`). And `iconImg()`
(`shared/index.js:168`) returns:

```js
const iconImg=src=>`<img class="narrIcon" src="${src}" alt="">`;
```

**This string contains three literal double-quote characters.** When `emojify()`'s regex finds a
🌕 anywhere in the fully-assembled HTML — including *inside* an already-correctly-escaped
`data-why="Ye can't afford the powder — 5🌕 a broadside..."` attribute value — it splices in
`<img class="narrIcon" src="assets/....png" alt="">` **in place of the emoji character, at that exact
position inside the attribute string.** The very first `"` in that injected markup
(`class="narrIcon"`) closes the `data-why="..."` attribute early. Everything from that point in the
original why-sentence onward (` a broadside, and yer purse won't stretch.`) is no longer inside any
attribute — it becomes loose, unquoted content the HTML parser attaches to the button's opening tag
(as junk attribute-like tokens) or spills into the element as text, depending on exactly where the
`>` characters land relative to the rest of the tag. **This is exactly "a greyed button's `why`
sentence containing a coin breaks its own label out of its quote marks"** — confirmed mechanism, not
inferred.

This directly explains the character-count symptom in the phase brief: the Attack button's clean
label (`⚔️ Attack (−5🌕)`) is short, but once `data-why`'s attribute boundary is broken open by the
injected `<img ...>` markup, part of the why-sentence and the broken tag fragments leak into what
`menuButtons()` (`stage.js:1029`) measures as the button's own `textContent`, pushing it well past
the 16-character radial cutoff and forcing the whole prompt (`ap.querySelector(...)` disqualifies
radial mode for the WHOLE panel, not just one button — `stage.js:1024`) to fall back to a flat card.

**This bug is not limited to Attack, and not limited to `why`.** Any `why:` string containing a
mapped emoji (🌕 is the common one — buy-crate `flow.js:1243`, powder cost `flow.js:1760` — but the
mechanism applies to any character in `EMOJI_IMG`, `shared/index.js:84-101`) will corrupt the
attribute the same way, on **both** the host (`localAsk`/`panel()`) and the guest (`watchPrompt`/
`panel()`) — `panel()` is the single shared render sink both paths call into, which is why the phase
brief correctly says this "hits host and guest alike."

**The smallest correct fix:** `emojify()` must never touch text that is already inside an HTML
attribute value. The `data-why` attribute in particular does not need emoji-to-`<img>` substitution
at all — `showWhy()` (`flow.js:155-162`) reads it back via `b.dataset.why` and sets
`d.textContent=why` directly (a plain-text tooltip; the browser renders the native 🌕 glyph fine with
no image substitution needed there). Two viable fixes, in order of preference:

1. **Stop passing `data-why`'s content through `emojify()` at all.** Since `panel()`'s blanket pass
   is what causes the corruption, and the attribute value was never meant to be emoji-imaged, the
   cleanest fix is to make `emojify()` skip matches that fall inside an attribute-value span (a small,
   generalizable regex/state-machine tweak — protects every future `data-*` attribute from the same
   class of bug, not just `data-why`).
2. **Narrower, faster to ship:** HTML-entity-encode the coin (and any other `EMOJI_IMG`-mapped)
   glyphs specifically *within* `esc()`/`escW()` before they reach the attribute, so by the time
   `panel()`'s `emojify()` pass runs, there is no longer a matchable emoji character left inside the
   attribute for it to touch. Cheaper, but narrower — protects only the sites that already call
   `esc`/`escW`, not every future `data-*` attribute.

**Confidence: HIGH / VERIFIED** for the mechanism (every step traced to a specific file:line and
quoted). The **one thing not independently reproduced in a live browser** during this research (read
-only, no browser driven) is the exact resulting DOM shape after the parser recovers from the broken
attribute — I traced the HTML-parsing consequence from first principles (an unescaped `"` inside a
double-quoted attribute value closes it) rather than observing it render. The planner should treat
the mechanism as confirmed and the exact visual/DOM outcome as worth one quick browser screenshot
before shipping the fix, per this project's own rule 19 ("look at it in the browser, with
screenshots, before handing it to Wyatt").

the earlier code stop assuming a narrower world than the one it now runs in, not to patch around the
symptom.

## Common Pitfalls

### Pitfall 1: Trusting `appState.game` for anything on a guest
**What goes wrong:** any new code (this phase's own fix included) that reads `appState.game.round`/
`.windNow`/`.players[i].pos` directly, believing it to be live.
**Why it happens:** it IS live on the host, and was live on the guest too before Phase 2 turned
multiplayer back on — the assumption predates the bug.
**How to avoid:** after Option B lands, this stops being a pitfall (the object becomes true on both
tiers) — but until it lands, any interim code must read `events[evIdx].state` as `render()` already
does, never `appState.game.players` directly.
**Warning signs:** a guest's UI element that is correct at game start and silently freezes/drifts as
the voyage progresses — exactly the day-counter and camera symptoms already reported.

### Pitfall 2: `panel()`'s blanket `emojify()` pass touching attribute content
**What goes wrong:** any future `data-*` attribute built from player-facing copy that happens to
contain a mapped emoji character will corrupt in the same way as the flat-card bug.
**Why it happens:** `emojify()` (`shared/index.js:113-116`) has no concept of "inside an attribute" —
it is a blind string replace, applied once, late, over the whole assembled HTML in `panel()`.
**How to avoid:** fix `emojify()` to be attribute-aware (Question 7's recommended fix #1) rather than
patching each individual attribute site as new ones appear — the codebase has already had to add
`data-why`, `data-seat`, and `data-stage`-style attributes several times, and each one is a fresh
opportunity for this exact bug.
**Warning signs:** a prompt that renders as a flat card in exactly the configurations where a
disabled/greyed reason text happens to contain a 🌕, 🔥, ⚔, or any other `EMOJI_IMG`-mapped glyph.

### Pitfall 3: Fixing the render sites (Option A) before the state layer (Option B)
**What goes wrong:** if the planner sequences per-renderer patches before the state-layer fix, each
patch has to independently decide how to read `events[evIdx].state`, producing the exact "match by
discipline, not by structure" drift `host_guest_parity_check.js`'s own D-56 citation warns about.
**Why it happens:** it feels incremental/lower-risk to fix one visible symptom (the ribbon) at a time.
**How to avoid:** Wyatt's own sequencing ruling already covers this ("fix the state layer FIRST... let
the render bugs fall out") — this research confirms it is also the technically cheaper path (Option B
deletes 6 sites of special-casing rather than adding 6).

## Open Questions

1. **Should the guest-reload gap (Q1's note on `boot()`/`resumeHostGame`) be folded into this phase?**
   - What we know: today a guest who reloads mid-voyage rebuilds nothing locally until the next
     broadcast event arrives — their board is blank/stale for a gap of unknown length.
   - What's unclear: whether this is severe enough to be part of "one render path for host and
     guest," or belongs with the backlog Phase 999.1 resume item / a future guest-resume phase.
   - Recommendation: raise it to Wyatt as a scoping question rather than silently including or
     excluding it — it is adjacent to, but not named by, ROADMAP's Phase 02.1 success criteria.

2. **Should `watchDraftPrompt` be unified into the same button-builder as `localAsk`/`watchPrompt`, or
   kept deliberately narrower (Q5)?**
   - What we know: it currently duplicates ~15 lines of button HTML with a smaller field set
     (no `disabled`/`why`/`colors`/`back`/`flip`) because recipe-draft cards are never disabled.
   - What's unclear: whether a future prompt type might route through the draft channel and need
     those fields, which would make the narrower duplication a future bug rather than a deliberate
     simplification.
   - Recommendation: unify the pure HTML-building function (cheap, removes the duplication risk)
     while keeping the draft channel's simpler wire payload — matches the `sailHighlightRect()`
     precedent (share the builder, not the whole call site).

3. **Should this phase build a minimal host/guest parity gate for `4/` now, or accept the gap until
   Phase 3?**
   - What we know: no automated gate exists; Phase 3 is explicitly where one gets ported.
   - What's unclear: how much regression risk this specific phase's own changes carry without one.
   - Recommendation: name the decision explicitly in the plan rather than leaving it implicit — a
     minimal version (even just asserting the option-object field set localAsk/watchPrompt both
     support matches, mirroring `host_guest_parity_check.js` assertion 1) is cheap insurance given
     this phase is precisely what that gate is designed to catch regressions in.
