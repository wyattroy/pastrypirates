# Phase 02.1 Plan 01: The Guest's Game Stops Lying — Summary

**One change inside `watchEvents()` makes a guest's `appState.game` tell the truth, and the stuck day
counter, the blank wind pill and the off-target sail camera all disappear without a single renderer
being touched.**

## Performance

- **Duration:** ~45 min (excluding two harness-repair reruns of the red probe)
- **Started:** 2026-08-19T21:43Z
- **Completed:** 2026-08-19T22:12Z
- **Tasks:** 3 of 3
- **Files modified:** 1 (`4/src/orchestrator.js`, +49 −2)

## Accomplishments

- **Proved the bug was real before fixing it**, on two real browsers against the live database, and
  captured it in pictures a person can read at a glance.
- **Fixed it in one place.** `watchEvents()` now writes each event's own baked-in snapshot onto
  `appState.game` as the event lands. Nothing in `4/src/ui/stage.js`, `4/src/ui/board.js` or any
  other renderer changed — the six broken sites simply became correct.
- **Proved it gone with the identical instrument**, verified byte-identical by md5 across both runs.
- **Confirmed PAR-04** (narration) at 60 matched moments rather than asserting it.
- **Zero engine changes**, so no determinism question and nothing new crosses the wire.

## What the bug actually was

`beginGame()` (`orchestrator.js:1568`) constructs `appState.game` on **both** tiers, but only the
host's `runLiveNet()` ever mutates it again (`:1592-1593` is the one branch point). So on a guest
that object was a photograph taken the instant the voyage began: `round` stayed `0`, `windNow`
stayed `null`, and every captain's `pos`/`coins`/`ing`/`done`/`baking` stayed at their spawn values
for the entire voyage — while `events[]` filled up with everything that actually happened.

`render()` has always known this and draws from `events[evIdx].state` (`board.js:1567`). **That is
precisely why the board looked right and the ribbon, the pill and the camera were wrong**: those six
sites read `appState.game` directly and never went through the snapshot.

## PAR-04 — narration, confirmed rather than rebuilt

60 matched moments across two days, host and guest. The result needs stating precisely, because a
naive "are the strings equal" reading would call it a failure and it is not one:

- **Table-wide lines are byte-identical on both screens** — *"Dough Hook sets sail"*, *"HEADS! Dough

- **Lines addressed to a captain are deliberately different on each screen, and that is the design.**
  The host (Wyatt) reads *"Claude attacks ye! One broadside each…"*; the guest (Claude) reads

  showing the next bubble.

No narration code path was touched by this plan, so this is a non-regression confirmation, not a fix.

## The A1 safety check, run against the tree at execution time

The plan required this to be re-run rather than recalled. **What was searched:** every read of
`appState.game.players` in `4/src` and `4/index.html`, excluding `4/src/engine/` — 54 sites across
`util.js`, `orchestrator.js`, `flow.js`, `board.js`, `recipe.js`, `panel.js`. **What was looked for:**
any guest-reachable reader that assumes those fields stay at their construction-time (spawn) values.

**What was found: none.**

- **Exactly one site treats `.pos` off that array as authoritative** — `renderLiveShips()`
  (`board.js:1382`), whose own header comment already names this bug (*"reads
  `appState.game.players[i].pos`, which on a GUEST NEVER UPDATES"*). It is **host-only by
  construction**: its sole caller is `runStormLive()` (`flow.js:1108`), reached only from
  `runLiveDayClassic`/`runLiveNet` — the `isHost` branch of `beginGame:1592`. Unreachable on a guest.
- `paintShipAt` (`board.js:1567`) already prefers the event snapshot; its `appState.game.players`
  fallback goes from stale-wrong to correct.
- `render()` (`board.js:1582`) draws positions from `st[i].pos` and only uses the players array for
  `.strategy`/`.recipe`, neither of which this change touches.
- The handful reading `.ing`/`.done`/`.coins` on a guest — `assignBadges()`'s fallback
  (`util.js:1151`) and `panel.js:237`'s bot-playing check — go from frozen-wrong to correct.
- `computeAwards()` walks `events` for everything and reads only `players.length`.
- Everything else reads `.strategy`, `.recipe`, `.flips`/`.heads` or `.length` — untouched fields.

**A record entry this supersedes, named because the next session will find it:** `.planning/WINDOWS.md`
entry 2 states *"reading `game.players[].pos` on the GUEST is the wrong probe — guests are render-only
(host-authority model), so their local game object is intentionally stale."* That staleness was
written down as a property of the design. It was a latent bug in code that had never been run against
a second browser, and it is now fixed. Same wording appears in `docs/DRIVING-THE-GAME.md` §5c — see
Deferred Items.

## The diff, in words

`watchEvents()` now declares `const e=fixEv(snap.val())` before pushing it, then — still before any
`await`, so the ordering guarantee G14 depends on is untouched — applies `e.state` onto the existing
player objects **by field assignment**, and sets `round`/`windNow`/`stormNow` from the event's own
`round`/`wind`/`storm`. `windNext`/`stormNext` are written only inside the `e.t==="newround"` branch,
because those two fields ride on no other event.

Three deliberate details:

1. **Mutated in place, never reassigned.** `renderBattleFromSnap` holds `appState.game.players[i]`
   object references across a fight (`flow.js:2283-2285`). Replacing the array would strand them;
   writing their fields makes those same references become true.
2. **The arrays are copied, not aliased** (`[...s.pos]`, `[...s.ing]`) — exactly as `Game.ev()` copies
   them on the way out. `events[i].state` is the scrubber's history, and history must not be reachable
   for writing through a live player object. This is a small hardening on top of the research's
   illustrative diff, taken deliberately.
3. **The re-fetch of `events[evIdx]` after `render()` is deleted.** It was already handing back the
   identical object (`evIdx` was set to `events.length-1` the instant after `e` was pushed), and it
   would now be a redeclaration this scope refuses to parse. `spawnPops`, `playForEvent` and the
   `end` branch read the `e` from the top of the callback.

**Nothing crosses the wire that did not before.** `Game.ev()` (`engine/index.js:316`) has always baked
`round`/`wind`/`storm`/`state` onto every event, and `newround` has always carried `next`/`nextStorm`.
This change only alters what the guest's own browser does with data it was already receiving — so
there is no engine change, no wire-format change, and no determinism question.

## Deviations from Plan

### [Rule 3 — Blocking] The documented autoplay driver could not play the game

- **Found during:** Task 1, before any code change
- **Issue:** `docs/DRIVING-THE-GAME.md` §5b's driver clicks `.apBtn` with no liveness filter. A guest
  reached `coinStepper()`'s remote-seat fallback (`flow.js:1475`), whose `− 1🌕` is `aria-disabled` at
  the floor. The driver clicked it **460 times over ten minutes**; the host froze mid-battle waiting
  for an answer that could never arrive. The probe reported "harness incomplete" — no game fault at
  all, a harness that could not reach the moment under test.
- **Fix:** the rig's driver now filters to live buttons (`aria-disabled !== 'true'`), prefers the
  committing circle (`cls:"primary"`), and rotates if the same label fails five times running.
- **Scope:** scratchpad rig only — no repo file changed. The doc fix is DOC-06's (see Deferred Items).
- **Commit:** none (scratchpad).

### [Rule 3 — Blocking] A click landing before boot is a silent no-op

- **Found during:** Task 3's confirmation probe
- **Issue:** `#choiceHost.click()` 500ms after `Page.navigate` sometimes lands before boot finishes.
  Nothing errors; the name modal simply never opens and the probe times out 15s later on a wait that
  looks unrelated.
- **Fix:** wait for `#choiceHost` to be *visible* before driving — the same `offsetParent` idiom §3
  already prescribes for `#btnNameConfirm`, applied one step earlier.
- **Commit:** none (scratchpad).

### Hardening beyond the research's illustrative diff

`p.pos`/`p.ing` are copied rather than aliased (detail 2 above). Stated as a deliberate choice, not
an accident: aliasing would make the scrubber's own history writable through a live player object.

PAR-03 covers three cameras: the **sail-window fit**, the **battle framing**, and the **storm
framing**. All three read `g.players[i].pos` through `camFitSail` / `camFitSeats` / the
`window.__pp4.battle` and `stormCam` hooks, so all three are fixed by the same one change — but
**only the sail-window camera was photographed and measured.** The plan's own truths named that one,
and a battle or storm cut is not something a bounded probe can reliably arrive at without driving far

Stated plainly rather than left implied: the battle and storm cameras are **correct by the same
mechanism**, not **demonstrated**. Worth a deliberate look at the phase gate, alongside the sail
prompt — a battle between two captains far apart is the shot most likely to reveal anything the sail
window would not.
