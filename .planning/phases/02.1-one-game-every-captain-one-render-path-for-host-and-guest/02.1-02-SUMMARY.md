# Phase 02.1 Plan 02: The Coin That Broke Its Own Button — Summary

**`emojify()` was rewriting text it could not see it was inside — an HTML attribute — and the three
double-quotes in the coin's `<img>` tag closed that attribute early, spilling half a sentence into a
button's label and collapsing the whole radial bloom into a flat card. One function now walks tags
and text separately, and the bloom comes back on host and guest alike.**

## Performance

- **Duration:** ~20 min
- **Tasks:** 2 of 2
- **Files modified:** 1 (`4/src/shared/index.js`, +24 −1)
- **Repro route:** the real in-game prompt, not the plan's hand-built fallback

## What the bug actually was, in one picture's worth of words

`panel()` (`4/src/ui/panel.js:435`) runs a **whole assembled button row** through `emojify()` —
every attribute included — before setting `innerHTML`. `emojify()` was a blind whole-string replace,
and `iconImg()` returns:

```html
<img class="narrIcon" src="../assets/icons/coin-emoji.png" alt="">
```

**Three literal double-quotes.** Spliced into an already-correctly-escaped
`data-why="Ye can't afford the powder — 2🌕 a broadside, and yer purse won't stretch."`, the very
first of them closed the attribute. The browser then recovered exactly as RESEARCH §7 predicted
from first principles — and this session watched it happen instead of inferring it:

| | RED (measured live, both tiers) | GREEN |
|---|---|---|
| the button's attributes | `class, data-i, aria-disabled, data-why,` **`narricon", src, alt`** | `class, data-i, aria-disabled, data-why, style` |
| `data-why` | `"Ye can't afford the powder — 2<img class="` — truncated | the whole sentence, coin glyph intact |
| the button's own `textContent` | `"a broadside, and yer purse won't stretch."> Attack (−2)"` — **55 chars** | `"Attack (−2)"` — **11 chars** |
| `#pp4Prompt` | `"centered"` — the flat card | `"radial"` — the bloom |

`menuButtons()` (`4/src/ui/stage.js:1029`) disqualifies a prompt from the radial bloom if **any**
button's label runs past 16 characters. 55 > 16, so the whole prompt fell back — which is the
symptom Wyatt reported. **The escaping was never wrong.** `esc()`/`escW()` did their job; the
corruption happened one step later, inside `emojify()`.

**Identical on host and guest**, byte for byte, because `panel()` is the one sink both `localAsk()`
(`flow.js:250`) and `watchPrompt()` (`orchestrator.js:1346`) render through. One change fixed both.

## The fix

`emojify()` splits on tag boundaries and substitutes only in the text spans between them.
`EMOJIFY_RE`, `EMOJI_IMG` and `iconImg()` are untouched — only **where** they are applied.
`panel.js`'s call site does not change, and the function's contract (HTML string in, HTML string
out) is the same.

Two details taken deliberately:

1. **Index parity decides text vs tag, not `startsWith("<")`.** `split()` with one capture group
   always alternates text, tag, text, tag — so odd indices *are* the tags, exactly. The prefix test
   looks equivalent and is not: a stray never-closed `<` in ordinary prose (`"5 < 3 🌕"`) lands in a
   text segment that begins with `<`, and the prefix test would silently stop swapping its emoji.
2. **The known limitation is named at the fix site**, in the codebase's own convention of stating a
   trade-off rather than hiding it: a literal `>` inside an attribute value would end a tag span
   early. No string this codebase feeds through `emojify()` contains one — checked, not assumed —
   and every `why:`/label is developer-authored, never player-typed. A real HTML tokenizer is
   disproportionate here (threat T-02.1-04, accepted by RESEARCH §7).

## Red-proofed twice — at the string level and in two real browsers

**String level** (`scratchpad/test-emojify-attr-safety.mjs`, three cases). Against the *unfixed*
`emojify()`, case 1 failed with the corrupted output quoted above. Against the fixed one, all three
pass — including the plain-text case (`Ye win 🌕!` → the coin `<img>`), which is the non-regression
guard for the other eight call sites.

**Browser level** (`scratchpad/probe-02.1-02-flatcard.mjs`, md5 `6c024b0504aa1d822ac85b49e91d65db`
for both runs). Two independent headless Chromes, a real Firebase room, host and guest, driven to
the **real** turn menu whose Attack circle is greyed with `flow.js:1760`'s coin-bearing reason.
7 assertions per tier: **10 failing in red, 14 of 14 passing in green.**

The probe reaches that moment the way `docs/DRIVING-THE-GAME.md` §5e prescribes — inject the state,
do not play your way to it — on the **host's authoritative engine only**: every purse set to `0` (so
`!canAfford`, the branch that picks the coin-bearing `why`) and each bot parked on a human's square

path under test. The plan's `panel()` fallback was **not** needed; this is the prompt the shipping
code actually builds.

**23,082 lines scanned, 287 carrying a mapped emoji, ZERO disagreements.** No attribute anywhere in
`4/` holds an emoji today, so nothing could regress.

**The one whole-document difference, and why it is accepted:** `lobby.js:398` sweeps the whole body,
and `<!-- … -->` has no closing `>` until the comment ends — so the tag-aware pass treats a whole
developer note as one span and stops rewriting emoji inside it. `4/index.html` has exactly one such
note (the D-14 mute-button comment, line 2195, *"horn.png already carries the 📯 meaning"*).
**Comments never render, so nothing a player can see changes** — and not rewriting developer prose
into `<img>` markup is the better behaviour anyway. With comments stripped, the two passes are
byte-identical.

## Deviations from Plan

### [Rule 1 — Bug, in my own instrument] An assertion that passed in the RED run

- **Found during:** Task 2, first red run
- **Issue:** the check *"no `<img>` markup spliced into the opening tag"* (`!/narrIcon|<img/`)
  **passed on a fully corrupted button.** The HTML parser lower-cases the junk attribute name it
  recovers (`narricon"`) and re-escapes the leaked `<` back to `&lt;`, so neither pattern matched.
  A check that cannot fail is not protection — CLAUDE.md §4 says so in as many words, and this is
  precisely the trap that let seven faults reach Wyatt on 2026-08-18.
- **Fix:** made it case-insensitive (`!/narricon/i`), and tightened the `showWhy` assertion to
  demand the whole sentence rather than merely a coin. Both then **failed in red**, as they must.
- **Cost:** the red run was repeated with the hardened instrument, so the recorded red/green pair
  is one byte-identical file (`md5 6c024b0504aa1d822ac85b49e91d65db`) on both sides.
- **Scope:** scratchpad only — no repo file changed.

### The browser repro route was the strong one, not the fallback

The plan permitted a hand-built `panel()` call if the real prompt proved impractical to reach. It
did not: forcing `!canAfford` and `targets.length` on the host's engine reaches the genuine
`flow.js:1760` prompt in about forty seconds. **Stated plainly because the plan asked which route
was used: the real one.**

### Nothing else

No architectural change, no auth gate, no package install, no engine change, nothing crossing the
wire. `esc()`/`escW()` were left alone exactly as the plan's prohibitions require — they are
correct, and consolidating them is Plan 03's job.
