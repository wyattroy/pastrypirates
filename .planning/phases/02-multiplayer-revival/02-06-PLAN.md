    Put the guest a few turns into a voyage, snapshot the room, the seat and the host flag, then close
    the guest's **page** while leaving its Chrome process and its profile directory alive — closing the
    process takes localStorage with it and would prove nothing. Open a new page in that same process at
    the same URL, re-attach, and read the same three values back.

    The pass is not only that the values match. It is also that the join screen was never shown: the
    whole point of the synchronous session read is that a returning guest never sees the welcome or
    the code entry at all. Assert that the welcome modal and the join step were never displayed during
    the reconnect, not merely that they are hidden by the time you look — a value read after the fact
    cannot tell "never appeared" from "appeared and went away", and the flash of a welcome screen is
    exactly the "did my game get lost?" moment the code comment says this design exists to prevent.
    Arm a watcher before the reload rather than sampling after it; the window is far narrower than a
    second and cannot be caught by polling after the fact.

    Then let the guest keep playing for a few more turns and confirm it is really back in the game and
    not merely displaying a restored shell — a reconnect that renders correctly but cannot take a turn
    is a failure that a state comparison alone would pass.

    If the room's schema version guard fires and clears the session, that is a finding, not a bug to
    patch here. Record it.
  </action>
