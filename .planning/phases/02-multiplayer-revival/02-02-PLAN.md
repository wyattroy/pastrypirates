  <files>4/src/orchestrator.js, &lt;scratchpad&gt;/probe-fix03-draft.mjs</files>

  <read_first>

      whole callback; the iteration is one line and the shape assumption is the whole bug.
    - `4/src/net/watchers.js` — `netWatchRecipes`, to see exactly what is handed to the callback.
    - `4/src/net/writers.js` — the writer that produces the recipe-pick node, so the real shape is
      read from the producer rather than guessed from the consumer.
    - `docs/HARD-WON-LESSONS.md` §1b — a throw inside the awaited turn chain rejects silently and
      reports zero page errors. This fault is exactly that shape, which is why the probe cannot use
      the page-error stream as its signal.
    - `.planning/phases/02-multiplayer-revival/02-RESEARCH.md` § "The Test Rig" §6 — the wrap-and-read

      Its line numbers have drifted; locate by shape and treat a mismatch as drift, not a new bug.
  </read_first>

  <action>
    Firebase Realtime Database returns a JavaScript array only when the keys are a dense zero-based
    integer run. A draft in progress is by definition sparse — seat 0 and seat 2 have picked, seat 1
    has not — so the node arrives as an object with integer-like keys, and the array method the
    callback calls does not exist on it. The sparse shape is the expected shape, not the edge case,
    which is why this kills every guest on every draft rather than occasionally.

    Rewrite the iteration in `watchRecipes` so it walks whatever Firebase actually returns and applies
    each pick to the seat its key names. Both shapes must work: the object form during the draft and
    the array form once every seat has picked. Preserve the existing per-seat guard that skips a seat
    with no `recipeChoices` yet, and preserve the trailing `updateRecipeBanner()` and the
    render-if-events call exactly as they are — those are not part of the fault.

    Keep it in the orchestration tier. Do not touch `4/src/engine/index.js`, and do not change what
    the writer puts on the wire — the room shape is untouched by this phase, and Phase 3 captures the
    determinism corpus immediately after, so an emission change here costs a one-way re-record.

    Introduce no constant. There is no threshold, retry or cap in the correct fix; if one is appearing,
    the shape of the fix is wrong.

    Write the probe against the guest process from plan 01's rig, using a port neither browser has
    loaded this session. Do not read the page-error stream for the signal — wrap the call under test
    and read its own rejection into a window property, per RESEARCH.md §6. **Prove the probe reproduces
    the crash against the pre-fix code first**, on a stashed or pre-edit copy: a probe that has never
    gone red is not evidence of anything, and all four of this phase's faults sit on code no one has
    ever run.
  </action>

  <read_first>

  <action>
    `startGame` reads the room and immediately reads `numSeats` and `seats` off the result. If the room
    is gone — the host abandoned it, or a probe's teardown removed it, or two clients raced — that read
    returns null and the dereference throws inside an awaited chain, which is the silent-stall shape
    again rather than a clean message.

    The correct guard is not a new invention and must not be written as one. `watchRoom` already
    handles exactly this case: it tests the room read, shows the player the "that game no longer
    exists" message, clears the session, and returns to the home screen. Give `startGame` the same
    treatment against the same condition, reusing the same copy string so the two paths cannot drift
    apart into two different sentences for one situation. If the copy is already a shared `@copy`
    tagged string, reuse the tag rather than the literal.

    Guard the read only. Do not add a retry, a delay, or a re-check — the room is gone, and a captain
    who is told so and returned home is the whole correct behaviour.
  </action>
