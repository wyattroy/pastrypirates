<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| any captain's typed message → every other captain's screen | Free text, unmoderated, rendered into the log and the flash on every client |
| any client → `rooms/<C>/chat` | Every client writes and listens directly; there is no host authority over chat |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-14 | Tampering | Chat text rendered into `#chatLog` and `#pp4ChatFlash` | medium | mitigate | Both go through `escHtml`, the route `appendChatLine` already uses; the flash adds no second escaping path |
| T-02-15 | Denial of Service | A captain spamming chat walls off the board with stacked flashes | medium | mitigate | One flash element replaced by the newest message rather than a stack, instant tap-dismissal at any lifecycle stage, and the existing one-second client-side send guard in `sendChat` |
| T-02-16 | Denial of Service | An enormous message overflowing the flash box | low | mitigate | `sendChat`'s existing 140-character clamp bounds it at the source; no new limit is introduced |
| T-02-01 | Tampering | `rooms/<C>/*` — any client may write any node, chat included | medium | accept | D-01 — `/4` is `noindex,nofollow` with `Disallow: /4/`, and Wyatt is the only player. Rate limiting without auth is not something RTDB rules can do, as `sendChat`'s own comment records. |
| T-02-SC | Tampering | Supply chain — package installs | low | accept | This phase installs zero npm, pip or cargo packages; no package-manager surface, no legitimacy audit to run |
</threat_model>
