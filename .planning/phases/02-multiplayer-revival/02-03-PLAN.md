    **The chip.** The visibility condition in the ribbon tick already carries a pass-and-play term,

    networked mode when it was written. Add the networked term **beside** the existing one, in the

    before it sets the flag, so that the flag's reachability does not depend on the chip's CSS. Whether
    that is a guard inside the handler or a handler that does not attach at all in networked mode is
    yours to choose — state which and why, and choose the one that still behaves correctly if a mode
    changes after `buildStage()` has run.

    Introduce no threshold, delay or cap. This is a boolean about mode, and a number appearing here
    means the shape is wrong.

    D-05 is "verify, do not change." This task writes no production code at all, and a diff under `4/`
    at the end of it is a failure, not a bonus.

    The listener writes the **shared** `paused` node, and it is safe today only because it sits behind
    a gate that requires a solo bot game. Prove that gate holds now that multiplayer is live, in both
    directions: a guest hiding their tab, and the host hiding theirs. Read the shared node before and
    after each transition, and read it from the *other* browser as well as from the one being hidden —
    the whole risk is one player's phone changing something everyone else renders.

    Simulate the hide deliberately rather than hoping for one. Before trusting any reading, confirm the
    tab was genuinely visible to begin with: a CDP-opened tab that is already backgrounded never fires
    `requestAnimationFrame` and clamps timers, so a probe can measure a transition that never happened.
    Check `document.hidden` and `window.outerWidth` first, and record both.

    Also cover the re-show. `/4`'s listener auto-resumes a pause it created itself, and the correctness
    requirement is symmetrical: hiding must not pause anyone else, and re-showing must not resume
    anyone else either.

    If the gate does **not** hold — if the shared node moves — do not fix it here. Stop, record exactly
    what moved and under which transition, and raise it. A loosened gate is the failure this
    requirement exists to prevent, and quietly patching it inside a verification task would hide the
    finding that Phases 4 and 5 are scoped from.
  </action>
