**2. [Rule 6/measurement → relocated fix, resolved by the orchestrator, not this session alone] Item 10's ceiling was in the wrong file — found by measurement, relocated on instruction**
- **Found during:** Task 6's two-tab QA pass, while satisfying the overnight run's explicit instruction to measure a long narration line's hold "the number, not an impression"
- **First attempt (issue):** `4/src/ui/stage.js`'s outer clamp (`Math.max(2550, Math.min(8775, msgHoldMs(msg)*1.5))`) could never bind at 8775 (or the old 6750) because `msgHoldMs()` itself — imported unchanged from `4/src/ui/util.js` — capped its own return value at `HOLD_CEILING_MS = 2000` before the `*1.5` multiplier was even applied. `2000 × 1.5 = 3000`, always below both the old and new outer ceiling. So changing `6750` to `8775` was a correct, literal, harmless edit that had **zero effect on anything a player saw**.
- **First live measurement, not theory:** instrumented both host and guest with a `MutationObserver` on `.pp4Bub` add/remove during a real driven 22-second crew-game window. Longest bubble observed on **both** sides was the storm narration line, holding **3305ms (host) / 3304ms (guest)** — matching `3000ms` (the ceiling-capped `msgHoldMs(msg)*1.5`) plus the fixed ~300ms fade-out tail in `finish()`, to within 1ms of each other. This also positively confirmed the shared scheduler produces identical holds on both tiers.
- **Reported as a measured finding and initially parked** (Rule 4 territory — the real lever was a different constant in a different file than D-10 named, and raising `HOLD_CEILING_MS` directly would affect every hold computation in the game, not only the "long line" case).
- **Resolved from the record by the orchestrator, mid-plan.** D-10's ruling names the *quantity* — "a long narration line stays on screen about two seconds longer than it did — the ceiling only" — not the specific `stage.js` line number the plan's diagnosis pointed at. Only the LEVER's location was wrong. Directed to implement D-10's intent at the ceiling that actually binds, with an explicit stop-condition if the ceiling turned out load-bearing for something un-scopeable (e.g. the shot clock).
- **Blast-radius measurement before touching anything:** `HOLD_CEILING_MS` feeds exactly one function, `msgHoldMs()`, which has exactly two consumers in `4/src/`: `stage.js:643` (the live narration bubble — the only one that actually executes, since `initStage()` sets `window.__pp4` unconditionally at boot) and `panel.js:1305`'s `flash()` fallback (only reached when `window.__pp4` is unset — dead in practice once a game is on screen, but a real second reader). `botMsgHoldMs` is an exported alias with **zero call sites** anywhere in `4/src/` (confirmed dead). `chatBubbleHoldMs` has its own independent formula and clamp (1200/7000) and never reads `HOLD_CEILING_MS`. No shot-clock, prompt, or wait-line consumer exists — the stop-condition did not trigger.
- **The fix:** `msgHoldMs()` gained an optional second parameter (`ceilingMs`), defaulting to the unchanged `HOLD_CEILING_MS` so every existing call site — including `panel.js`'s fallback — behaves byte-identically when the parameter is omitted. Only `stage.js`'s narration-bubble call site passes a new named constant, `NARRATION_HOLD_CEILING_MS = 3330`, back-computed from the first measurement: the old path's longest observed bubble (3305ms) was `round(2000*1.5) + ~300ms fade tail`; solving for a ~5300ms final hold (his "about two seconds longer") gives `round(3330*1.5)+300 = 5295`. `stage.js`'s own outer clamp (8775) is unchanged and confirmed not to re-bind (`3330*1.5=4995` stays well under it).

A standalone formula check confirmed short lines are **byte-identical** with or without the override (both floor-bound at 2550ms) — the "ceiling only" proof.
