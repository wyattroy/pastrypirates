## First, the instrument was broken, and that is the most transferable lesson here

The probe that "confirmed" C tested visibility with `el.offsetParent !== null`.

**`offsetParent` is always `null` for a `position:fixed` element.** `#pp4Pill` is fixed. So that
check reported the wind pill hidden **on the host as well as the guest** — it could not have passed
for anyone, and it would have reported a permanently broken pill in a perfectly healthy game forever.

It was caught only because the result was *too* bad: the host is Wyatt's own working screen, and a
check that condemns the working screen is a check about itself. Had it failed on the guest alone it
would have looked exactly like the bug it was invented to detect.

The corrected predicate measures the painted rectangle (`getBoundingClientRect()` width and height)
plus the computed styles that actually remove a thing from view, and it is **red-proofed both ways**
in every run against two controls with known opposite states: `#pp4FF`, the ⏩ skip chip, which is
hidden by design in a crew game (D-04), and `#pp4Menu`, the ☰, which is always shown. A predicate
that cannot separate those two is not measuring visibility.

> `docs/HARD-WON-LESSONS.md`: *check that a check can FAIL before believing it passing.* This is that
> lesson costing a full evening, in a session that had read the line that morning.

The wind pill's later arrival is **correct on both tiers and is not a defect**: `pillHTML()` returns

**No width rule is involved.** The only media queries in `4/index.html` are `prefers-reduced-motion`,

**Where the false report came from:** a single small screenshot taken while the guest was still

## A — narrowed from "guests miss prompts" to "a battle prompt is lost when a browser is killed"

**What was directly observed in Wyatt's own room BVUR**, not inferred: `rooms/BVUR/prompt` held a
prompt for seat 1; the guest showed no message, no buttons and no sail cells while its driver ticked
past 140 with no error; one `watchPrompt()` call rendered it instantly and the queued turn played
out, advancing the voyage from round 1 to 2.

**The trigger took five runs to isolate, and every wrong turn is worth keeping**, because each was a
different way of fooling yourself with a browser.

| run | scenario | prompt kind | result |
|---|---|---|---|
| 1 | same-browser reload | ask | rendered |
| 2 | fresh browser reclaims seat by `pp_id` | ask | rendered |
| 3 | **browser SIGKILLed** mid-prompt, replacement reclaims | pick (sail) | *"failed"* — **bad check** |
| 4 | same | **ask + battle + flip** | **DREW NOTHING — 40s** |
| 5 | same | pick (sail) | rendered — **18 `.sailCell` rects** |
| 6 | same | ask (action menu) | rendered — 2 buttons |

**The trigger is a browser KILLED while holding the seat** — a graceful reload always recovers. But
runs 5 and 6 then narrowed it much further: after the same kill, a sail window and an action menu
both come back correctly. **Only the battle prompt drew nothing.**

That fits the code. `watchPrompt` renders a battle prompt down a completely separate path —
`renderBattleFromSnap(p.battle)` plus `setFlipActive()`, arming the flippenator coin — rather than
through the button row every other prompt uses. It is also the path 02.1-01 explicitly protected
when it warned *"must not reassign `appState.game.players`… anything already holding a reference
(`renderBattleFromSnap`'s `appState.game.players[snap.attIdx]`) stays valid."*

**Run 3 was a false alarm and is kept as a warning.** It reported a failure because the check looked
only at `apMsg`/`apBtns` — but a `kind:"pick"` sail prompt paints `.sailCell` rects on the BOARD and
legitimately leaves the button row empty. **Third time in one night that a check measured a different
thing than the one that mattered.** The corrected check asks what *this kind* draws: buttons, sail
cells, battle buttons, or an armed coin.

**Delivery is not the problem.** An independent Firebase listener attached to the same node fired
correctly on the replacement guest, with `mySeat:1, gameStarted:true, live:true, hasGame:true,
panelInDom:true, stageBuilt:true`. The prompt arrives. It is the rendering of *that one kind* that
does not happen.

**Confirmation is blocked, honestly.** One observation is not a reproduction. A sixth run hunted
specifically for a battle prompt and found none in five minutes — and battles are rare enough that
**this is the third phase running in which no probe has reached one** (02.1-01 named the battle
camera correct-by-mechanism but unphotographed; 02.1-03's drive saw no battle; Wyatt's gate voyage
saw none). Forcing one via injection is ruled out in multiplayer by DRIVING-THE-GAME.md §5e —
mutating the host desyncs the broadcast against the `dlog`.

**The way through, for 02.2:** §5e's own table says injection is **safe in solo**. Battle *rendering*
can therefore be exercised in a solo game with a forced battle, separately from the kill+reclaim
scenario that needs multiplayer. Splitting the question that way is likely cheaper than waiting for
a battle to occur by chance, and it would finally close D7 as well.

**Do not fix anything from this evidence yet.** One observation, mechanism not confirmed. The next
job is to make a battle summonable; the fix follows the red case, not the other way round.

## B — RESOLVED: correct behaviour. The host is hailed, and the prompt renders in 3.1 seconds.

Wyatt's report: he made no move, then refreshed, and only then saw the guest's trade offer. He
confirmed explicitly that the game was **visible beside his terminal and still running** — so
`DRIVING-THE-GAME.md` §8b's hidden-tab throttling is ruled out, not assumed away.

**Three probes were needed because the first two measured nothing:**

1. The guest's trade walk **oscillated on the coin stepper** (`+1 → −1 → +1 …`) and never pressed a
   committing button, so no offer was ever sent. This is 02.1-01's documented 460-click stall wearing
   different clothes: a remote seat gets `coinStepper()`'s ± fallback, because TRADE-SYSTEM.md §4's
   named exception routes the slider to the **local** prompt path only.
2. The offer sent, but the **host driver was answering prompts every 700ms while the probe polled
   every 2000ms** — racing its own observation. Its reload check was void too: reloading a host
   mid-game returns it to the welcome screen, not into the voyage.
3. `probe-B2.mjs` installs a `MutationObserver` on the host's `#actionPanel` that records every
   button row ever painted, with timestamps, so a prompt answered in 700ms is still in the record.

**Result:** offer sent at a known timestamp; the host painted **7 rows in the entire voyage and 0 in
the 45 seconds after the offer**. At that moment the only prompt on the wire was addressed to
**seat 1, the guest who made the offer** — the asker's own "choose among the answers" step.

**And then the ambiguity dissolved, because the question was the wrong one.** `flow.js:1579`:

```js
for(const q of g.holdersOf(offer.want,p).filter(q=>g.worthReAsking(p,q,offer.want,offer)))
```

`holdersOf` returns only captains **carrying the wanted crate**. In probe B2 the host's hold was
empty, so it was correctly never hailed. "The host painted nothing" was the system working exactly as
designed — you do not hail a captain for a crate they do not have.

`probe-B3.mjs` makes it decisive: play until the host genuinely holds something, ask for *that*, and
spy on `holdersOf` and `worthReAsking` so a filtered host is visible as filtered rather than inferred
from silence. Result:

| step | observed |
|---|---|
| host's hold at round 2 | `["spice"]` |
| guest asks for | Hot Cinnamon (spice) |
| `holdersOf("spice", asker=1)` | `[{idx:0, strategy:"human"}, {idx:3, strategy:"rusher"}]` — **host present** |
| `worthReAsking(asker=1, asked=0)` | **true** — not filtered |
| host's action panel | **+3.1s:** *"Wyargh: Claude offers 1 coins for yer Hot Cinnamon."* — Accept · Ask for summat else · Deny |

**No refresh. No delay worth the name. B does not reproduce.**

(The row is recorded twice, 3.1s apart, once as "Ask for summat else" and once as "Counter" — that
is the radial bloom's `_shortHtml` swap working as designed, not a double paint.)

**Nothing in the trade path was changed**, which turned out to be the right call for a second reason
beyond caution: there was nothing to fix. I1 requires any trade change to report hails-per-game, and
`03a683c` holds that number at ~2.8 a game deliberately — a "fix" here would have damaged a defended
invariant to cure a bug that does not exist.

**What remains genuinely open about Wyatt's experience:** he did have to refresh, and he was
presumably a holder at the time. Chrome-to-Chrome the hail renders live, so the residue is either
Safari-specific or particular to his session. That is one question for a person, not a probe.
