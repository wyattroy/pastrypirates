## First, the instrument was broken, and that is the most transferable lesson here

The probe that "confirmed" C tested visibility with `el.offsetParent !== null`.

**`offsetParent` is always `null` for a `position:fixed` element.** `#pp4Pill` is fixed. So that
check reported the wind pill hidden **on the host as well as the guest** — it could not have passed
for anyone, and it would have reported a permanently broken pill in a perfectly healthy game forever.

It was caught only because the result was *too* bad: the host is Wyatt's own working screen, and a
check that condemns the working screen is a check about itself. Had it failed on the guest alone it
would have looked exactly like the bug it was invented to detect.

The corrected predicate measures the painted rectangle (`getBoundingClientRect()` width and height)
plus the computed styles that actually remove a thing from view, and it is **red-proofed both ways**
in every run against two controls with known opposite states: `#pp4FF`, the ⏩ skip chip, which is
hidden by design in a crew game (D-04), and `#pp4Menu`, the ☰, which is always shown. A predicate
that cannot separate those two is not measuring visibility.

> `docs/HARD-WON-LESSONS.md`: *check that a check can FAIL before believing it passing.* This is that
> lesson costing a full evening, in a session that had read the line that morning.

## C, D, E — measured, and they do not reproduce

`probe-timing.mjs`: two real Chromes against a local server, both tiers sampled every 500ms from the
moment the voyage starts, recording the first sample in which each control is actually painted.

| control | host | guest | gap |
|---|---|---|---|
| ribbon | 505ms, ev=0 | 505ms, ev=0 | **0ms** |
| clock chip | 505ms, ev=0 | 505ms, ev=0 | **0ms** |
| chat bubble | 505ms, ev=0 | 505ms, ev=0 | **0ms** |
| wind pill | 3018ms, ev=1 | 3018ms, ev=1 | **0ms** |

The wind pill's later arrival is **correct on both tiers and is not a defect**: `pillHTML()` returns
an empty string until `appState.game.windNow` exists, and wind first exists when the first event
carries it. There is nothing to draw before that. The guest's `timerOff` arrived at **2ms** — the
`watchTimer()` subscription that every client attaches (`orchestrator.js:1657`) works exactly as
written, which also retires an earlier hypothesis in this session that a guest never learns the
clock setting.

A second run (`probe-red2.mjs`) reached the same conclusion independently at DAY 2, with byte-identical
rects on both tiers: `{w:241,h:28,x:480,y:52}` for the pill on host and guest alike. Screenshot
`shots2/red2-guest.png` shows a guest ribbon carrying **DAY 2 · four boats · ⏱ off · 💬 · ☰** with
`WIND NOW: N↑ · FORECAST: ⛈↓` beneath it.

**No width rule is involved.** The only media queries in `4/index.html` are `prefers-reduced-motion`,
`print`, `max-width:600px` and `max-width:480px`; the guest window was 1100px.

**Where the false report came from:** a single small screenshot taken while the guest was still
behind the opening centre-stage card, read as a permanent absence and reported to Wyatt as a
confirmed defect *before it was measured*. The correct sequence was available and was not used.

## A — real, and the live evidence is strong, but it does not reproduce yet

**What was directly observed in Wyatt's own room BVUR**, not inferred:

- `rooms/BVUR/prompt` held `{seat:1, id:"q2_1787195977632", msg:"What do ye WANT from the table?"}`
- The guest at seat 1 showed **no message, no buttons, no sail cells** — `window.__g.n` was ticking
  past 140 with no error, so the driver was alive and simply had nothing to answer
- Calling `watchPrompt()` once, from the console, made prompts render **immediately** — the queued
  turn played out that second (`Crystal Sugar → coins only → Offer it!`) and the voyage advanced from
  round 1 to 2, events 18 → 27
- With the turn clock off there is nothing to break the resulting deadlock; the host waits forever

**The candidate mechanism**, from `orchestrator.js:1295`:

```js
if(!p || p.seat !== appState.mySeat){ panel(""); setFlipActive(null); … return; }
```

A guest that attaches this watcher before its seat is assigned discards the outstanding prompt, and
Firebase only re-fires a `value` watcher when the value **changes** — so the prompt is never offered
again.

**Three reproduction attempts, all negative:**

1. same-browser reload mid-voyage with a prompt outstanding → prompt rendered
2. fresh browser reclaiming the seat by `pp_id` → prompt rendered (`red2-guest2-reclaimed.png`)
3. same, with a battle call outstanding → prompt rendered

So the guard is not, on its own, sufficient to cause it. **Something about the live sequence is not
being replicated.** The strongest untested difference: in the live session the previous browser was
**killed while still holding the seat**, so the room may have carried a live presence/registry entry
for a client that no longer existed. That is the next thing to try, and it is 02.2's first job.

**Do not "fix" the guard blind.** Re-firing the watcher unconditionally on seat assignment is a
one-line change that would probably work — and would also be a change nobody can prove was needed,
in a file the determinism corpus depends on. Reproduce first.

## B — measured cleanly, and the answer is genuinely ambiguous

Wyatt's report: he made no move, then refreshed, and only then saw the guest's trade offer. He
confirmed explicitly that the game was **visible beside his terminal and still running** — so
`DRIVING-THE-GAME.md` §8b's hidden-tab throttling is ruled out, not assumed away.

**Three probes were needed because the first two measured nothing:**

1. The guest's trade walk **oscillated on the coin stepper** (`+1 → −1 → +1 …`) and never pressed a
   committing button, so no offer was ever sent. This is 02.1-01's documented 460-click stall wearing
   different clothes: a remote seat gets `coinStepper()`'s ± fallback, because TRADE-SYSTEM.md §4's
   named exception routes the slider to the **local** prompt path only.
2. The offer sent, but the **host driver was answering prompts every 700ms while the probe polled
   every 2000ms** — racing its own observation. Its reload check was void too: reloading a host
   mid-game returns it to the welcome screen, not into the voyage.
3. `probe-B2.mjs` installs a `MutationObserver` on the host's `#actionPanel` that records every
   button row ever painted, with timestamps, so a prompt answered in 700ms is still in the record.

**Result:** offer sent at a known timestamp; the host painted **7 rows in the entire voyage and 0 in
the 45 seconds after the offer**. At that moment the only prompt on the wire was addressed to
**seat 1, the guest who made the offer** — the asker's own "choose among the answers" step.

**Two readings, and this session cannot separate them:**

- **(a) Correct behaviour.** `flow.js:1577`: *"Only hail captains for whom something has actually
  changed since they last said no."* TRADE-SYSTEM.md invariant **I1** — *"the announcement IS the
  spam"* — deliberately suppresses hails that cannot go anywhere, and `03a683c` holds hails at
  ~2.8 a game **on purpose**. A host that is legitimately not hailed is the system working.
- **(b) The bug Wyatt hit.** The host was eligible, was asked, and the prompt was never painted.

**Nothing in the trade path was changed tonight, and that is a deliberate call.** I1 requires any
change to trading to report hails-per-game beside whatever else it improves, and CLAUDE.md rule 8
(*read the graveyard*) points straight at a number somebody already defended. Changing hail
eligibility on a coin-flip between (a) and (b) is exactly the settled argument that rule exists to
stop. `docs/TRADE-SYSTEM.md` §9 — *before you change anything here* — says the same thing louder.

**What would separate them, cheaply:** instrument `respondToOffer`'s caller to log which seats were
hailed and which were filtered out, then run the same probe. If the host appears in the filtered
list with a reason, it is (a) and there is no bug. If it appears in the hailed list and painted
nothing, it is (b) and the fix is in the render path, not the trade rules.
