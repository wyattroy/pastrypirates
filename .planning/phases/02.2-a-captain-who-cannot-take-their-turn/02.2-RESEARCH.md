## Per-Question Findings

### Q1 — Item 17, duplicated narration ("Ahoy!" behind the ceremony stage)

**CONFIRMED**, traced end-to-end. `showAhoyIntro()` (`4/src/ui/flow.js:2218-2243`) calls
`netIntroBarrier(msg, btnLabel)` (`4/src/ui/flow.js:2185-2215`), which does BOTH of the following for
the SAME `msg` text, unconditionally:

1. **Line 2187**: `netHandlers().onNetBroadcast(msg)` → resolves to `orchestrator.js:307`
   (`netBroadcast`), which writes the raw text to the room's `narr` node in Firebase. Every GUEST
   subscribes to this via `watchNarr()` (`orchestrator.js:1381-1389`, only attached on the
   `!appState.isHost` branch at `orchestrator.js:1655`), which calls `showNarration()` → a normal
   floating narration bubble.
2. **Lines 2212-2214**: `Promise.all(humans.map(p => seatLocal(p.idx) ? localAsk(...) : netHandlers().onRemoteDraftPrompt(p.idx, msg, opts, waitMsg)))`. For a remote human (any guest), this resolves to
   `remoteDraftPrompt()` (`orchestrator.js:1169-1185`), which writes a SEPARATE Firebase node
   (`draftPrompt`) carrying the SAME `msg` text, plus `stage: opts.some(o=>o.stage) ? 1 : null` (line
   2190 sets `stage:true` on the ahoy option). The guest's `watchDraftPrompt()`
   (`orchestrator.js:1186-1217`) receives this and builds a CENTER-STAGE card
   (`$("actionPanel").dataset.pp4Stage="1"` at line 1192, which routes through `enterCenterStage()` at
   `stage.js:1099-1101`).

**Result on a guest's own browser**: two independent renders of the identical "Ahoy!" text land
simultaneously — a normal narration bubble (from `watchNarr`) and a dimmed, centred ceremony card
(from `watchDraftPrompt`) — with no coordination between the two listeners. This is item 17a exactly:
the bubble renders BEHIND the ceremony overlay (z-index), producing the visible duplicate. Confirmed
further by `remoteDraftPrompt`'s own comment at `orchestrator.js:1172-1173`: *"which is precisely
where Wyatt saw the host get a dimmed centre-stage card and the joining captain get a small pill"* —
an EARLIER symptom of the same underlying two-channel design.

**On the host's own browser**: `netBroadcast()` (unlike `netNarrate()`) does NOT call
`showNarration()` locally — it only writes to Firebase. The host never attaches `watchNarr()`
(`isHost` branch at `orchestrator.js:1654` calls `runLiveNet()` instead). So the host sees only its
own local `localAsk()` ceremony card — no duplication on host. This is a guest-only symptom, which is
consistent with D-03's finding that host/guest divergences are invisible to a single-browser check.

**Fix shape**: `netIntroBarrier` should send the text through exactly ONE channel per client, not two.
Since the `draftPrompt` channel already carries `stage`, `waitMsg`, and per-seat delivery, the simplest
fix is to STOP calling `onNetBroadcast(msg)` at line 2187 entirely for this function (it appears to be
vestigial — a leftover broadcast that nothing besides `watchNarr` needed once the draft-prompt channel
existed) OR to make `watchNarr` skip rendering while a `draftPrompt`/stage card is already showing the
same text. Recommend the first (delete the broadcast call) as the smaller, safer change — but confirm
nothing else depends on that specific `narr` write for this call before removing it (grep `watchNarr`
callers/consumers for anything besides `showNarration`).

### Q2 — Item 19, the wait box fading on a timer

**CONFIRMED**, exact mechanism traced. `showNarration()` (`4/src/ui/panel.js:1020-1023`) routes any
non-empty HTML through `window.__pp4.narr(html)` → `stageFlash(html)` (`4/src/ui/stage.js:526+`) when
the stage is active. `stageFlash` computes a fixed hold at line 578:

```js
const hold = Math.max(2550, Math.min(6750, Math.round((msgHoldMs ? msgHoldMs(msg) : 1700) * 1.5)));
```

and registers a deadline (`S.bubDue = Date.now() + hold`, line 673) with a resolver (`S.bubFinish`,
line 674). The tick loop checks this deadline unconditionally at TWO sites (`stage.js:1506` and
`:1531`): `if (S.bubDue && Date.now() >= S.bubDue){ ...f(); }` — i.e., the bubble is torn down purely
on ELAPSED TIME, with zero connection to whether the underlying wait condition (recipes still being
chosen, mateys still deciding) is still true.

This is used for BOTH the "⚓ Waiting for yer mateys…" line (`flow.js:2211-2213`, inside
`netIntroBarrier`) and the "⚓ Everyone's choosing their recipe…" broadcast (`orchestrator.js:805`,
inside `recipeDraftNet`) — two SEPARATE functions for two SEPARATE moments (ahoy/turn-order dismissal
vs. recipe choosing), both exhibiting the identical pattern CONTEXT's D-06 describes generally, not
one single call site.

**What SHOULD dismiss it, per Wyatt's own words** ("it should disappear when their teammates have
played"): the natural mechanism already exists and requires no new event wiring. `stageFlash` already
retires the PREVIOUS bubble the instant a NEW one is shown (`S.hurry()` call at line 558, "one live
bubble: retire the old one NOW"). If the WAIT message's hold were NOT capped by the normal
`msgHoldMs*1.5` formula — i.e., if it never registered a `S.bubDue` deadline at all — it would sit on
screen exactly until the next real narration line (fired by the actual resolving event: the last
matey finishing their pick, which already triggers the next `showNarration`/`netNarrate` call in the
normal flow) replaces it via `S.hurry()`. **The fix is narrower than "add an event listener"**: give
wait-specific messages a distinct, uncapped/very-long hold (or a `sticky` flag threaded through
`showNarration` → `stageFlash` that skips registering `S.bubDue`/`S.bubFinish` entirely), so dismissal
becomes "replaced by the next real line" rather than "timed out."

**Read before implementing**: `.planning/todos/pending/narration-two-schedulers-unenforced.md` — see
Graveyard section below. This exact area (narration hold/fade scheduling) was explicitly scoped and
deferred twice already, with a recommended approach.

### Q3 — Item 21, the guest's top-bar boats not updating

**CONFIRMED — this is a real, unfixed gap, not "may already be fixed."** Traced end-to-end:

`ribbonTick()` (`4/src/ui/stage.js:401-410`) computes which boat glows "on" (the active-turn
indicator) from:

```js
const act = (S.activeSeat != null) ? S.activeSeat : (appState.curSeat ?? -1);
```

`appState.curSeat` is set ONLY by `setActor(s)` (`4/src/ui/util.js:1740`: `appState.curSeat=s`).
`S.activeSeat` is set ONLY by `window.__pp4.actor(seat)` (`4/src/ui/stage.js:1635`).

**Every call site of `setActor`/`window.__pp4.actor`** (`orchestrator.js:414,600,624,671,799,808`;
`flow.js:290,525,589,1195,1502,1581,1630,1731,1920,1922,2005,2052,2114,2322`) lives inside functions
that only run as part of the **host's own live simulation** (`runLiveNet()` → `takeTurn`/`botTurn`/
`humanTurn`/`ask()` etc.) or a **local `localAsk()`/`botTurn()` invocation on whichever browser owns
that seat**. None of them is reachable from a guest's `watch*` handlers.

The guest's ENTIRE input pipeline is `watchEvents()`, `watchPrompt()`, `watchNarr()`, `watchFlip()`,
`watchBattle()`, `watchDraftPrompt()`, `watchClock()`, `watchTurnOrder()`, `watchRecoveryState()`
(dispatch list at `orchestrator.js:1655`) — **not one of these calls `setActor` or
`window.__pp4.actor`.** `watchEvents()` (`:1219-1291`) explicitly bakes `round`, `wind`, `storm`, and
per-seat `state` (pos/coins/ing/done/baking) onto `appState.game` from each event's snapshot — this is
what fixed PAR-01 (day counter) and the sail camera — but it does **not** bake an "active seat" field,
because the engine's `ev()` (`engine/index.js:316`) never records one; there IS no `actor`/`turn`
field in the event schema. `watchPrompt()` (`:1292+`) only reacts when `p.seat===appState.mySeat` (its
own prompt) — it never updates `S.activeSeat` for prompts addressed to OTHER seats, which is most of
them in a 3-4 player game.

**Consequence**: `ribbonTick()` runs identically on host and guest (shared tick loop, `stage.js:1510`)
and correctly shows the right DAY (fixed by PAR-01/02.1-01), but the "whose turn" boat-glow indicator
in the top ribbon is frozen at whatever `appState.curSeat`'s default (0) was for the entire game, on
every guest, for every seat's turn except possibly momentary flickers from stale local state. This is
item 21 exactly, and it is a genuinely NEW finding this event stream does not currently support —
fixing it needs either (a) a new lightweight field on events (`o.actor` or similar, baked at `ev()`
time — an ENGINE emission change, flag per the phase's hard constraint) or (b) a UI-tier inference: a
guest could derive "whose turn" from whichever seat the most recent non-`newround`/`end` event's `p`
field names, without any engine change, since every meaningful event (`turn`, `sail`, `dock`, `pass`,
`attack`, etc.) already carries a `p:seat` field per `ev()`'s call sites. **Recommend (b) — UI-tier
only**: in `watchEvents()`, read `e.p` (when present) and call `window.__pp4.actor(e.p)` /
`appState.curSeat = e.p`, mirroring what `setActor` already does on the host. This needs no engine
change and no new wire field.

### Q4 — Item 7, is the count wrong or only the wording?

**CONFIRMED mechanism; the root-cause characterization needs Wyatt, not more code-reading.**

`board.js:1935` reads `appState.game.finishOrder.length`. Under the ACTIVE ruleset (`cfg.bakeoff:
true`, confirmed via `roundCfg()`'s `bakeoff: bakeoffEnabled()` and the whole `runLiveDayBakeoff`
driver that this codebase actually runs — see `orchestrator.js:871-889`), `finishOrder` is populated
**only** by `endBakeDay()` (`engine/index.js:2857-2862`):

```js
endBakeDay(){
  const won=this.players.filter(q=>q.bakedToday);
  for(const q of won){ q.done=true;q.baking=false;this.finishOrder.push(q.idx); }
  ...
}
```

— i.e., a captain joins `finishOrder` only once they have **successfully completed a bake**, not when
they merely arrive/dock at Tortuga or begin baking. Arrival alone sets `p.baking=true` via
`lightOvens()` (`engine/index.js:2770-2771`, `canBake(p)`), which is a DIFFERENT flag from `done`.

(There is a separate, OLDER `checkFinish()` method at `engine/index.js:2863-2868` that DOES push to
`finishOrder` on mere arrival with a complete recipe — but it belongs to `runLiveDayClassic()`, the
CLASSIC/pre-bake-off ruleset, called only when `!cfg.bakeoff`. It is not the path Wyatt's game runs.)

So `finishOrder.length===1` with three captains visibly "home" is **not a scoring bug** —
`finishOrder` is doing exactly what its name and every downstream reader (`bakeRank`,
`eligibleFinishers`, `resolveEnd`) expects: counting **finished bakes**. The mismatch is between that
quantity and what the "Bakery" stat row implies it's showing. There is no existing per-player boolean
already surfaced for "currently at Tortuga / baking" as a table stat — it would need to be newly
computed from `p.baking || p.done` at render time (UI-tier only, zero engine change, since `baking`
and `done` are both already-tracked player fields carried in every event's `state` snapshot per
`ev()`'s `o.state` construction at `engine/index.js` — see `Q3`'s citation of the same mechanism).

**This is now a precise, answerable question for Wyatt**, not an open-ended "measure before fixing":
does he want the stat to show (a) captains who have **finished** baking (today's correct-by-design
`finishOrder.length`, needing only a clearer label), or (b) captains who are **currently at Tortuga**
(arrived and/or baking, a NEW count derived from `p.baking||p.done`, small UI-tier addition)? His own
"3 bakers home" wording (D-12) reads like (b).

### Q5 — Item 4, the bot that passes AND bakes

**CONFIRMED, exact mechanism, in TWO separate code sites that must both be fixed.**

`lightOvens(p)` (`engine/index.js:2770-2771`) fires **unconditionally** whenever
`cfg.bakeoff && !p.baking && !p.done && canBake(p)` — i.e., regardless of what action the captain took
that turn. It is called once per captain, every turn, from the day-loop driver right after that
captain's turn resolves (`orchestrator.js:889`, inside `runLiveDayBakeoff`, and the engine's own
headless day driver).

For a **human**, `flow.js` explicitly prevents the collision: `canOvens =
appState.game.cfg.bakeoff && appState.game.canBake(p)` (`flow.js:1795`) — when true, the menu shows
"🍰 Fire up the ovens!" (`:1797`) and the Pass button is **suppressed entirely**:
`if(!canOvens) opts.push({label:"🌊 Pass..."})` (`:1832`). A human physically cannot collect the pass
dubloon on the same turn they become bake-eligible.

For a **bot**, there is no equivalent guard, in either of the two places a bot's turn is decided:

1. **Headless engine path** — `takeTurn(p, windDir, storm)` (`engine/index.js:2704-2743`). Its
   fallback, reached whenever `chooseAction`'s plan doesn't resolve to attack/trade/dock: `if
   (fallbackPort && ...) return; this.doPass(p);` (line 2742) — **no `canBake(p)` check at all.** If a
   bot arrives home with a full recipe and nothing else worth doing this turn (the common case), this
   fallback fires `doPass(p)` (paying the dubloon), and the calling day-loop's `lightOvens(p)` fires
   immediately after, in the same turn.
2. **Live-animated UI path** — `botTurn(p)` (`4/src/ui/flow.js:2113-2172`), which the comment at
   `flow.js:2159-2162` explicitly says exists because *"botTurn does not call Game.takeTurn — it
   reimplements the turn so each step can animate... A fallback added only to the engine would fix the
   simulator and leave every real browser game exactly as broken, which is the opposite of the point."*
   Its own fallback ends identically: `g.doPass(p); await botBeat();` (line 2170) — **also no
   `canBake(p)` check.** This is the path a REAL multiplayer game actually calls for a bot's turn.

**Fix**: add a `canBake(p)`-style guard mirroring `flow.js:1795`'s `canOvens` before EACH `doPass(p)`
call — at `engine/index.js:2742` and at `flow.js:2170` — so a bot that is bake-eligible ends its turn
silently (ovens light via the unconditional `lightOvens()` call the day-loop already makes) rather
than also passing.

**Engine-emission flag, as CONTEXT anticipated**: the `engine/index.js:2742` guard changes what
`takeTurn()` emits — a `{t:"pass"}` event that fires today in this exact scenario would no longer
fire. This is used by the headless simulator (`bot_ladder4.js`) and any determinism replay. Per
CONTEXT/`docs/DETERMINISM-RERECORD.md`, the corpus does not exist yet (captured in Phase 3), so this
costs nothing today — but it must be called out explicitly to the planner as an engine-tier change,
not a pure UI-tier fix. The `flow.js:2170` half is pure UI-tier and carries no such cost by itself,
but per the comment at `flow.js:2159-2162`, fixing ONLY the engine half "leaves every real browser
game exactly as broken" — **both sites must land together.**

### Q8 — Item 22, the desktop aspect-ratio stopgap

**CANDIDATE, well-grounded.** `4/index.html` has exactly two breakpoints (`max-width:600px` at
`:1159`, `max-width:480px` at `:1165`) — no `min-width` query exists anywhere, confirmed by grep.

funnels through these two helpers by explicit design ("Every box on this stage is laid out from the
LAYOUT viewport... never window.innerWidth/innerHeight").

reversible stopgap possible. Wrap the stage in one new fixed-max-width, centered container above a new
breakpoint (e.g. `@media (min-width:620px){ #pp4Stage-or-equivalent{ max-width:480px; margin:0 auto; }
}` — confirm the actual outermost stage wrapper element id before writing this), and change
`vwPx()`/`vhPx()` to measure THAT container's `getBoundingClientRect()` instead of
`document.documentElement` when it exists (falling back to today's behavior otherwise — a zero-risk
default). Because everything (ribbon, camera, prompt placement, bubble placement) already reads
`vwPx()`/`vhPx()` rather than the raw viewport, this ONE change point propagates everywhere with no
widespread renderer edits. **To revert in Phase 8**: delete the new CSS rule and the container-measure
branch in `vwPx()`/`vhPx()` — both are additive, not destructive, to existing code. Not verified live
this session (no browser probe run); this is a code-reading-derived recommendation, not a measured
