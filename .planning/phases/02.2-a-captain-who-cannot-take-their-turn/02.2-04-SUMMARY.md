# Phase 02.2 Plan 04: Group C (the bot that passes AND bakes) Summary

**A bake-eligible bot now bakes instead of passing, at both the engine's headless fallback and the browser's animated botTurn fallback — the same `canBake(p)` the human menu already uses, guarding both, proven by a red-proofed event-stream check (99 violations pre-fix, 0 post-fix across 60 seeded games) and by a live, screenshotted solo session; live at `2026-08-20q`.**

## Accomplishments

- **Task 1 — the guard, in both places.** Added `if(this.cfg.bakeoff&&this.canBake(p))return;` immediately before `this.doPass(p)` in `4/src/engine/index.js`'s `takeTurn()` fallback, and the identical `if(g.cfg.bakeoff&&g.canBake(p))return;` before `g.doPass(p)` in `4/src/ui/flow.js`'s `botTurn()` fallback. Both reuse the engine's own `canBake(p)` — the same predicate `flow.js:1857`'s `canOvens` already calls to suppress the human's Pass button and show "Fire up the ovens!" instead. Ending the turn silently at that point is enough: `lightOvens(p)` still fires unconditionally right after, from both the headless day loop (`playBakeoff():2947`) and the live orchestrator (`runLiveDayBakeoff:934`) — exactly as it already does for a human whose turn ended on the ovens button. `4/src/engine/index.js`'s `no_undef_check`, `pass_coin_test`, `pass_narration_test`, and `planner_singleton_check` all green; RULE-01 (passing pays a dubloon) still holds for every ordinary case — only the bake-eligible fallback turn is affected.
- **Task 2 — the automated proof.** Wrote `4/scripts/bot_bake_pass_check.js`, the roadmap's own literal success criterion ("a bot never passes and bakes in the same turn, proven from an event stream"), which no prior check in this codebase could satisfy. Plays a range of seeds through the engine's own headless `play()` (construction copied from `scripts/bot_ladder4.js`), reads only the already-recorded event stream, segments it by `{t:"turn"}` markers, and fails if any single captain's turn segment carries both a `pass` and an `ovens` event. **Red-proofed before being believed:** checked out the parent commit's pre-fix `4/src/engine/index.js` and `4/src/ui/flow.js`, ran the check — **99 violations across 60 games, exit 1** — restored the fix, re-ran — **0 violations, exit 0**. ~12 seconds for 60 games, fast enough to run beside the other `4/` gates. The held-out seed family is never written as a literal in the file (verified by the plan's own regex assertion).
- **Task 3 — the drop, both measured and shown.** Ran a real two-tab crew game (host + guest, real Firebase room), drove it for ~60 real seconds, screenshotted both sides mid-game: identical event counts, identical board positions, correct per-viewer narration pronoun, correct D-26 own-captain-on-top ordering — no new divergence from this plan's changes. Separately, since natural multiplayer play could not reach a full recipe in a bounded window and state injection is forbidden in multiplayer, ran a **solo** session and injected one bot seat's hold to its own recipe (DRIVING-THE-GAME.md §5e), then drove the day loop live: the bot's full event sequence across the voyage was `turn,sail,pass` (not yet home-adjacent — correctly passed, matching what a human's `canOvens` gate would also do at that exact position) → `turn,sail,dock` (still not adjacent) → `turn,sail,ovens` (now adjacent with an empty hold — enrolled to bake, **zero** pass in that turn's segment). Purse held at 8 coins across the baking turn. Live screenshot confirms: *"Crustbeard reaches Tort[uga]"*, purse **8**, matching the instrumented snapshot exactly. All ten named `4/` gates green. `PP4_STAMP` bumped `2026-08-20p` → `2026-08-20q`. See `key-decisions` in frontmatter for the full reasoning on each. In one line each:

- **The guard is `canBake(p)`, nothing else** — no constant, no threshold, reusing the human menu's own predicate at both bot sites.
- **The engine-emission change is disclosed, not hidden** — flagged in the commit, this summary, and the drop message; costs nothing today because Phase 3 has not recorded the determinism corpus yet.
- **The proof script instruments nothing new** — reads the already-recorded stream, same technique `bot_ladder4.js` already uses.

- **The required two-tab screenshot proves parity, not a bake** — multiplayer injection is forbidden, so it serves its usual D-03 purpose instead.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug, found during Task 1's own verification] The added comment broke an existing gate's fixed-width anchor window**
- **Found during:** Task 1, running `4/scripts/pass_coin_test.js` immediately after the first draft of the `botTurn` fallback guard
- **Issue:** `pass_coin_test.js` locates the "animated bot fallback calls the shared method" region by taking a **fixed 500-character slice** starting at the `"v2 rule 3: no fishing"` comment. The first draft of the fix inserted ~700 characters of new explanatory comment between that anchor and `g.doPass(p)`, pushing the actual call outside the scanned window — the gate then read a slice that never reached `doPass(`, and failed with `got=false want=true`, correctly, since the check has no way to know a legitimate call sits just past its window.
- **Fix:** Reordered rather than trimmed the explanation to near-nothing: the new `canBake(p)` guard and its full comment now sit **before** the `"v2 rule 3: no fishing"` anchor (which is untouched, word-for-word), and the anchor-to-`doPass(` distance is back within the same ~350-character budget the pre-existing comment always used. No information was lost — the explanation is simply placed first, since the guard executes before the pass call it's explaining anyway.
- **Files modified:** `4/src/ui/flow.js`
- **Verification:** `node 4/scripts/pass_coin_test.js` — full suite green, "the animated bot fallback calls the shared method" reports `got=true want=true`, anchored correctly at `flow.js:2245`.
- **Committed in:** `4fa58e4` (part of Task 1's commit — caught and fixed before that commit was made, not a follow-up)

**2. [Rule 1 — Bug, found during Task 2's own verification] The check's own explanatory comment tripped its own held-out-seed-family assertion**
- **Found during:** Task 2, running the plan's second verify assertion (the regex that greps the new file for the held-out seed literal)
- **Issue:** The header comment explaining *why* the held-out family must stay out of a routine gate spelled the literal digit string out in prose, which is exactly the pattern the assertion greps for — the check would have failed a real audit for the wrong reason (an explanation, not a violation).
- **Fix:** Rewrote the two references to describe the held-out family by pointing at `scripts/bot_ladder4.js` (which does carry the literal, deliberately, as the tool that documents it) rather than repeating the digit string itself.
- **Files modified:** `4/scripts/bot_bake_pass_check.js`
- **Verification:** re-ran the plan's own regex assertion — passes; `bot_bake_pass_check.js` itself still green.
- **Committed in:** `9ddd865` (part of Task 2's commit — caught and fixed before that commit was made)
