## The headline finding: a captain who cannot take their turn

**Severity: breaks gameplay. Confirmed, not "observed once" — measured via live engine state, DOM,
and a direct escape-path test, and independently reproduced in two separate voyages.**

A captain who has **zero coins AND an empty hold** gets hailed into a trade and asked *"What will ye
GIVE for [item]?"* The give-prompt renders exactly **one button**, and it is disabled:

> `— coins only —` (`aria-disabled="true"`, `data-why="Yer purse is empty — ye've no coin to offer,
> so it must be a crate."`), with the italic subtext *"Ye don't have any coin to offer — pick a crate
> instead."*

There is no crate to pick (the hold is empty), so the game's own instruction is impossible to follow,
and no other control is offered. Clicking the corner **"‹" Back** button does not escape it — the
prompt re-renders (`data-reveal-seq` increments) with **identical content**, confirmed by a direct
before/after DOM diff. The captain — and, since the whole table waits on them, **the whole voyage** —
is stuck permanently.

**Reproduced twice, independently, in different game states:**

| Voyage | Seat | Coins | Hold | Round when it hit | Screenshot |
|---|---|---|---|---|---|
| Two-window crew (guest) | seat 1 ("Blackbeard") | 0 | `[]` | Day 7, 101 events | `q-final-crew-STALL-guest.png` |
| Pass-and-play | seat 1 ("Blackbeard") | 0 | `[]` | Day 2, 23 events | `q-final-pnp-STALL.png` |

Both voyages sat completely motionless (event count and day both flat) for 9+ minutes of continuous
autoplay-driving before I stopped to diagnose — this is not a slow turn, it is a dead end.

**Corroborated from the HOST's own screen** (not just the stuck client) — `q-final-crew-STALL-host.png`
shows the host passively waiting on *"Blackbeard is deciding…"* with Blackbeard's row in the CAPTAINS
panel reading `0` coins / `empty hold`, proving the whole table is blocked, not just the guest's
rendering.

**Back-button escape test**, run directly against the live guest client:

```
BEFORE: data-reveal-seq="40"  "What will ye GIVE for Toasty Wheat?"  [— coins only — (disabled)]
  → click .apBack ("‹")
AFTER:  data-reveal-seq="42"  "What will ye GIVE for Toasty Wheat?"  [— coins only — (disabled)]
```
Screenshot: `q-final-crew-STALL-guest-after-back-click.png`.

**Likely code path** (read, not modified — I did not attempt a fix per the QA brief):
`4/src/ui/flow.js:1589-1601`, `humanTrade()` step 1. `ingOpts` is built from `[...new
Set(p.ing)].map(...)` — if `p.ing` is empty this is an empty array, then the code pushes only the
"coins only" option (disabled when `p.coins===0`) and a Back option. The Back option *should* return
to step 0 (`if(baseIng==="__back__"){step=0;continue;}`, line 1599), but empirically it comes back to
the exact same give-prompt — consistent with step 0's `g.ings.map(...)` "want" list having exactly one
enabled item (the game may auto-resolve a single-choice prompt), which would silently cycle the
captain right back into the same dead end. **I have not fully traced this mechanism — the escape-path
failure is measured; the auto-resolve theory of *why* is a read of the code, not proven.**

## RESOLVED (2026-08-21) — the trade dead end

Full investigation, fix, and verification: `.planning/debug/resolved/captain-cannot-take-turn.md`.
Unattended overnight run per the dispatching brief; self-verified (not yet confirmed by Wyatt
playing it — see below).

**Pre-existence verdict: PRE-EXISTING, not a regression from this QA pass or from any of tonight's
other work.** `canTrade` (the defective gate) has been unchanged since 511c427 (2026-08-11, the
/4 redesign's very first commit) — confirmed by diffing `4/src/ui/flow.js` at `e58fda4` (the
commit immediately before this QA doc) against the working tree; the defect was present, byte for
byte, at both points. Tonight's QA pass didn't cause it — it was the first pass deep enough (two
voyages reaching real broke-and-empty-hold states) to hit it.

**Root cause:** `4/src/ui/flow.js`'s Trade action-menu gate (`canTrade`, then :1811) checked only
whether an OPPONENT held cargo — never whether the acting captain had anything at all to offer.
A captain with 0 coins and an empty hold could therefore click an enabled Trade button and enter
`humanTrade()`, whose "what will ye GIVE" step is built purely from that captain's own
coins/hold — independent of what they chose to WANT — so it was guaranteed unsatisfiable, and
Back only returned to the WANT step (which can't fix a GIVE-side problem), producing an
unbreakable cycle. Bots were never affected: `engine/index.js`'s `composeOffer` already declines
to hail when it has nothing to offer (`if(!giveIng&&!giveCoins)return null`) — this was a
human/bot parity gap (rule 13), not an intentional asymmetry.

**Fix (UI tier only, `4/src/engine/` untouched):** the Trade button gate now also requires
`p.coins>0||p.ing.length>0` (`canOffer`), following the exact pattern already used for Attack's
own independent affordability leg (same D-41 grey-button-with-reason family) — so a broke captain
now sees a correctly GREYED Trade button with a stated reason instead of an impossible prompt.
Two more layers of defense in depth, matching patterns already in this file: a redundant
action-guard in `humanAct`'s trade branch (mirrors Attack's existing `#5d` safety net), and a
symmetric top-of-function decline inside `humanTrade()` itself for any future caller (mirrors the
function's own existing step-0 `!anyHeld` guard). No new constants, no engine changes, no
`@copy`-only edits without house-style wording.

**Not the same fault-family as `flee-not-offered-when-broke`** (read before touching this): that
ruling is Wyatt's deliberate, FREQUENCY-based exception (double-tails recurs many times per
battle, so the flee option silently vanishing with no greyed button and no reason is correct and
must stay that way). This trade dead end is the opposite shape — a once-per-turn decision, already
a member of the D-41 grey+reason family, and a genuine total softlock (the whole table waits),
not a repeated nag. The flee ruling was read, confirmed unrelated, and left untouched.

**Verification:** live browser repro reproduced the exact dead end before the fix and confirmed
gone after it (fresh Chrome/server each time, module-cache-safe); `humanTrade()` on a broke
captain now returns `false` cleanly instead of dead-ending; all five gates green (root `npm test`,
`prompt_field_parity_check.js`, `audio_map_check.js`, `bot_bake_pass_check.js`,
`host_guest_parity_check.js --tree=4 --strict` — exactly the three documented reds, nothing new);
and — most direct — both of tonight's two stalled voyage modes were re-driven end to end on the
fixed build. The two-window crew voyage literally reproduced "Blackbeard is deciding..." with
Blackbeard's row reading `empty hold` on the host's own CAPTAINS panel (screenshotted), the exact
scenario that stalled it originally, and sailed straight through to a complete 14-day, 235-event
finish with 5 trades struck. Pass-and-play ran 17 days, 300 events, 23 trades struck (well past
the original Day-2 stall), to a clean end-of-voyage card. Full detail, screenshots, and gate output
in the debug session file.
