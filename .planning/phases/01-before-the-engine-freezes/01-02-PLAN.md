<objective>
Stop the development build from harming the live game.

`4/src/ui/stage.js:1478` writes the shared, un-namespaced turn-clock key. The live game reads it at
`src/orchestrator.js:1399` and pushes it to the whole room at `:1404`. So a player who opens
`playpastrypirates.com/4` has the clock switched off in the game real players play, and a host who
visited it pushes that setting to everyone in their room.

Purpose: this is the only requirement in the phase that affects real players today, and it is
independent of every promotion decision — it waits for nothing (D-01 through D-04).

Output: the per-game key at all five `4/`-side sites; a one-time, marker-guarded deletion of the
legacy key; and `4/scripts/pp4_timeroff_check.js` gating both the source shape and the runtime
behaviour.
</objective>

<assumption_delta_decision>
**Primary noun:** the turn-clock preference storage key.

**The transition:** one key shared by two co-hosted games becomes a per-game key, under the standing
rule Wyatt set on 2026-08-18 — *"share who you are, split how you play"* (D-04).

**Decision: `promote`.** The per-game key `pp4_timerOff` becomes primary, and the shared legacy key
is **deleted**, not left alongside. D-01 states this in exactly those terms: *"Not migrate, not
leave."* That is the promote-over-add-alongside move, and it is already the chosen approach — the
add-alongside alternative (write both keys, read the new one, leave the old) would keep the leak
alive for as long as any live-game session reads the shared key.

**Rationale:** decided by Wyatt on 2026-08-18. **Recorded here; do not re-ask him.** The blast radius
is small and known — `/4` is `Disallow: /4/` in `robots.txt:8` and `noindex, nofollow` at
`4/index.html:10`, so the only browsers carrying a `/4`-planted legacy key belong to people Wyatt
personally sent the link to, and both affected populations recover with one tap of the existing
toggle.

**Standing consequence:** D-04 answers every future storage key without asking again — identity is
shared, behaviour is split — and it survives the Phase 6 cutover, where the promoted game and
`/classic` still share one origin and want opposite clock defaults.

**Non-transition, for the record:** an earlier discussion framing claimed "five more localStorage
keys leak the same way." That was wrong — it grepped what `4/` writes without checking what the live
game reads. Only the turn-clock key leaks. `pp_rematch` and `pp_seaIdx` are `4/`-only and the live
game has no `SEA_CREATURES` list at all. Do not re-derive this.
</assumption_delta_decision>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-03 | Tampering | shared localStorage key across two co-hosted apps | medium | mitigate | Non-adversarial, same-origin, same-developer collision — one app silently overwrites the other's user preference, and the host then pushes it to a whole room. Mitigated by per-app key namespacing (`pp4_` prefix) at all five write/read sites, which is exactly the standard control for this pattern and already the chosen approach (D-01). Gated by `4/scripts/pp4_timeroff_check.js`. |
| T-01-04 | Tampering | the one-time cleanup, if it were unguarded | medium | mitigate | An unguarded cleanup would re-commit the same cross-app tampering from the opposite direction, deleting the live game's preference on every `/4` visit. No mitigation warranted. |
| T-01-SC | Tampering | npm/pip/cargo installs | n/a | accept | This plan installs zero packages. `package.json` declares no `dependencies` or `devDependencies` and this project has no build step. No supply-chain surface. |
