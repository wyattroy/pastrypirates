<objective>
Fix the Safari storm frame-rate collapse (BUG-01) by making the narration reveal cheap, and ship the temporary instrumentation Wyatt needs to confirm it on his own machine (D-09).

`typewriterReveal()` (around index.html:3120) writes to a live text node **once per revealed character** via `n.nodeValue += u.ch`, every 16-32ms, and its `while(revealed<target)` catch-up loop means several separate DOM writes land in a single tick when the machine is under load. On its own that is a mild, well-understood cost. It becomes crash-level only while a storm is active, because the storm overlay is four `filter:blur()` + animated `mask-image` layers whose `rainFall` animation runs **only** while `.storming` is applied — with no storm those layers are paused or absent, so there is nothing expensive nearby for an unrelated layout-invalidating write to force WebKit to re-evaluate. That asymmetry is exactly what Wyatt observed: zero frame drops without a storm, near-crash with one. Any candidate fix that does not explain the asymmetry is the wrong fix.

Purpose: cut DOM mutation volume per tick without touching the storm CSS, without special-casing storms, and without altering the promise contract the turn loop depends on.

Output: a batched reveal and a strippable dev overlay.
</objective>

  Rewrite `typewriterReveal()` per 01-RESEARCH.md §Pattern 1, which is already grounded against the current source and preserves the exact promise and pacing contract. Structure of the change:

  During the tree walk, keep one record per text node holding the node, its full original text, and a revealed count — instead of pushing one `{node, ch}` unit per character. Keep pushing one entry per character into the flat pacing array so timing arithmetic is untouched, but have each entry reference its owning node record rather than carrying a character. `<img>` units stay exactly as they are.

<risks>
**Determinism / lockstep exposure:** LOW — the lowest of any plan in this phase. `typewriterReveal()` is a pure client-side DOM animation with no engine, network, or RNG involvement; 01-RESEARCH.md's responsibility map classifies it as browser-client-only. The dev block consumes no randomness and never touches the `Game` instance.

The one real lockstep exposure is indirect and serious: `flash()` awaits `_revealDone`, and the bot-turn loop awaits `flash()`. A rewrite that resolves the promise early makes narration race ahead of the moves it describes; one that never resolves hangs the loop outright. Both are host-side pacing failures that would show up in multiplayer as the host appearing stuck. This is why the promise contract is pinned in `<behavior>`, asserted structurally, and checked by playing a full solo game rather than only eyeballing a single line of narration.

**Named uncertainty:** 01-RESEARCH.md Assumption A1 — the WebKit compositing-overlap explanation for the storm-only asymmetry is a well-reasoned hypothesis, not a profiled fact. The batched write is independently justified as a real DOM-mutation reduction regardless of whether A1 is correct, but it may not fully close the gap to "acceptable frame rate." Task 2 requires measuring and recording the outcome honestly instead of assuming success. If it falls short, the correct next move is a new finding in the summary and a scoped follow-up, not an unplanned excursion into the storm CSS that D-02 forbids.

**Phase 3 collision:** NARR-05 changes `REVEAL_MS_PER_CHAR` in the same few lines. This plan must not touch that constant; the summary should note the rewritten function's shape so Phase 3 can retune the constant without re-reading the whole region.
