Detecting it (01-01) is not enough; the host needs a way out that does not destroy the voyage, and the guests need to not be abandoned mid-turn.

<risks>
**Determinism / lockstep exposure:** MEDIUM — the highest of any plan in this phase. This plan edits `resumeHostGame()` and the `endReplay()` failure branch, the exact machinery `CONCERNS.md` flags under "Replay Mechanism Complexity" and the ROADMAP names as Phase 1's principal risk.

Specific exposures and how they are contained:
- **Double-broadcast during fast-forward.** New render/broadcast work inside the replay path must respect `if(replaying)return;`. Task 3 explicitly checks this for the guest watcher; task 2 keeps `endReplay()` free of new `await`s so the replay-to-live handoff cannot interleave.
- **Duplicate guest events after Resume anyway.** The `evPushed` clamp intentionally allows re-pushing events guests already rendered. Guests render from `child_added`, so a repeat is visible as a duplicate narration line — verify this in the two-tab check and record what was observed. Duplicates are acceptable; silence is not.
- **RNG untouched.** No task here consumes randomness or reorders decision consumption from `dlog`, so the mulberry32 sequence and lockstep between host and guest are unaffected on the healthy path.
- **Watcher leak.** `watchRecoveryState()` adds one more never-`.off()`'d listener to a known-leaky set. Accepted deliberately — the cleanup pass is a deferred idea in `01-CONTEXT.md`, and fixing one watcher while leaving eight others would obscure the real debt.

**Residual risk:** the failure path is exercised rarely and only reproducible by deliberately corrupting Firebase state. The manual reproduction in the human-checks is the only real coverage it gets; the automated gates prove structure, not behaviour.
</risks>
