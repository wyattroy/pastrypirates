<task type="checkpoint:human-verify" gate="blocking">
  <precondition>A local static server is serving the repo root over HTTP and the Firebase Realtime Database console is open on this project — both BUG-02/03/04 checks require a live room, and the BUG-03 failure path requires manually truncating the `dlog` node.</precondition>

  <what-built>
  Four fixes across `index.html`, all landed and passing their automated gates:
  - **BUG-01** — `typewriterReveal()` now performs one `nodeValue` write per text node per tick instead of one per character, cutting DOM mutation volume during narration. Storm CSS untouched, no storm special-casing, typing pace unchanged. A dev frame-rate readout and force-storm affordance are available behind a URL gate (parameter name and sentinel strings are in `01-04-SUMMARY.md`).
  - **BUG-02** — `rearmShotClock()` re-arms the current turn's clock with a fresh 30 seconds on an off→on timer toggle, without resetting the already-fired penalty ledger, and the 30-second auto-skip safety net survives the toggle. No pause button was added.
  - **BUG-03** — `resumeHostGame()` no longer swallows its Firebase read failures, and an incomplete replay now opens a "couldn't fully restore this voyage" dialog with Resume anyway / Restart instead of silently handing back a fresh board.
  - **BUG-04** — `endReplay()` no longer pins `evPushed` past what the replay actually rebuilt, so guests keep receiving events after a recovery instead of going permanently silent. Guests also see an explanatory strip during a failed host restore.
  </what-built>

  <how-to-verify>
  **Setup.** Serve the repo root over HTTP and keep the server running for the whole session. Open two Chrome tabs for the multiplayer checks. Known gotcha (D-10): both tabs share `localStorage`, so they will collide on the same `pp_id` — use a second profile or an incognito window for the guest seat, or clear/override `pp_id` in the guest tab, otherwise the two tabs fight over one identity and the results are meaningless.

  ---

  **A. BUG-01 — Safari storm frame rate**

  1. Open the game in **Safari** with the dev parameter appended to the URL.
  2. Enable the frame-rate readout, start a game, and note the steady-state fps and frame time with **no storm** active. This is the control — Wyatt's original report was zero frame drops without a storm, so if this number is already bad, something else is wrong.
  3. Force a storm with the dev affordance and let narration play through several lines.
  4. **Expected:** the frame rate during the storm stays close to the no-storm control, with no visible hitch or stall. Compare against the baseline numbers recorded in `01-04-SUMMARY.md`.
  5. Confirm the rain overlay looks exactly as it did before (D-02) and that narration still types out character by character during the storm at the same pace as outside one (D-01, D-03).
  6. Repeat in **Chrome** to confirm no cross-browser regression.

  ---

  **B. BUG-02 — timer off→on, the canonical sequence**

  Run Wyatt's original sequence exactly (`01-VALIDATION.md` §Canonical Reproduction Script):

  7. Two human players in a multiplayer room, two tabs.
  8. Wait for the **non-host** player's turn.
  9. Let the clock count 20 → 0 and enter the final 10-second range. Let the 20-second penalty fire — note which player lost the coin and that it was narrated.
  10. Host toggles the ⏱ timer **off**.
  11. Host toggles the ⏱ timer **back on**.
  12. **Expected:** the guest can still click and act; the clock shows a **fresh 30 seconds**; the already-lost coin is **not** returned (D-06); and **no second penalty** fires for the same turn.
  13. Repeat the toggle **early** in a turn rather than in the final 10 seconds — 01-RESEARCH.md Open Question 3 asks whether the freeze needs the specific late timing, so both must be checked.
  14. Toggle off then on and then **deliberately click nothing for 40 seconds**. **Expected:** the game does not hang — the decision resolves or the turn advances. This is the auto-skip safety net; a hang here means the force-resolver fix is incomplete.
  15. Confirm no ⏸ pause button appeared in the multiplayer UI (D-04).

  ---

  **C. BUG-03 / BUG-04 — refresh recovery**

  16. Continuing the same live game, the **host refreshes** the page mid-game.
  17. **Expected (healthy path):** the in-progress voyage restores — ingredients, positions, and coins all intact. **Not** a board reset to the start. No false "couldn't restore" dialog on a normal, healthy refresh.
  18. Now force the failure path: in the Firebase console, delete or empty `rooms/{room}/dlog`, then refresh the host again.
  19. **Expected:** the "couldn't fully restore this voyage" dialog appears with a shortfall count and two choices. It must never silently hand back a reset board (D-07).
  20. While that dialog is up, check the **guest** tab. **Expected:** an explanatory strip, not a silently frozen board (D-08).
  21. Choose **Resume anyway**. **Expected:** the guest's explanatory strip clears and the guest starts receiving new events again as play continues. Note whether any duplicate narration lines appear — some re-push is expected and acceptable; permanent silence is not.
  22. Repeat the failure and choose **Restart** instead. **Expected:** a clean return to home with no stale state.

  ---

  **D. BUG-04 — lockstep after the full cycle**

  23. Run the complete canonical sequence once more end to end: pause, unpause, refresh, continue playing several turns.
  24. Compare host and guest side by side: board state, every player's position, ingredient holdings, and coin counts.
  25. **Expected:** identical on both clients. Any divergence is a determinism regression and is a blocking failure regardless of how well A–C went.

  ---

  **E. Full regression**

  26. Run `node scripts/real_game_test.js 2000` and `node scripts/dlog_replay_test.js`. Both must exit 0.

<risks>
**Determinism / lockstep exposure:** this plan writes no code, so it introduces no exposure — it is the plan that *measures* the exposure every other plan created. Section A's control measurement (step 2) and the healthy-refresh check (step 17) both exist to catch a mis-set-up session before its output is trusted.
