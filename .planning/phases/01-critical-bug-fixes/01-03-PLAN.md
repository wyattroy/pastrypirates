<objective>
Make the existing ⏱ timer off/on toggle behave correctly in multiplayer (BUG-02), without adding a pause button (D-04).

Today `watchTimer()` (around index.html:2917) reacts only to the *off* transition — it calls `stopShotClock()` and then, on the way back *on*, does nothing but repaint the UI. That is the confirmed, code-level cause of "the timer never re-arms." But the naive fix is a trap: calling `startShotClock()` unmodified resets `shotClockFired`, which re-enables a second 20-second penalty for the same turn in direct violation of D-06, and `stopShotClock()` has already nulled the shared `shotClockForce` global that nothing but a brand-new decision's `withShotClock()` executor ever repopulates — so the 30-second auto-skip silently stops working for the decision currently in flight. That auto-skip is the only denial-of-service mitigation the turn system has.

Purpose: restore an interactive game after an off→on toggle while keeping both the penalty ledger honest and the safety net armed.

Output: a dedicated `rearmShotClock()` path and a defined behaviour for a null force-resolver.
</objective>

  <behavior>
  The state machine after this task must satisfy:
  - Off→on toggle mid-decision, player then stays silent for 35+ seconds → the decision resolves by itself (auto-skip fires, or the clock visibly expires and the turn advances). The game never hangs indefinitely.
  - Off→on toggle mid-decision, player clicks normally → the click resolves the decision exactly as it would have without any toggle. The click path must not be disturbed.
  - Timer left off entirely → no penalty fires and no auto-skip fires; the game waits for a real click. This is the existing, correct behaviour of `timerOff` and must not regress.
  </behavior>

  <action>
  This is the trap 01-RESEARCH.md Pitfall 1 and Assumption A2 both flag, and the one piece of BUG-02 that a "just re-arm the countdown" fix silently leaves broken.

  `stopShotClock()` sets `shotClockForce=null`. `withShotClock()` — the only assigner — already ran for the decision in flight and will not run again for it. So after an off→on toggle, `expireShotClock()` reaches `if(shotClockForce)shotClockForce();` with a null and the auto-skip does nothing. The countdown looks alive and expires, but the decision is never force-resolved. That silently removes the only DoS mitigation the turn system has against a player who never responds.

  First **confirm the mechanism before fixing it**, because 01-RESEARCH.md rates the *consequence* as unproven even though the code fact is high-confidence: the normal click path (`base.then(...)` inside `withShotClock`) resolves independently of `shotClockForce`, so this defect may degrade only the safety net rather than causing the total freeze Wyatt observed. Reproduce it directly — toggle off then on mid-decision, then deliberately do not click for 35+ seconds, and observe whether anything happens. Record the observed behaviour in the summary either way; it is the evidence that decides whether BUG-02 is one causal chain or two independent defects, which `01-CONTEXT.md` leaves to Claude's discretion.

  Then pick one of the two approaches 01-RESEARCH.md sanctions, and record which and why:

  **(a) Preserve the resolver across the stop.** Instead of discarding it, have `stopShotClock()` stash the current resolver in a `shotClock`-prefixed holding variable and have `rearmShotClock()` restore it when the seat it is re-arming matches the seat the resolver belongs to. This is the smaller diff and restores full parity with a never-toggled turn. The seat match is essential — restoring a resolver that belongs to a previous decision would force-resolve the wrong promise, which is far worse than no auto-skip.

  **(b) Give `expireShotClock()` a defined null-resolver fallback.** If no resolver is available, degrade explicitly and visibly rather than silently: log it, and let the turn wait for a real click instead of pretending the clock did something. Weaker, but honest.

  Prefer (a). Choose (b) only if reproduction shows (a) risks resolving a stale promise, and say so in the summary.

  Whichever you pick, `expireShotClock()` must stop treating a null resolver as an ordinary no-op — the null case gets an explicit, commented branch so the next reader knows it was considered rather than overlooked.

  Do not change how a guest's response is validated or bounds-checked. 01-RESEARCH.md's security domain notes guest-submitted decision values are already consumed without validation; that is a pre-existing gap and this phase must neither widen it nor start narrowing it here.

  Do not introduce randomness of any kind in this path. `Math.random()` is forbidden project-wide in engine-adjacent code, and any jitter near the decision-resolution path would put non-determinism directly into the replay-sensitive machinery.
  </action>

<risks>
**Determinism / lockstep exposure:** MEDIUM. This plan does not touch `dlog`, `logDecision()`, or the `replaying` guard, so it cannot perturb decision *ordering* or the mulberry32 sequence directly. The exposure is indirect but real: force-resolving the wrong pending promise would inject a decision into `dlog` that no player made, and every subsequent replay of that room would faithfully reproduce the wrong game. That is why task 2's approach (a) requires a seat match before restoring a resolver.

Second exposure: a re-arm that double-fires (host and guest toggling within one Firebase round trip) could arm two intervals and expire a decision twice. The `shotClockSeat == null` guard plus the single-`setInterval`-after-`clearInterval` pattern contain this; the two-tab check should include a rapid double-toggle.

Third: `watchTimer()` fires on *every* client for *every* write to the node. All new behaviour must sit behind `isHost`, or guests will run host logic against their own render-only state.

**Coverage gap, stated plainly:** `01-VALIDATION.md` records zero automated coverage of the shot-clock state machine, and extracting it into testable pure functions is explicitly a nice-to-have rather than a blocker for this phase. BUG-02's real verification is therefore the two-tab manual reproduction. The automated gates here assert structure (guards present, penalty ledger not reset, resolver branch exists) — they prove the traps were handled, not that the live timing is right.
