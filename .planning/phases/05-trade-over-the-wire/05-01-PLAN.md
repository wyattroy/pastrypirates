# Plan 05-01: Trade Over the Wire

**A multi-captain trade works, paces, and gives a guest exactly the controls the host has.**

Everything below is either a locked ruling of Wyatt's, a figure quoted from `docs/TRADE-SYSTEM.md`,
or a fact measured by reading this tree on 2026-08-23. **`docs/TRADE-SYSTEM.md` is required reading
before Task 2 — all of it, at its trigger, not once at session start.** CLAUDE.md §4 forbids
touching anything that trades without it, and this is the subsystem that has burned this project
hardest.

> Wyatt, 2026-08-23: *"for the next 8 hours, any time you think you need my input, instead look to
> all of your documents to understand my intention."*

**An instruction to READ, not permission to guess.** At any point where this run wants a ruling, the

- **YES** → cite it and proceed.
- **NO** → take the **reversible** option, write down in the SUMMARY what was chosen and what the

A recorded decision costs him a sentence to overturn. A stalled run costs him the window.

## ⚠ MP-08 IS NOT A DECISION. IT IS A CONVERGENCE JOB.

> Wyatt, 2026-08-23: *"guest should OBVIOUSLY get the real coin slider, and you already know why —
> guests and hosts are given the same experience."*

**The ruling is already binding and already written down three times. Cite it; do not re-derive it.**

- **CLAUDE.md rule 23 / `docs/DISPLAY-RULES.md` §1:** *"Host/guest decides WHO COMPUTES the game and
  WHO CREATES THE ROOM. It never decides WHAT IS DRAWN."* A remote seat getting a different control
  is precisely the thing that rule forbids.
- **CLAUDE.md rule 8, consistency:** the same gesture behaves the same way everywhere **unless Wyatt
  chose the exception.** He did not choose this one. The code itself flags it as an open hole
  (`4/src/ui/util.js:1747-1753`, `4/src/ui/flow.js:1447-1450`): *"this must be closed if /4 ever
  ships online multiplayer."* **/4 is shipping online multiplayer. That is this milestone.**
- **`docs/DISPLAY-RULES.md` §4:** `ask()` is prompt **fork 2** and is **NOT converged**. The stepper
  fallback exists *because of* that unconverged fork. So this is a convergence job, not a
  preference.

**So criterion 2 is: `coinStepper` is DELETED, and every seat — local or remote — gets the slider,
reached from both tiers by name.**

**Rule 23's design-time question, answered before a line is written:**

> **What makes the host's coin control and a guest's coin control agree?**

**They are the same builder, producing the same markup, wired by the same function.** Not two
controls kept in step. If at the end of Task 3 there are two pieces of slider markup in the tree,
the task failed however green the gates are — and `stage.js` will say so out loud, because it
identifies the slider **by class** in two places (`input:not(.apSlider)` and `.apSliderWrap`), so a
second copy that differs by one class name gives the guest a flat card where the host gets the
radial bloom. That is the 2026-08-19 complaint — *"the guest doesn't have radial action menus"* —
waiting to happen for the eighth time.

## THE CONVERGENCE ANSWER FOR MP-09 (rule 23 / DISPLAY-RULES §1)

> **What makes a local holder's answer and a remote holder's answer agree?**

**They are the same function, reading the same offer, writing into the same list, in the same seat
order.** Not two paths kept in step.

The tree does not have that today. **It has the answering loop TWICE**, and the diff proves it:
`humanTrade` (`4/src/ui/flow.js:1704-1760`) and `botOpenTradeLive` (`:2196-2242`) hold the same
block, comment for comment, differing only in whether the holder list is filtered by
`worthReAsking`. `docs/TRADE-SYSTEM.md` §8 already names this family — *"A deal is settled in THREE
places, and they must agree"* — and records what the third copy cost: a captain who countered
asking for a different crate had their counter accepted on screen and **the original trade executed
instead.**

**So the deliverable of Task 4 is a DELETION as much as an addition:** one
`collectTableAnswers(asker, offer, holders)`, named by both callers, and the second copy gone. That
is CLAUDE.md rule 9's property too — the elegant version of a trade change deletes code. **Task 3
deletes `coinStepper`; Task 4 deletes an answering loop. Two deletions is what a good night looks
like here.**

**The trap, named so it is refused:** the cheapest-looking build is *"leave the sequential loop
alone and add a parallel branch beside it for the networked case"* — or, in Task 3, *"leave the
host's slider alone and add slider markup to the guest's branch."* **That is the second director**
(`4/src/orchestrator.js:1654`) and it is exactly how seven host/guest divergences got built. **When
a second consumer appears, CONVERGE — make the first go through the new path too.**

**Do NOT add a tenth Firebase listener.** `watchDraftPrompt` already exists, is already in the
parity gate's `LISTENERS` array, and already carries a per-seat prompt with several outstanding at
once. Its own comment says the payload is *"deliberately narrower … so a field it one day needs is
already built."* **This is that day.** Widen the payload; reuse the listener.

## THE DETERMINISM DOOR — this plan does not go through it

Phase 3 deliberately left the corpus uncaptured *for Phases 4 and 5*. **This plan does not need it
and must not use it.**

- `respondToOffer` is **pure** — no `r()` draw anywhere in it (read 2026-08-23,
  `4/src/engine/index.js:1066-1104`). Bot answers can be computed inside a restructured round with
  no determinism consequence **provided the ORDER is preserved**.
- `holdersOf` is a `.filter` over `this.players`, so it **already returns holders in seat order**.
  Fixed order is free; keep it and never sort.
- `g.ev({t:"openoffer",…})` fires before any answer is collected and settlement events fire after.
  Neither moves.
- `noteDemand`, `rememberRefusal` and `refusedFlagWanted` are called per holder — **call them in
  holder order, after the round, exactly as today.**
- **The slider change emits nothing.** A coin count already crosses `settleTrade` as a number; where
  the player dragged it is a UI-tier fact.

**If you find yourself about to change what the engine emits, STOP and report it instead.** Say why
a UI-tier fix cannot do it. CLAUDE.md prefers UI-tier, and going through that door costs Phase 3's
whole safety net.

## WHAT THE WIRE COSTS TODAY — arithmetic, not a measurement (rule 6)

`startShotClock` (`4/src/ui/util.js:2081`) holds **one** seat and a **30,000ms** deadline, and every
`ask()` re-arms it for whoever is being asked. The answering loop asks holders **one at a time**. So
for a hail reaching three other captains:

| | `ask()` calls in series | clock windows in series |
|---|---|---|
| three holders, all answer plainly | 3 + 1 (the asker picks) | **4 × 30s = 120s** |
| three holders, all counter | 3 × 3 + 1 | **10 × 30s = 300s** |

And the stepper multiplies the middle row. `coinStepper` (`4/src/ui/flow.js:1605`) is a loop of
whole `ask()` calls, so for a remote counter of N coins it costs **N taps plus a confirm = N+1 full
prompt round trips**, each one a Firebase prompt write, a response write, a complete panel re-render
on both screens, a fresh 30-second clock and another `…is deciding…` broadcast to the table. The
slider costs **one**. Against the mean bot purse of 5.51 (TRADE-SYSTEM §6 — recompute in Task 1), a
typical 5-coin counter is **6 round trips against 1**.

**These are ceilings derived by reading the source. They are NOT the number.** Real captains answer
in seconds; what a real captain actually endures is the *sum of everyone else's thinking time, in
series*, plus a round trip and a full prompt re-render per step. **Task 1 measures it. Nothing in
this plan may quote a duration that was not measured.**

The line the other captains stare at during all of it is `ask()`'s own:
`` `${pn(seat)} is deciding…` `` with `{wait:true}` — **a wait line registers no dismissal
deadline** (DISPLAY-RULES §2), so it stands for the entire chain. That string, and how long one
screen holds it without a break, IS criterion 3.

## ABANDONMENT ORDER — this run may not finish, and that is planned for

Tasks are ordered so that stopping early always leaves the game **better than it was and never
half-safe**.

| Stop after | What a player gets | What is still broken |
|---|---|---|
| Task 1 | Nothing shipped — numbers where there were assumptions: the hail baseline, and what a multi-captain trade actually costs in seconds | Everything |
| Task 2 | **MP-07 proven, or fixed** — a guest can counter with a crate over the wire | Guests still get the ± stepper; pacing unchanged |
| Task 3 | **+ MP-08** — a guest drags the same slider the host drags, and the stepper is gone | Pacing unchanged |
| Task 4 | **+ MP-09** — one round, every captain asked at once, one answering loop instead of two | — |
| Task 5 | + shipped, played, and the record corrected | — |

**Task 3 is before Task 4 on purpose.** It is smaller, it is self-contained, and it lands a
player-visible win early — and because Task 4 leaves the counter sub-machine on the singular `ask()`
channel, a converged slider is inherited by the parallel round for free rather than needing doing
twice.

**Task 4 is last of the code tasks on purpose.** It is the only one that restructures a path the
game already plays correctly. Until it runs, trading is slow but works; a half-done parallel round
is a stalled table.
