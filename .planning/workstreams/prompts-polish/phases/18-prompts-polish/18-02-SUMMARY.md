**1. [Rule 2 - missing critical functionality] `RECIPE_BOOK` had to be exported for the test to be writable at all**
- **Found during:** Task 1, while writing the `scripts/narration_test.js` assertion block
- **Issue:** The plan requires matching assertions by title text across all 21 entries plus the fallback, but `recipeArticle()`/`recipeTitle()` both take an `ings` array, not a title — the test needs access to each entry's `{ings,title,article}` triple to drive the calls and check the result. `RECIPE_BOOK` was module-private, so this was unwritable without either exporting it or hand-duplicating all 21 `ings` arrays inside the test (which would itself violate "match by title text, not by a second hardcoded copy of the data").
- **Fix:** Exported `RECIPE_BOOK` from `src/ui/recipe.js`. The test then iterates it and checks each entry's `recipeArticle(entry.ings)` against an *independently* hardcoded 8-title no-article set (not `entry.article` alone, which would be tautological), plus asserts `entry.article` agrees with that same independent answer key.
- **Files modified:** `src/ui/recipe.js`
- **Verification:** `node scripts/narration_test.js` — all 84 FIX-08 assertions PASS; `RECIPE_BOOK.length === 21`
- **Committed in:** `fb4e2df` (Task 1 commit)

**2. [Rule 3 - blocking issue] The narration audit tool's live-eval sandbox didn't know `recipeArticle` and broke `npm test`**
- **Found during:** Task 3, immediately after committing the `src/ui/board.js` change and re-running the full verify chain
- **Issue:** `npm test` went from 23/23 to 22/23 — `scripts/narration_audit_check.js` failed with `card misc:board:adhoc.voyageend.victory rendered no text`. `art-review/narration-core.js` re-evaluates each shipped copy site's *raw source expression* live (via `new Function(...)`) against a curated `CTX_BASE` scope of allowed identifiers, so its own review page always shows real shipped text rather than a hand-transcribed copy. `recipeArticle` is a brand-new identifier the raw `victoryLine` expression now references, and it wasn't in `CTX_BASE` — so the sandboxed eval threw a `ReferenceError`, silently caught and treated as "could not evaluate." This is the exact failure mode this repo's own history already names: *"a new symbol used in a shipped copy site must be added to narration-core.js's CTX_BASE, or EVERY snippet in that file fails to render"* (STATE.md, `20260729-playtest-bug-fixes`).
- **Fix:** Added `recipeArticle` to `art-review/narration-core.js`'s import from `src/ui/recipe.js` and to `CTX_BASE`'s allowed-identifier list, mirroring how `recipeInfo`/`winRecipeSpan` were already registered there.
- **Files modified:** `art-review/narration-core.js`. `art-review/narration-inventory.json` was also regenerated (not hand-edited) by `scripts/extract_narration_lines.js`, which `npm test` runs automatically before `narration_audit_check.js`.
- **Verification:** `npm test` — 23/23 assertion groups PASS, exit 0 (re-confirmed at final HEAD).
- **Committed in:** `ff27b12` (see Issues Encountered — this commit's message and authorship don't reflect that it carries this fix)

## Issues Encountered

**A concurrently-running coordinator process, sharing this exact worktree, committed Task 3's staged changes bundled into two of its own unrelated docs commits.** Per this session's `<sequential_execution>` framing, this plan ran on "the main working tree (worktree isolation disabled)" — not an isolated per-agent git worktree — because the environment's own worktree-base-check reported `shouldDegrade: true`. That means this session and the coordinator's own concurrent session were operating on the literal same checkout at the same time.

What happened, in order:
1. This session edited and verified `src/ui/board.js`, `art-review/narration-core.js`, `art-review/narration-inventory.json`, and `.planning/todos/pending/copy-shipped-vs-approved-gate.md`, then ran `git add` on exactly those four files (`git status --short` confirmed only those four staged, nothing else).
2. Before this session's own `git commit` call executed, the coordinator's concurrent process ran its own `git commit` in the same working tree. Because this session's changes were *already staged* (`git add` had already run), the coordinator's commit swept them in alongside two coordinator-authored files (`docs/DRIVING-THE-GAME.md` §8b, `.planning/WINDOWS.md`) that this session never touched and never staged.
3. The result: commit `ff27b12` ("docs: a hidden tab is a second fake freeze — and it corrupts layout readings") carries this plan's Task 3 code changes (`src/ui/board.js`, `art-review/narration-core.js`, `art-review/narration-inventory.json`, the copy-ledger entry) *and* the coordinator's own unrelated docs work, under a commit message that names neither.

**This was not caused by any git command this session ran incorrectly** — `git add` was scoped to exactly the 4 intended files, and no blanket `git add -A`/`git add .` was used at any point. It is a genuine race in a shared, non-isolated working tree between two live agent processes.

**Verified after the fact, not assumed:** `git show --stat ff27b12` confirms the file list matches exactly (the 4 files this session staged, plus the coordinator's 2 files, nothing else); `git diff` of each of this session's 4 files at `ff27b12` byte-matches what this session wrote and verified before staging; `npm test` at final HEAD is 23/23, exit 0; `src/engine/index.js` is byte-identical to `34f0cb7` (pre-plan HEAD).

**Consequence:** Task 3's changes are correctly and completely committed, but the commit is attributed to the coordinator's docs work rather than to this plan. The Task Commits table above records `ff27b12` as Task 3's commit hash for traceability, with this explanation attached, rather than treating the commit as missing or re-doing the change under a new commit (which would either duplicate the content or require a destructive git operation this session's constraints explicitly prohibit).
