<objective>
Clear both of this phase's human gates in ONE interruption, before any wind-dot code is written:
can Wyatt's iPhone reach the branch build at all, and is the one-way determinism door confirmed?
And give him one file holding every URL and instruction he will need for the Safari afternoon.

Purpose: Safari time is this phase's scarce resource, and the phone is the device whose ceiling D-09
turns into Phase 20's budget. `19-RESEARCH.md` Open Question 2 recommends treating the very first
phone connection as its own small checkpoint, before investing in the full prototype, so a firewall
or router surprise does not eat into the same afternoon budgeted for the actual verdict. And
D-11/D-12 are rated **one-way** in CONTEXT.md — an unintended draw from the game's own RNG stream
desyncs every client and invalidates all 31 determinism fixtures, a re-record explicitly scheduled
for v1.4. That door is confirmed before anything walks through it.

Both questions are put in a single blocking checkpoint with a single answer, at Wyatt's request:
one stop, not two. Folding the door confirmation EARLIER than the task it guards is safe in that
direction — 19-03's tracer carries a `<precondition>` and an acceptance criterion asserting against
the recorded answer, so nothing downstream can run without it.

Output: `19-SAFARI-RUN.md` — the self-serve run protocol Wyatt operates from — plus a recorded
phone-reachability result and a recorded go-ahead.
</objective>

  <context>
    Two quick things, then one answer.

    **First — the phone.** The build is now being served from the Mac so your iPhone can open it
    over wifi. This is deliberately the cheapest possible test: no wind dots exist yet, so all we
    are finding out is whether the phone can see the Mac at all. It is worth knowing now rather
    than on the afternoon you have set aside for the real test, because the phone is the device
    that decides the answer — whatever the phone can handle, not the Mac, becomes the budget the
    next phase is designed around.

    **Second — where the dots get their randomness.** Every dot needs a few random numbers: where
    it starts, how fast it drifts, how far it sways. There are two places those numbers could come
    from.

    The game already has its own stream of random numbers, and every player's browser walks that
    stream in step. That is what keeps everyone in a multiplayer room seeing the same game, and it
    is what 31 saved test games check line for line. If the decoration pulls even a handful of
    numbers out of that stream, every later number shifts — every player's game quietly drifts
    apart from everyone else's, and all 31 saved games stop matching. Putting that right is not a
    quick fix; it means re-recording the whole set, a job already scheduled for a later milestone.

    The other option is the one the storm rain already uses: a **separate, private** stream of
    numbers, started from the game's number so everyone in a room still sees identical dots, but
    taking nothing out of the game's own stream. Same weather in every browser, zero cost to the
    game. That is the way this was already decided, and it is what the plan follows.

    The same answer also covers the standing promise that nothing in this phase edits the game
    engine or changes what it reports. If the build ever appears to need that, it stops and gets
    re-thought rather than pressing on.
  </context>
