<objective>
Answer the cheapest question in the phase first: can Wyatt's iPhone reach the branch build at all?
And give him one file that holds every URL and instruction he will need for the Safari afternoon.

Purpose: Safari time is this phase's scarce resource, and the phone is the device whose ceiling D-09
turns into Phase 20's budget. `19-RESEARCH.md` Open Question 2 recommends treating the very first
phone connection as its own small checkpoint, before investing in the full prototype, so a firewall
or router surprise does not eat into the same afternoon budgeted for the actual verdict. This plan
costs a server, a document and about two minutes of Wyatt's time, and it de-risks everything after
it.

The other human gate this phase needs — confirming the one-way determinism door of D-11/D-12 — sits
in 19-03, immediately before the task that walks through it.

Output: `19-SAFARI-RUN.md` — the self-serve run protocol Wyatt operates from, plus a recorded
phone-reachability result.
</objective>

    the repository root in the background — it binds all interfaces, so the phone can reach it.
    Leave the server running for the rest of the phase; do not stop it until told to commit.

    Read the Mac's wifi address with `ipconfig getifaddr en0` (fall back to `en1` if empty).

    Create `.planning/workstreams/board-wind/phases/19-safari-check/19-SAFARI-RUN.md` with these
    sections, written in plain language for a non-coder, with no console commands anywhere in the
    parts Wyatt reads:

    1. **Serving and the fresh port** — the exact command, the chosen port number, the desktop URL
       (`http://localhost:&lt;PORT&gt;/index.html`) and the phone URL (`http://&lt;LAN-IP&gt;:&lt;PORT&gt;/index.html`).
       State the rule from `docs/DRIVING-THE-GAME.md` §1 in one plain sentence — a port that has
       already served an older build hands back the old code even after a reload — and note that
       this bites harder on the phone, which has no easy hard-reload. Keep a running "ports already
       used" list in this section so nobody has to guess mid-session.
    2. **Turning the prototype on** — the enable link is the same URL with `?wind=1` on the end.
       State that this is the ONLY thing that differs from a normal build, that a normal build shows
       nothing at all, and that once the page is open every other control is on screen and operated
       by touch (per D-04). Give the full tappable link for both desktop and phone.
    3. **The two runs, in order** (D-06) — run 1 is the headroom run (wind the dial up toward 100
       and note where it starts to hurt); run 2 locks the dial to 10 and plays a full voyage with
       narration, ship moves, and storms arriving and leaving. State that both runs happen on
       desktop Safari AND on phone Safari (D-09), and that the phone's number — not the Mac's — is
       the one that becomes the budget.
    4. **Where the answer goes** — a short "record the numbers here" stub, noting that the verdict
       is written into `19-VERDICT.md` at the end of the phase.
    5. **Phone reachability result** — an empty stub for Task 2 to fill.

    Sections 6 (the Chrome pre-flight checklist) and any results are added later by plan 19-06 —
    leave a placeholder heading for it so the file has one home for everything Wyatt needs.
  </action>
